## 선택 기준
- **필수 적합성 조건부터 적용한다.** 기술·제품·소프트웨어의 출시/기능/성능/사용 방식 변화, 기술적 발견, 기술 시스템의 구체적 문제를 설명할 수 있는 소식만 후보로 삼는다. 독자가 관심 가질 것이라는 이유만으로 일반 뉴스가 기술 뉴스가 되지는 않는다.
- 건강·질병 유행, 여행 정보, 일반 정치·주식·연예·범죄 소식은 기술적 변화가 명확한 사건이 아니면 제외한다. 기술 매체에 실렸다는 사실은 기술 적합성 근거가 아니다. 기사 제목을 새 기술 기사로 각색하지 않는다.
- **일반인용도 기술 뉴스다.** 일반인용이라는 이유로 일반 생활 뉴스나 설명하기 쉬운 잡학을 고르지 않는다. 새 기능을 직접 써볼 수 있는 앱·서비스, 익숙한 기술의 새 쓰임, 기술로 가능해진 구체적인 일은 우선 검토한다.
- 기술 전반을 다룬다. 사람들이 알고 싶어할 구체적인 새로운 소식인가를 가장 먼저 본다.
- 제목의 대상·행동은 자료와 일치해야 한다. CCTV·웹캠을 스마트폰 카메라로 바꾸는 식으로 더 익숙한 제품을 임의로 넣지 않는다. 후킹도 확인된 사실 안에서 한다.
- 새롭게 무엇을 할 수 있게 됐는지, 무엇이 놀랍거나 달라졌는지, 독자가 써보거나 남에게 알려주고 싶을지를 평가한다. 익숙한 회사·기술의 변화도 좋지만 기업 인지도만으로 고르지 않는다.
- 일반인용은 기술의 효용·발견·변화를 쉽게 전달할 수 있는 소식, 실무자용은 실제 작업·도입 판단과 연결되는 소식이다. 피해·가격·보안만 반복해서 우대하지 않는다.
- 기술과 직접 관련되지 않은 주식 전망·기업 행사·정치 발언은 후순위다. 이미 제작한 사건은 새로운 별도 변화가 있을 때만 고른다.
- 다양한 수집 자료를 비교하되 분야별 할당이나 AI 금지는 없다. 제목이 다른 같은 사건을 중복 선택하지 않는다.
- 뉴스 브리프(news)와 비교(compare)는 독자의 질문에 맞게 선택한다. 비교는 양쪽 대상·두 개 이상의 비교 축에 자료 근거가 있어야 한다.

## 근거와 반응
- news_urls·hn은 코드가 모은 관측이다. 원문 URL 자체가 기사일 수도 있고 공식 발표일 수도 있으며 source로 구분한다. 값·상태·근거를 다시 작성하거나 반응 수를 추정하지 않는다.
- HN 점수·댓글은 HN 해당 게시물 반응일 뿐 대중 전체 반응이 아니다. 매체 수는 독립 보도 수가 아니고, null은 미확인이지 0이 아니다. 공식 발표만 있는 소식도 흥미롭고 내용 근거가 충분하면 선택할 수 있다. 반응 자료가 없는 경우를 인기 없는 소식으로 단정하지 않는다.
- summary는 피드 요약이다. 확인되지 않은 기능·가격·성능을 덧붙이지 않는다. 오래된 원문을 공유한 커뮤니티 게시 날짜(submission)·검색 추정일(estimated)·네이버 제공일(naver_provided)을 최초 발표일로 쓰지 않는다. 발표일을 확인하지 못하면 announced_at은 빈 문자열이다.
- URL은 수집 자료의 url 또는 news_urls·hn.url만 쓴다. news의 sources에는 기준 자료의 url 하나만 작성한다. 서버가 selected_id와 same_event로 확정한 자료에서 최종 출처 목록을 구성한다. compare의 sources에는 최소한 선택 항목의 url을 포함한다. published_at은 자료의 확인 가능한 날짜 또는 null을 쓴다.

## 같은 사건의 기사 묶기
- 선택한 후보마다 `same_event`에 기준 자료와 **같은 구체적 사건**을 보도·언급하는 다른 자료의 ID와 이유를 반환한다. 선택 ID 자신은 넣지 않으며 근거가 부족하면 빈 배열이다. 자료 전체를 분류하지 않고 선택한 후보의 묶기만 한다. 숫자를 작성하지 않는다.
- 제품·버전/대상, 발표·발견·사고의 내용, 시기와 장소 등 사건을 식별하는 근거가 제목·요약에서 서로 일치해야 한다. 언어·제목이 달라도 같은 사건이면 묶는다. 이유는 양쪽 자료에 보이는 공통 사실로 짧게 쓴다.
- 같은 회사·분야·키워드·취약점 유형만 공유하면 묶지 않는다. 동일 제품의 다른 버전/발표, 별개 피해 사건, 행사 예고와 다른 기술 발표도 구분한다. 일반적인 배경 설명은 기사 수를 늘리는 근거가 아니다. 불확실하면 제외한다.
- 기준과 묶은 자료 사이에 모순이 없는지 확인한다. 동일 자료 ID를 두 후보에 중복 배정하지 않는다.
- news의 최종 sources는 서버가 기준 자료를 먼저, same_event 순서대로 최대 6개 구성한다. 같은 사건으로 판단한 추가 기사는 same_event에 ID와 이유를 넣는다. 비교 후보의 반대편 기술·배경 출처는 sources에 포함할 수 있지만 기준 사건과 다르면 same_event에 넣지 않는다. 묶기는 sources의 최대 6개 제한과 별개다.
- 서버가 묶인 자료의 관측 기사·매체·HN 반응을 URL 중복 제거 후 계산한다. 사건 동일성은 너의 판단이고 보도 독립성이나 전체 인기를 확정하는 것은 아니다.

## 출력
JSON 한 개: candidates 배열과 shortage_reason 문자열. 후보마다 selected_id는 자료의 id를 그대로 쓴다.
후보 필드는 제공된 스키마를 따른다. same_event는 `[{"id": 자료ID, "reason": "두 자료에 공통으로 보이는 사건 근거"}]` 또는 `[]`다. title·summary·reader_question·why_interest·format_reason은 선택 이유와 사건의 정체가 읽히는 한국어로 쓴다. 과장된 파산·산업 멸망·확정되지 않은 영향은 쓰지 않는다.
anchor_url은 선택 자료의 url, attention_query는 소식을 식별하는 제품명·사건이다. compare_targets·compare_axes는 news이면 빈 배열이다.
상위 일반인용 2개·실무자용 1개 순서로 선택한다. 적합한 후보가 적으면 확보한 만큼만 반환하고 shortage_reason에 이유를 적는다. 없는 후보를 만들지 않는다.
