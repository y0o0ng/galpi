## 편집 목표와 말투

- 독자가 두 대상의 실제 차이와 자신의 상황에 맞는 선택 기준을 이해하도록 쓴다. 최근 소식은 비교의 계기로 연결하고, 관련 원리는 차이를 이해하는 데 필요한 만큼만 설명한다.
- 본문과 완결된 강조 문장, 게시 캡션은 **짧고 담백한 해요체**로 쓴다. 친근함을 위해 반말이나 과한 감탄을 섞지 않는다.
- 제목, 항목명, 지표명, 라벨은 짧은 명사구도 허용한다. 모든 라벨에 억지로 `~예요`를 붙이지 않는다. 직접 인용문은 원문의 말투를 유지한다.
- 발표를 사실로 설명할 때는 `공개했어요`, 조건이나 해석에는 `~할 수 있어요`, 미확인 사항에는 `아직 확인되지 않았어요`처럼 상태를 구분한다. 전망을 확정된 결과처럼 쓰지 않는다.
- 독자가 가장 알고 싶어하고 이해에 꼭 필요한 정보를 앞에 둔다. 관심을 끌 만한 변화·차이·문제·영향을 먼저 보여주고, 배경은 그 내용을 이해하는 데 필요한 위치에서 설명한다. 이는 정보의 우선순위이며 고정된 진행 순서가 아니다.
- 발표 주체·날짜·제품명·사양을 관성적으로 앞에 나열하지 않는다. 독자의 핵심 질문에 중요할 때 본문에 넣고, 부차적인 정보는 편 정보나 캡션에 남긴다.
- 독자가 기술이나 제품을 모를 수 있으면 무엇이고 어디에 쓰이는지, 핵심 내용을 이해하는 데 필요한 만큼 짧게 설명한다. 흥미를 위해 대상의 정체와 핵심 정보를 숨기지 않는다.
- 표지 제목은 단순한 제품명·공개·출시 안내에 그치지 않고, 독자가 다음 카드를 넘기고 싶게 만드는 후킹을 담는다. 근거가 있는 뜻밖의 차이, 눈에 띄는 변화, 독자에게 미치는 영향이나 궁금증을 짧고 강하게 드러낸다. 약간 자극적인 표현과 도발적인 질문도 허용하며, 모든 표지를 같은 문형으로 만들지 않는다.
- 후킹은 이번 소식에서 확인된 구체적인 변화·가능해진 작업·가격이나 사양의 의외성에서 뽑는다. 막연한 기술 용어와 가격만 붙여 궁금증을 만들지 않는다. 본문에서도 핵심 변화와 독자의 이해관계를 선명하게 드러내되 원문보다 강한 성능·성과를 만들어내지 않는다.
- 제목의 강도는 유지하되 사실·조건을 왜곡하거나 근거 없는 최상급·성공·실패를 단정하지 않는다. 질문형 제목도 거짓 전제를 넣지 않는다. 본문은 표지가 만든 궁금증에 실제로 답하고, 핵심 답을 마지막까지 미루지 않는다.
- 설명 여부는 기술 전공자가 아니라 일반 독자의 일상적인 지식선을 기준으로 판단한다. 내 기기에 저장하거나 내 기기에서 처리한다는 정도의 개념은 기초 강의로 풀지 않는다. 용어가 등장했다는 이유만으로 정의 카드를 만들지 않는다. 설명을 빼면 이번 소식의 기능·차이·의미를 이해하기 어려울 때만 설명하며, 짧은 문장이나 괄호로 충분하면 별도 페이지를 쓰지 않는다. 낯선 제품의 정체·용도와 이미 익숙한 일반 개념의 정의를 구분한다. 실무자용도 불필요한 정의 대신 작업·도입 판단에 필요한 기능, 가격, 호환성, 조건을 구체적으로 쓴다. 둘 다 정확성과 해요체는 유지한다.
- 한 장에는 중심 메시지 하나를 둔다. 먼저 짧은 문장 두 개 정도로 설명을 시도하고, 빠뜨리면 뜻이 달라지는 조건은 남긴다. 긴 문장을 작은 글씨로 압축할 계획을 세우지 않는다.
- 기업 발표, 독립 실측, 편집자의 해석을 구분한다. 핵심 성능이 기업 주장이라면 해당 카드에서도 `회사 설명으로는` 등으로 귀속을 밝힌다.
- 정리나 판단을 넣을 때는 앞 문구를 반복하기보다 독자가 기억할 내용 하나를 남긴다. 필요 없는 팔로우 요청, 다음 편 예고, 상투적인 전망을 덧붙이지 않는다.

## 기술 비교의 구성과 장수

이 후보는 `mode: compare`로 선택됐다. 후보의 비교 대상과 독자의 선택 질문을 유지한다. 이번 소식으로 왜 두 대상을 다시 비교할 필요가 생겼는지 짧게 연결한다.

내용에 맞게 설명 단계를 정하고, 각 단계는 1~2페이지로 구성한다. 단계의 종류·개수·진행 순서는 주제와 독자의 질문에 맞게 직접 정한다.

전체는 최소 4장, 권장 5~6장, 최대 8장이다. 한 장에 억지로 압축하거나 장수를 맞추려고 빈 페이지와 반복 설명을 만들지 않는다.

각 축에서 A와 B에 같은 질문을 던진다. 한쪽 장점과 다른 쪽 무관한 단점을 대칭인 것처럼 배치하지 않는다. 대상 이름·정확한 버전·기준일·가격 조건을 확정하고, 두 대상의 근거를 각각 확인한다. 예전 버전이나 오래된 자료를 사용할 때는 날짜와 범위를 밝힌다.

벤치마크는 테스트·설정·단위·버전이 비교 가능한 경우에만 수치로 우열을 설명한다. 조건이 다르면 차이를 밝히고 직접적인 순위·점수차를 주장하지 않는다. 데이터가 없는 축은 미확인으로 남기거나 제외하고, 비어 있는 칸을 추정으로 채우지 않는다. 가격은 요금제·단위·통화·지역·기준일 등 실제 판단에 필요한 조건을 함께 적는다.

억지로 비교 축을 늘리거나 모든 지표를 하나의 점수로 합치지 않는다. 선택 기준을 제시할 때는 보편적인 승자를 선언하기보다 독자의 상황과 그 근거를 설명한다.

근거를 확인한 결과 비교 자체가 성립하지 않으면 막힌 대상·축·이유를 보고한다. 임의로 뉴스 브리프 형식으로 바꾸지 않는다.

## 카드별 원고와 그림 지시

- 각 카드에 번호, 중심 메시지, `layout`, `eyebrow`, 필요하면 `title_style`과 `composition`을 지정한다. 한 편의 카테고리는 일관되게 쓴다.
- 기존 9종 `cover`, `story`, `points`, `numbers`, `compare`, `closing`, `stat`, `steps`, `quote` 중 내용에 맞는 것을 고른다. 같은 레이아웃을 반복해도 된다. 9종을 모두 사용할 필요는 없다.
- README의 해당 layout 입력 필드명으로 게시 문구를 적는다. 예: `title`, `body`, `statement`, `items`, `columns`, `labels`, `rows`, `value`, `unit`, `label`, `note`, `attribution`. 목록과 비교 열은 항목별 확정 문구를 모두 적는다.
- 화면에 보이는 문구와 내부 설명을 분리한다. 각 카드에 내부용 사실 근거 ID 목록을 별도로 적고, 문구에 근거 ID를 섞지 않는다.
- 제목은 뜻 단위에서 최대 두 줄로 쓴다. 현재 한 줄 한글 폭 참고값은 display 7자, standard 12자, quiet 15자다. 공백·영문·숫자가 섞이면 실제 폭이 달라지므로 이것을 일괄 글자 수 제한으로 쓰지 않는다. 최종 적합은 렌더 검증으로 확인한다.
- 그림이 필요한 카드에는 대상, 대상 사이의 관계, 방향·순서, 라벨, 반드시 보여야 할 특징, 그리면 뜻이 달라지는 요소를 적는다. 근거가 필요한 관계에는 사실 확인 ID를 연결한다. 그림이 필요 없으면 `그림 없음`으로 명시한다.
- 그림을 직접 제작하거나 공용 레이아웃을 수정하지 않는다. 도트 그림의 의미를 정하고, 세부 위치·크기·여백은 공용 템플릿의 허용 영역에서 조립 에이전트가 조정하도록 한다. 별도 좌표가 뜻을 전달하는 데 필수인 경우에만 제작 제약에 이유와 함께 지정한다.
- 숫자 비교는 같은 지표의 두 대상에 같은 단위와 기준을 사용한다. 측정 조건·버전·날짜가 다른 자료를 동등한 실측처럼 비교하지 않는다. 비교가 성립하지 않으면 숫자 그래프 대신 조건 차이를 설명한다.
- `numbers`는 지표별 `max`와 단위, 판단 기준을 확정한다. 값이나 그래프 상한을 출처의 수치인 것처럼 만들어내지 않는다. 편집상 축 상한은 실제 측정값과 구분해 적는다. 높은 값이 유리한지 단정할 근거가 없으면 좋고 나쁨을 표시하지 않는다.
- `stat`은 큰 숫자에 기준·조건을 붙인다. `quote`는 발언 주체·날짜와 인용을 구분하며, 번역이면 번역임을 밝히고 사실 확인 목록에 원문을 남긴다.

## 사실 확인

- 제목, 본문, 그림 라벨, 수치, 결론, 캡션의 모든 사실 주장에 근거 ID를 연결한다. 편집 해석은 그 전제의 근거를 연결하고 해석임을 구분한다.
- 공식 발표, 원 논문, 프로젝트 릴리스 노트, 표준 문서 등 1차 출처를 우선한다. 독립 실측을 다루면 실측 보고서 자체를 확인한다. 발표가 있었다는 사실과 성능이 검증됐다는 사실은 별개다.
- 발표일, 출시일, 사용 가능일, 기사 수정일을 구분한다. 후보의 위험·불확실 항목은 하나씩 확인하고, 해결하지 못한 주장에는 한계를 붙이거나 원고에서 뺀다.
- `## 사실 확인 목록`에 `번호 | 주장 | 출처 | 원문 인용` 네 열의 Markdown 표를 쓴다. 번호는 `C1`, `C2`처럼 쓰고, 출처 열에는 원 URL을 적는다. 원문 인용은 글자 그대로 복사해 ASCII 큰따옴표로 감싼다. 여러 근거가 필요하면 행을 나눈다.
- 기존 대조 도구는 25자 이상 인용만 검사한다. 해당 주장을 포함한 충분한 원문 문맥을 인용한다. 검사 길이를 채우려고 문구를 만들거나 서로 떨어진 문장을 이어 붙이지 않는다. 짧은 원문밖에 없다면 자동 대조 미지원으로 메모하고, 검증 완료로 보고하지 않는다.
- 내려받은 원문은 지정 자료 폴더에 출처별로 저장한다. 접근이 막혔으면 원 URL과 사용한 로컬 파일의 관계를 기록한다. 검색 결과 일부만 보고 확인한 것처럼 쓰지 않는다.
- 산출물을 쓴 뒤 지정 Python으로 `{{repo}}/reels/factcheck.py`에 대본 경로와 `--json`을 넘겨 검사한다. 로컬 원문 대조는 기존 `URL=로컬파일` 인자를 쓴다. missing 0뿐 아니라 모든 주장 행에 인용·출처가 있고 결과가 `found: true`인지 확인한다. 실패·누락은 고치거나 해당 주장을 뺀다. 실행할 수 없으면 그 사실을 보고한다.
- 문자열 일치는 인용 존재만 확인한다. 인용이 주장과 비교 조건을 실제로 뒷받침하는지는 별도로 확인한다.

## 산출물

지정 대본 파일 하나와 지정 자료 폴더 안의 출처 자료만 작성한다. 저장소의 공용 코드·템플릿·설정은 수정하지 않는다.

대본 파일 형식:
1. 편 정보: `card_id`, `topic`, `mode: compare`, 대상 독자, 독자가 궁금해할 질문, `date`, 짧은 `source`, 실제 발표 주체·발표일·원 URL
2. 카드 구성: 직접 정한 설명 단계와 단계별 페이지 배정, 순서와 각 장의 중심 메시지
3. 카드별 확정 원고: layout 입력 필드, 내부용 근거 ID, 그림 지시, 의미상 필수 제작 제약
4. 게시 캡션: 짧은 해요체 소개, 필요한 한계, 발표 주체·발표일·원문 링크. 링크는 사실 확인 목록에 사용한 출처만 넣는다.
5. 사실 확인 목록: 주장과 원문 인용 표
6. 메모: 후보 불확실성 처리, 뺀 내용과 이유, 실행한 검사와 결과, 미확인 사항

후보의 최초 발표일은 필수 조건이 아니다. 최근 언급으로 선정된 기존 기술은 새 발표로 묘사하지 않는다. 발표일이 미확인이면 편 정보·캡션에 날짜를 억지로 채우지 않는다.
발행일은 서버 입력을 그대로 사용하고, 발표일과 혼동하지 않는다. 모델이 날짜를 추정하거나 새로 만들어 넣지 않는다.
최종 보고는 한국어로 짧게: 산출물 경로, 구성과 장수, 사실 확인 결과, 미확인 사항.

## 서버 전달 형식

카드별 게시 필드를 한 곳에서 정확히 읽을 수 있게 `## 조립 원고` 절에 JSON 코드 블록 하나를 둔다. 객체는 README의 deck 형식 그대로 `mode`, `topic`, `date`, `source`, `cards`를 가지며, cards에는 확정 layout과 실제 게시 필드만 넣는다. 그림의 실제 파일 경로는 조립 단계가 정하므로 `art`를 넣지 않는다. 그림 지시·근거 ID·검토 메모는 JSON 밖에 둔다. `## 게시 캡션` 절은 게시할 문구만 담고 다음 절과 분리한다. 접근이 막힌 출처의 로컬 대조가 필요하면 자료 폴더의 `source-map.json`에 원 URL과 그 폴더 안 파일의 절대 경로를 기록한다.
