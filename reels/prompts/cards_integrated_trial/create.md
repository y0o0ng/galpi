## 편집

`{{repo}}/reels/prompts/script_cards_{{mode}}.md`의 후보·독자·편집·말투·장수·출처·사실 목록 기준을 적용한다. 이 흐름에서는 대본 작성 뒤 별도 조립에 넘기지 않고 네가 대본과 카드를 함께 만든다. 그 문서의 대본만 작성/그림 제작 금지/쓰기 경계는 이 흐름의 작업·출력·자료 폴더 허용으로 대체한다. 내용 단계와 순서는 직접 정하고 단계마다 1~2페이지를 쓴다. 제품 뉴스는 제품의 정체·실제 기능·새로운 차이가 중심이며 익숙한 개념의 정의로 대신하지 않는다. 구체적 사실에서 강한 제목을 뽑고 본문이 답한다.

## 디자인과 자유도

`{{repo}}/reels/cards/README.md`·`design-v0.2.md`·`render.py`와 기존 9종 템플릿을 출발점으로 쓴다. 팔레트·던파 비트비트체 v2 원본 비율·Pretendard Medium/Bold·공통 브랜드 헤더/푸터·픽셀 로고·진행 표시·릴스 시온 캐릭터·1080×1350 규격을 유지한다. 가로 폰트 확장은 하지 않는다.
기존 템플릿의 고정 슬롯, 제목 크기, composition, 항목 수를 그대로 따르라는 규칙은 이 흐름에서는 적용하지 않는다. 편 전용 렌더 코드를 작업 폴더에 만들거나 공용 코드를 복사해 콘텐츠 영역을 수정할 수 있다. 콘텐츠의 위치·높이·분할·그림 비중·타이포그래피 크기·항목 배치를 조정해도 된다. 같은 브랜드와 반복되는 그리드의 질서는 유지한다. 공용 파일 자체는 수정하지 않는다.
헤더·푸터는 콘텐츠 자유도에서 제외한다. 공용 Renderer.frame의 로고·브랜드명·선·정렬·좌표·폰트·크기·색·진행 표시 형태를 그대로 사용한다. 카테고리·현재/전체 페이지 번호·확정 날짜·해당 출처 값만 내용에 맞게 바꾼다. 필요하다고 판단해 브랜드 영역을 재설계하지 않는다. 콘텐츠는 y=160~1239 안에 둔다. 서버가 최종 카드에 같은 공용 헤더·푸터를 합성하므로 콘텐츠가 이 영역을 침범하면 가려진다.

사진도 콘텐츠의 시각 자료로 허용한다. 제품 실물·실제 장면·사건을 이해시키는 데 도움이 되면 적합한 사진을 먼저 찾아보고 사용한다. 모든 장에 픽셀 큐브나 비슷한 노트북 그림을 반복할 필요는 없다. 사진은 원래 사진으로 보여주고 억지로 픽셀화하지 않는다. 구조·작동 관계에는 픽셀 도식을, 실물·현장에는 사진을 쓰는 등 역할로 선택한다. 정확한 제품·버전·장면을 확인하고 원본 비율을 유지하며 중요한 부분을 자르지 않는다.
공식 보도용 이미지·사용이 허용된 원본 등 이용 가능한 자료를 선택하고 편 폴더에 저장한다. `assets.json`은 배열이며 각 항목에 `file`(편 폴더 내부 파일), `kind`(photo/pixel), `source_url`, `provider`, `usage_terms`, `caption`, `purpose`를 기록한다. 직접 만든 픽셀 자산의 source_url은 null이어도 되며 외부 사진은 원URL과 확인 가능한 사용 조건을 적는다. 단순히 웹에 공개됐다는 이유로 자유 이용으로 간주하거나 허용 조건을 지어내지 않는다. 적합한 사진을 확보하지 못하면 억지로 사용하지 않고 이유와 대안을 보고한다. 실제 제품 사진처럼 보이는 허구의 이미지를 만들지 않는다. 사진 안에 게시 문구를 새로 넣지 말고 텍스트는 렌더 코드로 그린다.

지면이 빈 이유가 빠진 제품 정보인지, 너무 작은 그림인지, 벌어진 간격인지 먼저 판단한다. 필요한 정보와 의미 있는 그림에 공간을 쓰고, 단어 정의·반복 문구·장식으로 빈 곳을 채우지 않는다. 표지와 결론은 여백을 허용하고, 설명·제품 소개는 읽을 내용과 충분한 크기의 그림으로 구성한다. 모든 장을 같은 밀도로 만들지는 않는다.

## 한 장씩 제작하는 필수 반복

1. 해당 장의 중심 메시지·게시 문구·근거·그림을 정하고 렌더한다.
2. 그 장의 원본과 390px 축소본을 실제 이미지 도구로 각각 연다. 코드나 미리보기 전체만 읽고 시각 검토했다고 하지 않는다.
3. 제품 정보의 충실함, 글과 그림의 연결, 불필요한 빈 공간, 그림의 디테일과 크기, 모바일 가독성·대비·잘림·줄바꿈을 자가 검토한다.
4. 문제가 있으면 문구·그림·배치를 직접 수정하고 다시 렌더·확인한다. 해결되거나 해결 불가 이유를 기록한 뒤 다음 장으로 넘어간다. 자가 검토는 독립 검토의 PASS가 아니다.
5. 전체 완성 후 모든 장을 함께 보고 흐름·리듬·내용 중복을 확인한다.
`self-review.md`에 장별 실제 확인 파일·발견한 문제·수정 내용·확인 결과를 순서대로 기록한다. 수정이 필요 없으면 구체적 확인 근거를 남긴다. 확인하지 않은 장을 확인했다고 기록하지 않는다.

## 산출물

작업 폴더에 `manuscript.md`(게시 문구·그림 지시·C번호별 주장/원URL/원문 인용·캡션·메모), `deck.json`(실제 게시 문구·데이터·자산), `art.py` 및 그림, `render_episode.py`, `assets.json`, `caption.txt`, `self-review.md`, `report.md`를 만든다. 화면의 문구와 manuscript/deck/caption은 일치해야 한다. 내부 근거 ID는 이미지에 넣지 않는다. 출처 원문과 원URL 대응을 자료 폴더에 보존한다. 공식 발표·실측·해석을 구분하고 지원하지 않는 사양·가격 조건·가능한 작업을 만들지 않는다.
출력은 01.png부터 전 장, preview.png, mobile/의 390px 축소본, jpeg/의 RGB JPEG다. report.md에는 출력 목록과 템플릿에서 조정한 것·이유·미확인 사항을 적는다. 패키지 설치·운영 설정·DB·git·게시를 하지 않는다. 쓰기는 이 편 폴더들에 한정한다.

## 서버 실행 계약

본문 폰트 `{{font_path}}`, 굵은 본문 폰트 `{{bold_font_path}}`를 사용한다. 파일이나 의존성이 없으면 임의 교체·설치 없이 보고한다.
편 전용 `render_episode.py`는 생성·수정 에이전트의 Codex sandbox 안에서 다음 명령으로 현재 manuscript/deck/자산을 렌더할 수 있어야 한다:
`{{python}} {{work_dir}}/render_episode.py --out {{out_dir}} --font {{font_path}} --bold-font {{bold_font_path}}`
편 전용 코드는 서버가 sandbox 밖에서 직접 실행하지 않는다. 서버는 신뢰된 공용 `finalize_integrated.py`만 실행해 생성된 PNG의 헤더/푸터·preview·mobile·JPEG를 동기화한다. 직접 확인할 때도 이 최종 합성 결과를 연다.
`manuscript.md`에 기존 대본과 같은 `## 조립 원고` JSON, `## 게시 캡션`, `## 사실 확인 목록` C번호/주장/원URL/원문 인용 표를 반드시 남긴다. `## 게시 캡션`의 마지막 줄은 해시태그 정확히 5개다: `#시온의원리노트` → 주제 태그 2개(편의 핵심 대상을 사람들이 실제로 검색하는 넓은 말로, 편에서만 쓰는 전문용어 금지. 예: `#반도체` `#메모리`) → 범용 태그 2개(`#과학` `#상식` `#IT` `#테크` 중에서만 고른다). deck/caption과 같아야 하며 그림 파일·사진은 편 폴더 내부 경로만 사용한다.

## 최종 응답 JSON — 고정 계약

최종 응답은 아래 JSON 객체만 반환한다. 키를 추가하지 않고, Markdown 제목·코드 펜스·설명을 붙이지 않는다. Codex CLI가 이 JSON 스키마를 강제하고 `response.json` 파일로 저장한다. 이 파일을 별도로 직접 작성하지 않는다.

완료했으면:
```json
{"status":"ok","message":"제작과 자가 검토를 완료했어요. 독립 검토는 아직 받지 않았어요."}
```

완료할 수 없으면:
```json
{"status":"blocked","message":"완료할 수 없는 구체적인 이유를 적어요."}
```

`status`는 정확히 `ok` 또는 `blocked`, `message`는 문자열이다. `ok`는 독립 검토 PASS나 게시 승인이 아니다. `report.md`는 출력 목록·조정 이유·미확인 사항을 적는 설명용 문서이며 서버는 여기서 완료 상태를 읽지 않는다.
