# 갈피 음성 반이중(half-duplex) 파이프라인 설계

> Date: 2026-08-01
>
> Status: H1·H2·H4·H5와 지연 C1·C2 Pi 배포·실기기 인수 완료. H6a 서버 단일 턴과 H6b iPhone 화면 활성 경로 인수 완료·디스플레이 소등 호출은 플랫폼 제약으로 종료, H6d 단축어 직접 일정 생성 Pi·실기기 인수 완료, H3 미구현
>
> Scope: 핸즈프리 반이중 음성 대화, 전사 검증·되묻기, 음성 답변 분리, iOS 잠금화면 단축어 입구, 기존 채팅 파이프라인 재사용
>
> 이 문서는 V4-B 음성의 **새 단일 기준**이다. [Realtime 설계](voice-realtime-design.md)는 R0~R2c-1의 구현·인수 기록으로 보존하되, 이후 신규 작업의 기준으로 삼지 않는다.

## 0. 왜 바꾸는가

R0~R2c-1을 Pi 운영까지 올린 뒤 실기기에서 반복 관찰된 실패다. 추측이 아니라 저장된 대화와 로그에서 나왔다.

| 관찰 | 근거 | 원인 |
|---|---|---|
| 한국어 날짜 청취 실패 | `"8월 6일"` → `"파월 주일"` → `"8월 1일"` 고착. 사용자가 3회 정정했으나 회복하지 못함 | Realtime 모델의 한국어 이해 |
| 동문서답 | `"내 옷 취향이 어떤 것 같아?"` → `"고취향 맞아. 저한테도 들리는데…"` | 같음 |
| 노트가 있는데 회수 안 함 | `내 옷 취향을 다시 한 번 정리해줄래` 노트가 `ready`·`ai_readable`인데 도구 미호출 | 모델이 도구 호출을 판단 |
| 보정 전사 25~29% 유실 | `REALTIME_TRANSCRIPTION_EMPTY` 5건 / 22턴. assistant 답변까지 함께 소실 | 미규명 |
| 헛기침 오중단 | 마이크 거리 의존, 근접 시 5/5 | VAD가 성대 소리를 발화로 판정 |

앞의 셋은 파이프라인 수정으로 해결되지 않는다. 모델 자체의 문제이고, Realtime은 오디오를 직접 이해하므로 우리가 만든 보정 전사가 아무리 정확해도 답변에 반영되지 않는다.

결정적으로 같은 오디오에서 `gpt-transcribe`는 `"8월 6일"`을 두 번 다 정확히 전사했다. **전사 능력이 없는 게 아니라, 정확한 전사가 답변 생성에 도달하지 못하는 구조가 문제다.**

### 무엇을 포기하는가

즉시 끼어들기(barge-in), 1초 미만 응답, 억양·감정의 직접 이해를 포기한다. 사용자 사용 패턴은 빠른 핑퐁이 아니라 노트를 놓고 생각하며 주고받는 대화이므로, 응답 속도보다 **정확한 이해와 신뢰할 수 있는 기록**이 우선한다는 판단이다.

## 1. 측정된 지연 (H0 스파이크, 2026-08-01 Pi 실측)

`gpt-transcribe` + `gpt-5.6-terra` + `gpt-4o-mini-tts`, 3회 반복 median.

|구간|median|범위|
|---|---|---|
|STT 전체|674ms|475–1312|
|LLM 첫 바이트|372ms|353–554|
|LLM 전체|1797ms|1441–1856|
|TTS 첫 오디오|545ms|440–705|
|TTS 전체|1627ms|1399–1696|

|말 끝나고 첫 소리까지|median|
|---|---|
|직렬 (LLM 전체 대기)|4777ms|
|스트리밍 (첫 문장부터 TTS)|3333ms|

**병목은 API가 아니라 침묵 감지다.** 세 API 합계가 1.5초인 반면 침묵 대기 1.8초가 스트리밍 총합의 54%를 차지한다. 따라서 최적화 우선순위는 ①침묵 임계값 ②스트리밍 TTS ③API 순이다.

### 이 수치에 포함되지 않은 것

낙관 편향이므로 설계 판단에서 감안한다.

- 폰 → Pi 오디오 업로드 (측정치는 Pi → OpenAI 구간만)
- 폰에서의 오디오 디코딩·재생 시작
- TTS 시작에 필요한 **첫 문장** 대기 (측정은 첫 바이트 기준)
- 합성 TTS 음성으로 측정했다. 실제 실내 발화는 STT 정확도가 더 낮을 수 있다

현실 보정 시 **4.0~4.5초**로 본다. 진행 기준 6초 이내다.

### 남은 지연과 줄이는 순서

C2까지 LLM·TTS 스트리밍을 적용했고 실기기에서 체감이 확실히 빨라졌다고 인수했다. 남은 조정은 침묵 임계값과 earcon이며 각각 별도 변경으로 검토한다.

1. **스트리밍 TTS — 약 1,000ms.** LLM 첫 바이트가 372ms인데 전체는 1,797ms라 1,400ms를 그냥 기다린다. 첫 문장이 확정되는 즉시 읽기 시작한다. 걸림돌이 셋이라 두 단계로 나눈다.

   - **C1 조각 재생 — 2026-08-03 Pi 배포·실기기 인수 완료.** 답변을 문장 조각으로 나눠 TTS를 여러 번 부르고, 지금 조각을 재생하는 동안 다음 조각을 미리 받는다. LLM 스트리밍이 없으므로 **지연은 아직 줄지 않는다.** 목적은 재생 큐와 iOS 동작을 먼저 검증하는 것이다. H1에서 자동재생 차단과 AudioContext suspend로 두 번 물렸으므로, 되돌리기 쉬운 단계에서 오디오 경로를 확인하고 간다.
   - **C2 LLM 스트리밍 — 2026-08-03 Pi 배포·실기기 인수 완료.** 문장이 완성되는 즉시 조각을 progress로 흘려보내 읽기 시작한다. **음성 턴에서만 스트리밍한다.** 텍스트 채팅은 기존 비스트리밍 호출과 `result` 한 번을 그대로 쓰므로 회귀 위험이 없다. 화면 타이핑은 열지 않았다.

#### 스트리밍으로 실제로 얼마나 줄어드는가 (2026-08-03 실측)

설계가 근거로 삼았던 `첫 바이트 372ms`는 **HTTP 첫 바이트였고 첫 토큰이 아니었다.** `gpt-5.6-terra`는 추론 모델이라 첫 텍스트까지 1.2~1.4초가 reasoning에 들어가며 **이 시간은 스트리밍으로 줄지 않는다.** 실제 절약은 답변 길이에 좌우된다.

|답변|첫 delta|첫 문장|전체|절약|
|---|---|---|---|---|
|12자|1247ms|1254ms|1258ms|**4ms**|
|252자|1374ms|1988ms|2948ms|**960ms**|
|2747자|5691ms|5880ms|21399ms|**15.5초**|

우리 코드 경로로 끝단 확인했을 때 295자 답변에서 1154ms를 앞당겼다. 즉 **짧은 턴은 체감 차이가 없고 길수록 커진다.**

음성 답변은 기본 6문장 이내로 생성하고 최대 600자까지 읽으므로 보통은 전부 들린다. 사용자가 자세한 설명을 요청해 상한을 넘을 때만 닫는 말과 이어 듣기로 넘어간다.

**도구 호출 앞에는 텍스트가 나오지 않았다.** `schedule_prepare`를 부르는 응답에서 텍스트 delta가 0개였으므로, 흘려보낸 문장이 최종 답변이 아니게 되는 경합은 이 모델에서 일어나지 않는다. 그래도 모델이 바뀔 수 있으니 발생하면 조각을 버리고 로그로 센다.
2. **침묵 1200 → 1000ms — 200ms.** 설정만 바꾸면 되지만 사용자가 천천히 말하는 편이라 문장 중간을 자를 수 있다. 실사용 로그를 보고 조정한다.
3. **생각 중 earcon — 0ms.** 지연을 줄이지 않고 죽은 침묵만 없앤다.

더 빠른 텍스트 모델로 내리는 선택은 하지 않는다. 답변 품질 때문에 아키텍처를 바꾼 것이므로 되돌리는 셈이다.

### 왕복 통합 (설계만, 미구현)

현재 한 턴에 폰과 Pi 사이를 세 번 왕복한다. 오디오 업로드와 전사 수신, 질문과 답변, 답변과 음성이다. 뒤의 둘은 폰을 거칠 이유가 없고, 서버가 전사에서 답변, TTS까지 내부에서 이으면 왕복 두 번이 사라지며 스트리밍도 서버 안에서만 처리하면 된다.

대신 화면에 전사와 답변 텍스트를 언제 보여줄지 정해야 한다. NDJSON으로 전사를 먼저 보내고 이어서 오디오를 흘리는 형태가 후보다. 스트리밍 TTS를 구현할 때 함께 검토하고, 그 전에는 지금의 세 왕복을 유지한다.

## 2. 상태 기계

```
LISTENING      음성 대기
  │ 음성 감지                              idle 120초 ──→ ENDED
CAPTURING      발화 녹음
  │ 침묵 1.2초(CLARIFYING 응답은 0.8초) 또는 최대 120초
TRANSCRIBING   STT                        타임아웃 30초 ──→ RECOVER
  │
VALIDATING     폐기 판정 ──→ 조용히 LISTENING
  │            불확실 슬롯 ──→ CLARIFYING (누적 2회 상한)
THINKING       회수·답변 생성. 마이크 OFF   실패 ──→ RECOVER
  │ 첫 문장
SPEAKING       스트리밍 TTS 재생. 마이크 OFF
  │
COOLDOWN       500ms
  └──→ LISTENING

CLARIFYING     짧은 되묻기 TTS → LISTENING (응답은 같은 pending_turn에 병합)
RECOVER        짧은 안내 음성 → LISTENING
```

모든 상태에 타임아웃과 LISTENING 복귀 경로를 둔다. 마이크가 꺼진 채 멈추는 상태를 만들지 않는다.

**재생에도 감시 타이머가 필요하다.** `playAudio`는 `ended`만 기다렸고 타임아웃이 없어 이 규칙을 어기고 있었다. 재생이 4초 동안 진행되지 않으면 끝난 것으로 보고 넘어간다. `timeupdate`가 오는 동안에는 계속 미루므로 긴 조각이 잘리지는 않는다.

### 파라미터 초기값

|이름|값|근거|
|---|---|---|
|침묵 종료|**1200ms**|1800ms는 총 지연의 54%. 실사용 로그로 조정|
|CLARIFYING 침묵 종료|**800ms**|한 단어 답변을 오래 기다릴 이유가 없다|
|최대 발화|120초|기존 R2b 상한 재사용|
|COOLDOWN|**500ms**|마이크를 완전히 끄므로 방 잔향 꼬리를 피한다. 브라우저 `echoCancellation`은 그대로 켜 둔다|
|idle 종료|120초|배터리·과금 보호|
|소음 바닥|초기 12프레임의 하위 20%|답변 직후 사용자 목소리가 중앙값을 끌어올리는 고착을 피한다|
|소음 재보정|LISTENING 8초 무감지|잘못 잡은 문턱이 영구 고착으로 남지 않게 한다. 발화를 잡으면 타이머를 해제한다|

## 3. 턴 폐기 규칙

**신규 구현하지 않는다.** `lib/realtime-turn-store.js`의 `isPersistableUserTurn`을 그대로 쓴다. 실기기 표본으로 만들고 회귀 테스트가 붙어 있다.

```
폐기 ⟺ 문장부호·공백 제거 후 빈 문자열
      또는 실질 문자 2자 이하이고 남은 글자가 전부 필러 집합
```

폐기된 턴은 사용자 턴으로 제출하지 않고 조용히 LISTENING으로 돌아간다. 시온이 반응하지 않는다.

`녹음 0.5초 미만`은 폐기 조건으로 쓰지 않는다. 실측된 헛기침 턴은 1536~1621ms였으므로 길이 기준이 걸리지 않는다.

## 4. 전사 검증과 되묻기

되묻기는 **답변 생성 전**에만 한다. 답변한 뒤의 정정은 하지 않는다.

### 되묻는 조건

- 전사가 비었거나 지나치게 짧다
- 날짜·시각·금액·수량·이름 같은 **핵심 슬롯이 불명확**하다
- 일정 생성·삭제·저장처럼 오류 비용이 큰 행동이다

검색 0건은 되묻기 조건이 **아니다.** 회수가 이미 QA 청크 단위이므로 전사가 맞으면 본문에 있는 내용을 찾는다. `8월 6일` 시 원문도 `ready` 청크에 있고 텍스트 채팅에서 정상 회수됨을 확인했다. 0건은 정직하게 "못 찾았어"로 답한다.

### 되묻는 방식

막연한 "다시 말해줘"가 아니라 **불확실한 슬롯만** 묻는다.

> "시 제목을 '8월 1일'로 들었는데, '8월 6일'이라고 한 거야?"

### pending_turn

정정 왕복을 별개 질문 세 개로 저장하지 않는다. 하나의 휘발 상태로 유지한다.

```
pending_turn
  raw_transcript   원본 전사
  uncertain_slot   불확실 슬롯 이름과 위치
  correction       사용자 정정값
  final_query      슬롯만 교체한 최종 질의
```

**병합은 LLM에 맡기지 않는다.** 원본 문장은 그대로 두고 슬롯 값만 치환한다. LLM 병합은 호출이 추가되고 환각 여지가 생긴다.

되묻기는 **누적 2회 상한**이다. 초과하면 되묻기를 멈추고 최선 추정으로 진행하거나 화면 입력을 안내한다. 되묻기 응답 자체가 오전사되어 무한 루프가 되는 것을 막는다.

DB에는 `final_query`만 사용자 메시지로 저장한다. 원본 전사와 정정 이력은 진단 로그에만 남긴다.

## 5. 음성 답변과 화면 답변의 분리

마이크를 끄고 재생하므로 긴 TTS는 사용자를 붙잡아 둔다. 핸즈프리 상태에서 정지 버튼을 누르려면 폰을 잡아야 하므로 핸즈프리가 깨진다.

LLM은 한 번만 호출하고 화면과 음성에 같은 답변을 쓴다. 음성 턴의 시스템 지시는 기본 답변을 **6문장 이내**, 제목·목록·표 없이 결론부터 말하게 한다. 사용자가 특정 항목을 자세히 설명해달라고 명시하면 그 항목만 길게 답할 수 있다. 서술형 길이 지시는 A/B에서 오히려 1,605자까지 늘었고, 문장 수와 구조를 규칙으로 못 박았을 때 196~360자로 줄었다.

음성 길이는 프롬프트만 믿지 않고 코드에서 최대 600자로 가둔다. 답변이 그 안이면 최대 7개 조각으로 전부 읽고, 넘을 때만 닫는 말을 위한 한 자리를 남긴다. `gpt-4o-mini-tts`, speed 1.3 실측은 초당 약 8자라 4,000자 문서를 그대로 읽으면 8분 가까이 걸린다.

닫는 말은 `end()`로 미룬다. 답변이 마침 상한에서 끝났다면 남은 글이 없으므로 "자세한 건 화면에 정리해뒀어"를 붙이지 않는다. 붙이면 거짓말이 된다.

### 이어 듣기

핸즈프리로 쓰면 화면을 못 본다. 남은 답이 있을 때만 **`화면에 정리해뒀어. 더 들으려면 말해줘.`**로 닫는다. `계속`·`더`·`이어서`·`말해줘` 등을 한 번 말하면 남은 내용을 400자 조각으로 끝까지 읽고 다시 묻지 않는다.

**서버는 아무것도 기억하지 않는다.** 답변과 함께 아직 안 읽은 나머지를 돌려주고, 사용자가 이어 듣기를 요청하면 클라이언트가 그 나머지를 다시 보낸다. 스트리밍이든 아니든 같은 경로로 처리되고 세션도 offset도 없다.

이어 듣기 턴은 새 질문이 아니므로 모델도 저장도 거치지 않고 확인 카드도 건드리지 않는다. 남은 것이 없을 때의 `계속`은 평범한 발화로 흘려보낸다.

알려진 낮은 확률 경계가 하나 있다. 정상 길이의 여러 문장을 모두 읽은 뒤 마지막 문장이 클라이언트 `spokenRemaining`에 중복으로 남을 수 있다. 이때 안내가 나오지 않으므로 사용자가 직후 우연히 이어 듣기 어휘를 말해야만 마지막 문장을 다시 읽는다. 실기기 인수 뒤 사용자 판단으로 재배포·재인수 비용보다 발생 확률이 낮다고 보고 현재는 수정하지 않는다.

**"결론 먼저"가 실제로 동작하는지는 A/B로 확인했다.** 같은 질문에 지시문이 없으면 앞 세 문장이 `~로 보고 정리하겠습니다`, 배경 설명으로 채워졌고, 지시문이 있으면 첫 문장부터 핵심 발전 방향을 말하고 둘째에서 결론, 셋째에서 단서를 달았다. 다만 모델이 항상 따른다는 보장은 없으므로 이어 듣기가 안전망이다.

**자르기만으로는 부족하다.** 문서형 답변의 앞부분을 읽으면 개요를 읽다 끊긴다. `{spoken, full}` 두 필드를 받는 대신 **음성 턴에서는 결론을 먼저 말하게** 한다. 앞 2~3문장만 들어도 답이 되게 하고 그 뒤에 근거를 잇는다. 스트리밍과 자연스럽게 맞고 새 필드가 필요 없다.

**마크다운 기호는 벗기지 않는다.** 읽힐 것으로 의심했으나 실제로는 아니었다. 같은 문장을 기호 있는 것과 없는 것으로 합성해 되전사했더니 `## 결론`은 `결론`으로, `---`는 무음으로 처리됐고 길이도 7.70초로 같았다. 오히려 기호를 뺀 쪽이 `1.`을 `1점`으로 읽어 더 나빴다. 기호가 읽힌다는 전제로 코드를 넣지 않는다.

TTS는 첫 문장이 확정되는 즉시 시작한다. 스트리밍은 선택이 아니라 필수다. 측정상 1444ms를 절약한다.

### 조각 재생 (C1)

- 나누기는 서버가 한다. `POST /api/voice/speak/segments`가 문장 조각 배열만 돌려주고 모델은 부르지 않는다. 600자 상한과 닫는 말은 `selectSpokenText` **한 곳에서만** 적용된다
- 오디오 라우트 `POST /api/voice/speak`는 그대로 두고 조각마다 호출한다. 조각은 상한보다 짧으므로 다시 잘리지 않는다
- 소수점과 줄임표에서는 끊지 않는다. `3.5`, `음...`이 갈라지면 어색하게 읽힌다
- 12자 미만 조각은 앞뒤로 붙인다. `응.` 하나 때문에 왕복을 늘릴 이유가 없다. 짧은 답변은 그래서 한 조각으로 남는다
- 조각 수 상한은 8이다. 넘으면 꼬리를 하나로 묶어 호출 수를 가둔다
- **재생은 제스처로 잠금을 푼 요소 하나만 재사용한다.** 조각마다 새 `Audio`를 만들면 iOS에서 두 번째부터 막힌다
- 다음 조각 받기는 지금 조각의 **재생 시작 전에** 건다. 재생 뒤에 걸면 직렬이라 빨라지지 않는다

화면에는 정지 버튼을 둔다. 긴급 중단용이며, 이를 위해 양방향 인터럽트를 다시 만들지 않는다.

### 조각별 음량 맞추기

조각마다 TTS를 따로 부르면 **요청별로 음량이 달라진다.** 실기기에서 한 문장만 작게 들리는 것으로 나타났다. 조각을 나눈 대가이므로 서버에서 같은 기준으로 맞춘다.

- 귀는 RMS를 따라가므로 사용자 실기기 선택값인 **RMS 0.18을 목표**로 하고, 피크가 0.97을 넘지 않도록 이득을 깎아 클리핑을 막는다
- 이득 상한은 6배다. 거의 무음인 조각을 목표까지 끌어올리면 잡음만 커진다
- 16비트 PCM이 아니면 손대지 않는다
- 음량을 재려면 조각 전체가 필요하므로 스트리밍 대신 버퍼링한다. 조각이 짧아 비용이 작다
- **WAV 헤더의 길이를 진짜 값으로 고쳐 쓴다.** provider는 스트리밍으로 만들어 `data` 크기에 `0xFFFFFFFF`를 적어 보낸다. C1까지는 청크 전송이라 연결 종료가 끝을 알렸지만, 버퍼링하며 `Content-Length`가 붙자 재생기가 데이터가 더 온다고 믿고 `ended`를 쏘지 않아 턴이 끝나지 않았다. 실기기에서 마지막 턴 뒤 듣기로 돌아가지 못한 원인이다

### 말하는 속도

`speed`는 `gpt-4o-mini-tts`에서 동작한다. 실제 호출로 확인했다. 같은 문장이 기본 41,856 bytes에서 `speed=1.15`일 때 38,016 bytes로 짧아졌고, 4.0을 넘기면 `400`으로 거절된다.

- 기본값은 `1.3`이며 `VOICE_TTS_SPEED`로 덮어쓴다. 실기기에서 고른 값이다
- 범위는 코드에서 `0.25~4.0`으로 가둔다. 설정값이 벗어나면 매 턴이 `400`으로 죽는다
- 전달 지시문에서 `너무 빠르지 않게`를 뺐다. 지시문과 `speed`가 서로 싸운다

## 6. 저장 경계

기존 텍스트 채팅 경로를 그대로 쓴다. `dbSaveChatExchange`가 이미 세션 보장·user/assistant 순서·임베딩 20자 가드를 한 transaction에서 처리한다.

- `messages`에는 `final_query`와 `full` 답변을 저장한다. `spoken`은 저장하지 않는다
- R2c-1의 `realtime_turn_receipts`·exactly-once 기계는 **필요 없어진다.** 전사가 답변보다 먼저 확정되므로 두 반쪽을 대사할 이유가 없다. schema v10 테이블은 무해하므로 제거하지 않고 미사용으로 둔다
- 음성 출처 턴은 **topic 자동 저장에서 제외**한다. 전사 오류가 지식 베이스에 굳으면 되돌리기 어렵다. 명시적 저장만 허용한다
- 원본 오디오는 DB·Vault·backup·temp file에 저장하지 않는다. 기존 R2b 경계를 유지한다

전부 단위 테스트를 통과한 상태에서 실기기에서만 나왔다. 다음 단계에서 같은 유형을 미리 잡기 위해 기록한다.

**H2 저장 — 2026-08-01 Pi 배포·실기기 인수 완료.** messages 499→509(5턴이 `shared-main`에 순서대로), `note_chunks` 110 불변으로 topic 자동 저장 0건, 헛기침 턴 0건 저장을 확인했다. 음성 루프가 자체 `/api/chat` 호출을 버리고 텍스트와 같은 `sendSingleMessage`에 위임한다. 그래서 음성 턴이 `shared-main`에 저장되고 메인 채팅에 마크다운·저장 버튼·일정 카드까지 기존 렌더링으로 그려진다. 서버 변경은 없다. 통과 기준: 5턴이 `shared-main`에 순서대로 저장, 폐기 규칙으로 헛기침 턴 0건 저장, topic 자동 저장 0건.

세 가지를 함께 정리했다.

- **패널 로그 제거.** 본문을 메인 채팅이 그리므로 패널이 같은 말을 다시 적으면 중복이다. 패널은 상태 표시줄만 남긴다
- **`overrideText` 호출에서 `inputEl.focus()` 생략.** 핸즈프리 대화 중에 모바일 키보드가 올라오는 것을 막는다
- **`sendSingleMessage`가 결과를 반환.** `{ok, reply}` 또는 `{ok:false, reason:'busy'|'error'|'empty'}`. 텍스트 답변이 진행 중이면 `isLoading` 가드가 음성 턴을 거절하는데, 이를 실패와 구분해 알려야 음성 루프가 조용히 멈추지 않는다

**C2 스트리밍·낭독 마감 — 2026-08-03 Pi 배포·실기기 인수 완료.** 첫 문장이 완성되면 TTS를 시작하고, 조각 RMS 0.18·실제 WAV 길이 헤더·재생 진행 감시·소음 바닥 하위 20%와 8초 재보정·기본 6문장 답변·한 번 요청으로 끝까지 이어 듣기를 적용했다. 로컬 347/347, Pi 343/343과 핵심 배포·서빙 hash, 새 PID·HTTP 200·warning 0건을 확인했고 사용자가 실기기에서 정상이라고 인수했다. UI는 Markdown 빈 줄 제거, 공통 16px 거터·600px 읽기 폭, 44px 터치 타깃과 테마 hairline을 함께 확인했다.

**판정은 모델이 아니라 좁은 어휘로 한다.** 확인 카드의 존재 이유가 "모델이 틀려도 사람이 막는다"인데, 그 확인마저 모델에 맡기면 안전장치가 사라진다. 오판정의 대가가 비대칭이다 — 못 알아들으면 손으로 누르면 그만이지만, 잘못 알아들으면 승인 없이 일정이 등록된다.

- 조각 하나의 바깥 상한은 **14자**다. 그보다 길면 접두어를 떼기 전에 문장으로 본다
- 확인 창은 카드가 뜬 뒤 **2턴**이다. 한참 뒤의 `응`이 묵은 카드를 등록하면 안 된다. 창을 넘겨도 카드는 남고 손으로 누를 수 있다
- 음성은 자기 요청을 만들지 않고 **카드 버튼과 똑같은 핸들러**를 부른다. 같은 `clientRequestId`, 같은 `POST /api/tasks`

- 등록 실패는 카드를 해제하지 않는다. 화면에서 다시 누를 수 있어야 한다

**확인은 그 턴에 끝낸다.** 카드가 떠 있을 때 등록도 취소도 아닌 말을 하면 카드를 그 자리에서 취소하고 평범한 대화로 넘어간다. 일정을 부탁해 놓고 한참 뒤에 다시 볼 이유가 없고, 다시 원하면 카드를 새로 만들어 달라고 하면 된다.

```
카드가 떠 있는데 사용자가 말함
  ├ 등록 어휘  → 등록하고 "일정 등록했어."
  ├ 취소 어휘  → 취소하고 "등록하지 않을게."
  └ 그 외      → 조용히 취소하고, 평소대로 LLM에 보낸다
```

이 규칙 하나가 세 가지를 대신한다. 확인 창(N턴) 개념이 사라지고, 묵은 카드가 쌓이지 않으며, 늦은 맞장구가 엉뚱한 일정을 등록할 수 없다. 카드는 LLM 호출 **전에** 취소되므로 서버가 대기 카드를 알 필요도 없다.

```text
음성 단축어 "시온아" 또는 Siri로 "시온 대화" 실행
  → iOS 텍스트 받아쓰기
  → POST /api/voice/shortcut/turn
  → 갈피 공용 voice-turn core
  → JSON answer
  → iOS 텍스트 말하기
```

- PWA는 열지 않는다. 긴 답변 확인, 과거 기록 열람, 노트 수동 저장, 일정 수정·완료·취소·삭제처럼 화면 확인이 필요한 일에만 연다. 명시적인 새 일정 생성만 H6d에서 예외로 연다
- 갈피 웹앱이 백그라운드에서 마이크를 켜거나 자체 호출어를 듣지 않는다. `시온아` 단독 호출은 사용자가 명시적으로 켠 iOS **음성 단축어(Vocal Shortcuts)** 가 맡는다
- 대안 경로로 Siri를 활성화한 뒤 단축어 이름 `시온 대화`를 말할 수 있다. 일반 Siri 단축어 실행과 `시온아` 단독 호출을 같은 기능으로 오해하지 않는다
- 첫 버전은 한 번 실행에 질문 1회다. 잠금 상태 단일 턴을 인수한 뒤 같은 실행 안에서만 최대 3턴을 연다
- iOS `텍스트 말하기`를 사용하므로 첫 버전의 목소리는 현재 OpenAI TTS `echo`와 같지 않다. 음성 파일 반환·재생은 별도 필요성이 확인되기 전에는 만들지 않는다
- PWA 상시 마이크, 무한 대화 루프, 잠금화면에서의 노트·설정 변경과 기존 일정 mutation은 범위 밖이다

### 한 파이프라인, 두 입·귀

```text
PWA:      브라우저 VAD → gpt-transcribe ─┐
                                           ├→ 공용 voice-turn core
단축어:   Apple 텍스트 받아쓰기 ──────────┘   회수 → GPT → shared-main 저장
                                           ├→ PWA: progress 조각 → OpenAI TTS
                                           └→ 단축어: JSON → Apple 텍스트 말하기
```

공용화 대상은 transport가 아니라 **텍스트가 확정된 뒤의 한 턴**이다.

- 기존 `/api/chat` 안의 회수·모델·저장 구간을 한 번만 실행하는 공용 함수로 최소 분리한다. 단축어 라우트가 자기 서버의 `/api/chat`을 HTTP로 다시 호출하거나 같은 코드를 복사하지 않는다
- 공용 함수는 `shared-main` 세션 잠금, 최근 대화, A2 전역 청크, 활성 일정, 웹·논문 읽기 도구, 모델 snapshot, `dbSaveChatExchange`를 그대로 사용한다
- 음성 여부를 스트리밍 callback 존재로 추론하지 않고 서버가 `voiceTurn: true`로 명시한다. 단축어는 progress stream을 소비하지 않아도 6문장 이내·제목/목록 없음·결론 우선 지시를 받아야 한다
- PWA는 기존 `source:'voice'` progress와 C2 문장 조각 스트리밍을 유지한다. 단축어의 `URL 콘텐츠 가져오기`는 완성된 JSON을 기다리므로 C2 스트리밍은 재사용하지 않는다
- 클라이언트가 `source`, 모델, DB session ID, 활성 노트, 웹검색 여부, 도구 목록을 고르지 못한다. 단축어 라우트가 음성 source·GPT·`shared-main`·허용 도구를 서버에서 고정한다

### 기존 기기 등록을 인증의 뿌리로 쓰는 법

현재 일정 알림의 `assistant_push_subscriptions`는 기기 계정이 아니라 서버가 알림을 보낼 Web Push endpoint와 암호화 키의 등록이다. `subscription_id`, `device_label`, 요청 본문의 `deviceId`는 복사할 수 있으므로 그 값만으로 발신 요청을 인증하지 않는다. Web Push의 `p256dh`·`auth`도 다른 프로토콜의 키라 API bearer로 재사용하지 않는다.

대신 활성 Push 구독에 단축어 전용 자격증명을 하나 연결한다.

```sql
assistant_shortcut_credentials
  id                    INTEGER PRIMARY KEY
  subscription_id       INTEGER NOT NULL UNIQUE
  token_sha256           TEXT NOT NULL UNIQUE
  token_prefix           TEXT NOT NULL
  status                 active | revoked
  created_at             INTEGER NOT NULL
  last_used_at           INTEGER
  revoked_at             INTEGER
  FOREIGN KEY subscription_id
    REFERENCES assistant_push_subscriptions(id)
```

- 등록된 iPhone의 인증된 PWA에서 현재 활성 Push 구독에 대해 `시온 단축어 연결`을 명시적으로 실행한다
- 서버는 최소 32바이트의 무작위 token을 만들고 원문은 그때 한 번만 돌려준다. DB에는 SHA-256과 식별용 짧은 prefix만 저장하고 로그·오류·백업 메타데이터에 원문을 남기지 않는다
- 단축어는 `Authorization: Bearer <기기 전용 token>`으로 정확히 `/api/voice/shortcut/turn`만 호출한다. 이 token으로 일반 `/api/chat`, 노트, task, Codex, 설정 API를 호출할 수 없다
- 서버는 token hash와 연결된 Push 구독의 `status='active'`를 함께 확인한다. Push 구독이 `expired`·`revoked`가 되거나 단축어 자격증명을 폐기하면 다음 호출부터 거절한다
- Push 구독이 재설치·재등록으로 바뀌면 단축어도 다시 연결한다. 결합이 조금 불편해지는 대신 잃어버리거나 폐기한 기기의 음성 입구가 함께 닫힌다
- Shortcuts 안의 bearer는 내보내기·공유 과정에서 복사될 수 있으므로 하드웨어 attestation으로 부르지 않는다. 단일 route scope, 활성 구독 결합, rate limit, 즉시 revoke가 유출 반경을 줄이는 경계다
- H6 route도 기존 Tailscale Serve의 private canonical HTTPS 안에만 둔다. scoped token은 Tailscale을 대신해 인터넷 공개를 허용하는 근거가 아니다
- 기존 전체 `API_TOKEN` middleware에서 단축어 경로만 무인증으로 통과시키지 않는다. exact path에 전용 인증 middleware를 먼저 적용하고, 다른 모든 `/api/` 경로는 기존 전체 token 경계를 유지한다
- credential당 동시 실행은 1개, 초기 rate limit은 1분에 10회로 둔다. key는 credential ID와 socket 주소를 함께 사용하며 token 원문이나 질문을 rate-limit 로그에 넣지 않는다

사용자에게 보이는 의미는 **등록된 기기의 호출만 받는다**이고, 실제 보안 계약은 **활성 등록에 묶인 별도 비밀을 가진 호출만 받는다**다.

### API 계약

첫 요청:

```http
POST /api/voice/shortcut/turn
Authorization: Bearer <scoped-device-token>
Content-Type: application/json
```

```json
{
  "text": "내일 일정 뭐 있어?",
  "requestId": "ios-shortcut가 턴마다 만든 UUID"
}
```

후속 요청은 서버가 발급한 `conversationId`만 추가한다.

```json
{
  "text": "병원에는 몇 시까지 가면 돼?",
  "requestId": "새 UUID",
  "conversationId": "opaque-random-id"
}
```

응답:

```json
{
  "answer": "내일 오후 3시에 병원 예약이 있어.",
  "conversationId": "opaque-random-id",
  "canContinue": true,
  "messageId": 123
}
```

- `text`는 NFC 정규화·trim 뒤 1~2,000자, JSON 본문은 8KiB로 제한한다
- `requestId`는 UUID 한 개이며 credential 안에서 멱등 키다. 같은 ID·같은 본문은 저장된 결과를 재생하고, 같은 ID·다른 본문은 `409`로 거절한다
- `conversationId`는 DB session ID가 아니다. credential에 묶인 128-bit 이상 난수의 서버 소유 휘발 상태이며 5분 TTL·최대 3턴이다. 다른 credential이 보내거나 만료·상한을 넘기면 새 대화를 요구한다
- 실제 대화 저장 위치는 항상 `shared-main`이다. Shortcuts가 임의 세션을 읽거나 쓰지 못한다
- `answer`는 음성 지시로 생성한 완결 답변이며 같은 전문을 assistant 메시지로 저장한다. 첫 버전에서는 별도 화면용/낭독용 LLM을 두 번 호출하지 않는다
- H6a 단일 턴에서는 `canContinue:false`, H6c를 연 뒤에는 3턴 상한에 닿기 전까지만 `true`다
- `Cache-Control: no-store`를 붙이고 오류는 token·질문 원문 없이 안정된 code와 짧은 한국어 안내만 돌려준다

네트워크 timeout 뒤 단축어가 같은 `requestId`를 다시 보낼 수 있으므로 저장 멱등성은 메모리에만 두지 않는다.

```sql
voice_shortcut_receipts
  id                    INTEGER PRIMARY KEY
  credential_id         INTEGER NOT NULL
  request_id            TEXT NOT NULL
  request_sha256         TEXT NOT NULL
  status                 pending | completed
  conversation_id       TEXT NOT NULL
  attempt_count          INTEGER NOT NULL DEFAULT 1
  user_message_id        INTEGER
  assistant_message_id   INTEGER
  created_at             INTEGER NOT NULL
  updated_at             INTEGER NOT NULL
  completed_at           INTEGER
  UNIQUE (credential_id, request_id)
```

완료 receipt와 user/assistant 메시지 ID 확정은 같은 DB transaction에 둔다. 완료 요청의 재전송은 assistant message에서 답을 다시 읽어 provider 호출과 메시지 삽입을 반복하지 않는다. 프로세스가 provider 응답 전에 죽은 `pending`은 메시지를 만들지 않았음을 확인한 뒤 bounded retry하고, 이미 완료된 행을 추측으로 다시 실행하지 않는다. 프로세스 crash를 가로지르는 provider 호출 exactly-once는 보장하지 않는다. 그 경우 비용 호출은 한 번 더 생길 수 있지만 메시지 저장은 exactly-once여야 한다.

### 대화·저장·권한 경계

- Apple 받아쓰기 결과는 `gpt-transcribe` 보정본이 아니므로 음성 source로 취급한다. user/assistant 대화는 `shared-main`에 남기되 topic 자동 저장·`auto_save_decisions`·`note_chunks` 쓰기는 하지 않는다
- 원본 오디오는 Apple과 iOS가 처리하고 갈피에는 텍스트만 온다. 갈피 DB·Vault·backup·temp file에 오디오를 저장하지 않는다
- 활성 일정, 시간, A2 기억, 노트·웹·논문 근거처럼 **읽기 결과**는 기존 경계를 재사용할 수 있다
- H6d 이후에는 마지막 사용자 발화가 명시적으로 새 일정·할 일·알림을 만들거나 등록해달라는 요청일 때만 `schedule_prepare`를 제공한다. 날짜·시각이 하나의 KST 값으로 확정되지 않으면 저장하지 않고 되묻는다
- 단축어의 명시적 생성 발화 자체를 최종 승인으로 본다. 기존 validator로 candidate를 canonicalize한 직후 같은 `shortcut-task:<requestId>`로 `assistantTasks.create`를 호출하며, 완료 receipt 재전송과 task 생성이 모두 같은 키로 멱등이다
- H4의 DOM 카드 확인 계약은 PWA에서 그대로 유지한다. 단축어가 DOM handler나 일반 `POST /api/tasks`를 호출하는 것이 아니라, exact scoped route 내부에서만 공용 store를 직접 사용한다
- 기존 일정 조회는 계속 허용하지만 수정·완료·취소·삭제와 메모·노트·설정·Codex 쓰기는 닫는다. shortcut bearer로 일반 task API를 호출하는 권한도 계속 없다

### 단축어 단계

**H6a-1 공용 턴 코어 — 2026-08-03 구현·Pi 배포 완료.** 기존 `/api/chat`의 세션 잠금·회수·도구·GPT·저장 구간을 `runSingleChatTurn`으로 한 번만 분리했다. 라우트의 입력 검증·progress·응답·오류 계약은 유지하고, 서버 소유 옵션으로 `voiceTurn`, 일정 후보 허용, topic 자동 저장 허용을 받는다. 기존 PWA가 넘기는 정책은 바꾸지 않았고 로컬 전체 회귀 347/347을 통과했다.

**H6a-2 서버 단일 턴 — 2026-08-03 구현·Pi 기술 인수 완료.** schema v11에 활성 Push 구독별 hash-only credential과 durable receipt를 추가했다. 인증된 기존 API에서 `POST /api/voice/shortcut/credentials`로 raw token을 한 번만 발급하고 `DELETE /api/voice/shortcut/credentials/:id`로 폐기한다. exact `POST /api/voice/shortcut/turn`은 기존 전체 `API_TOKEN`과 분리된 bearer만 받고 8KiB JSON·2,000자·UUID·credential/IP별 분당 10회·credential별 동시 1개를 집행한다. H6a에서는 `text`·`requestId` 외 필드를 거절하고 `canContinue:false`로 고정한다.

receipt는 provider 호출 전 `pending`으로 만들고 30초 뒤 최대 3회까지만 crash retry한다. 완료 시 기존 `shared-main` user/assistant 삽입과 receipt의 message ID·`completed` 전환을 같은 SQLite transaction에서 확정한다. 완료 재전송과 동시 중복은 저장 답변을 재생하며 provider와 메시지를 반복하지 않는다. 단축어 턴은 GPT·`shared-main`·`voiceTurn:true`·일정 후보 금지·topic 자동 저장 금지·읽기 전용 지시를 서버가 고정한다. `VOICE_SHORTCUT_ENABLED` 코드 기본값은 `false`이고 운영 Pi에서만 `true`다.

로컬 가짜 provider 통합에서 scoped token만 exact route `200`, 전체 API 우회 `401`, 같은 request 동시 2개 provider 1회, 완료 replay 추가 provider 0회·추가 메시지 0개, request 충돌 `409`, 11번째 분당 요청 `429`, 일정형 발화 task·topic write 0을 확인했다. 전체 순차 회귀는 352/352다.

Pi에서는 DB·Vault 백업 `20260803-2152`, 코드 복구본 `code-h6a-shortcut-pre-20260803-215203.tar.gz`와 권한 600의 별도 `.env` 복구본을 만든 뒤 schema 10→11을 적용했다. 변경 10개 파일의 SHA-256이 로컬과 일치했고 H6a 집중 4/4·전체 순차 348/348, 새 PID `184734`, HTTP 200, 인증 config `shortcutVoice.enabled:true`, warning 이상 journal 0건, SQLite integrity `ok`·외래키 0을 확인했다. 배포 전후 messages/notes/note_chunks/auto-save/task/event/reminder는 `579/36/113/198/12/24/4`로 불변이다.

등록된 iOS Push 구독 중 당일 갱신된 활성 구독 하나에 credential 1개를 발급했다. raw token은 응답에서 한 번만 전달하고 문서·Git·DB 원문에 남기지 않았다. 무토큰과 기존 전체 `API_TOKEN`은 exact 음성 route에서 `401`, scoped token은 인증 뒤 금지 필드 검증 `400`까지 도달했고 일반 `/api/memory`에서는 `401`이었다. 실제 provider 호출은 H6b 실기기용으로 남겨 receipt 0행과 기존 application 행 수를 유지했다.

**H6b 잠금화면 실기기 spike — 2026-08-03 첫 실사용 성공.** iPhone 단축어는 아래 순서만 갖는다.

1. `텍스트 말하기`: `응, 말해.`
2. `텍스트 받아쓰기`: `뭐가 궁금해?`
3. 현재 날짜를 `yyyyMMdd-HHmm-4ssS-8SSS-yyMMddHHmmss`로 포맷해 UUID형 request ID 생성
4. `URL 콘텐츠 가져오기`: JSON POST와 scoped bearer
5. `사전 값 가져오기`: `answer`
6. `텍스트 말하기`: answer

최초 마이크·네트워크·음성 단축어 권한 확인은 setup으로 분리한다. 일반 Siri 실행과 `시온아` 음성 단축어를 각각 시험하고, 잠금 상태에서 PWA가 열리거나 잠금 해제를 요구하는지 실기기로 판정한다.

첫 실사용에서는 URL 오타를 고친 뒤 단일 턴과 단축어 `3회 반복` 안의 후속 대화·로컬 종료어가 정상 동작했다고 사용자가 확인했다. Pi에는 총 9개 receipt가 모두 `completed`·시도 1회로 남았고, messages는 기준선 579→597로 정확히 18개 늘었다. notes/note_chunks/auto-save/task는 `36/113/198/12`로 불변이고 DB 무결성·외래키·warning 이상 journal도 정상이다. 이 9개에는 setup 중 열린 화면 호출이 포함되므로 잠금 상태 10회 중 9회 기준을 충족했다고 세지는 않는다.

**2026-08-04 디스플레이 상태 분리 결과.** 여기서 `잠금 화면 표시 상태`는 기기가 잠겨 있지만 디스플레이가 켜져 잠금 화면이 보이는 상태이고, `디스플레이 소등 상태`는 기기가 잠긴 채 화면이 꺼져 잠자기에 들어간 상태다. 전자는 기존 `시온아` 단축어가 정상 실행됐다. 후자는 서버 receipt가 생기기 전에 실패했으며, 네트워크·POST·받아쓰기를 모두 제거하고 말 한마디만 재생하는 최소 음성 단축어도 시작되지 않아 **호출 단계 실패**로 확정했다. 따라서 기존 9개 receipt는 화면 활성 경로의 서버·대화 동작 근거일 뿐 디스플레이 소등 호출 성공 근거가 아니다.

Apple 문서는 음성 단축어가 기기에서 문구를 듣고 동작을 실행한다고 설명하지만 디스플레이 소등 상태의 wake 동작을 보장하지 않는다. Siri를 별도 wake 경로로 쓰는 대안은 있으나 사용자가 원하는 `시온아` 단독 호출과 다르므로 채택하지 않는다. 화면 소등 10회 성공 기준, iPhone 동일 request ID 실기기 재시도, 추가 H6 연결 UX는 더 진행하지 않는다. 현재 iPhone credential과 route는 화면 활성 상태의 기존 사용을 위해 유지한다.

기기 확대도 미룬다. iPad 음성 등록은 갈피 강의 노트 구현을 시작할 때 강의 흐름과 함께 설계하고, 노트북 음성 등록은 V6 화면에 떠있는 시온을 만들 때 그 창구와 함께 설계한다. 그 전에는 두 기기에 H6 credential이나 음성 단축어를 미리 만들지 않는다.

**H6c bounded 후속 대화.** 현재 단축어는 기존 단일 턴 route를 고정 3회 반복하고, `끝`·`됐어`·`그만`은 API 호출 전에 로컬에서 `단축어 중단`한다. 모든 정상 턴이 `shared-main` 최근 문맥을 읽으므로 별도 `conversationId` 없이도 실제 후속 대화가 이어졌다. 따라서 서버 conversation 상태는 현 단계에 추가하지 않는다. 다른 대화와의 문맥 혼선이나 서버 강제 상한 필요성이 실측될 때만 다시 연다. 무한 반복은 만들지 않고, 3턴이 안정된 뒤에도 분당 10회 제한 안의 명시적 고정 상한만 늘린다.

**H6d 단축어 직접 일정 생성 — 2026-08-04 Pi 배포·실기기 인수 완료.** H6a의 읽기 전용 차단은 구현 제약이 아니라 초기 권한 선택이었다. 화면 없는 경로에서 후보 카드만 만들면 candidate가 유실되므로, 명시적인 새 일정·할 일·알림 생성 발화 자체를 최종 승인으로 보는 좁은 예외를 열었다. 단축어 라우트는 기존 `schedule_prepare` schema와 `assistantTasks.prepare` validator를 그대로 거친 뒤 `assistantTasks.create`를 즉시 호출한다. request key는 `shortcut-task:<voice shortcut requestId>`로 결정해 같은 receipt 재전송이 provider·message뿐 아니라 task도 중복 생성하지 않는다. 모델은 마지막 `<user_question>`만으로 도구를 선택해야 하며 과거 대화, 활성 일정, 기억, 노트, 웹 결과만으로는 쓰기를 시작하지 않는다. PWA 채팅은 계속 미저장 후보와 카드 확인을 사용한다.

새 단위·서버 통합을 포함한 로컬 전체 회귀는 386/386이다. 통합 fixture에서 명시적 생성 1건이 task 1행으로 저장되고, 완료 receipt replay는 provider·message·task를 모두 늘리지 않으며, 같은 request ID의 다른 본문은 `409`, scoped token의 일반 `/api/chat` 우회는 `401`, topic·note chunk 쓰기는 0임을 확인했다.

### 공식 근거와 실기기 불확실성

- Apple은 Siri 단축어에 대해 “단축어를 실행한 후 Siri가 결과를 알려줍니다”라고 설명하고, 잠긴 상태에서 **앱을 여는** 단축어는 잠금 해제를 요구한다고 구분한다. [Siri로 단축어 실행](https://support.apple.com/ko-kr/guide/shortcuts/apd07c25bb38/ios)
- `시온아` 단독 문구는 iOS 음성 단축어에 학습시킨다. Apple은 설정 뒤 “생성한 단축어에 대한 문구를 말하기만 하면 됩니다”라고 설명하며 음성 처리는 기기에서 수행된다고 밝힌다. [iPhone 음성 단축어](https://support.apple.com/ko-kr/guide/iphone/iph7f242ea2c/ios)
- `URL 콘텐츠 가져오기`는 POST와 JSON 요청 본문·변수를 지원한다. [단축어에서 API 요청하기](https://support.apple.com/ko-kr/guide/shortcuts/apd58d46713f/ios)
- 다만 Apple 문서는 `텍스트 받아쓰기 → 네트워크 POST → 텍스트 말하기` 조합 전체가 모든 잠금 상태와 권한 상태에서 무중단 실행된다고 보장하지 않는다. 최초 권한 뒤 동작, Tailscale 연결 유지, 음성 단축어의 배터리·마이크 표시, 시온 답변이 `시온아`를 말해 자기 자신을 다시 깨우는지까지 실기기에서 확인한다

### H6 통과 기준과 롤백

서버:

- 활성 등록에 연결된 scoped token만 `200`; 누락·오류·폐기 token과 inactive Push 구독은 거절
- scoped token으로 `/api/chat`, task, note, Codex, 설정 API를 호출한 성공 0회
- client가 model·source·DB session·tool을 바꾸는 입력은 무시하지 않고 schema에서 거절
- 완료 receipt 재전송은 추가 provider 호출 0회·추가 메시지 0개, 동시 중복은 provider 1회, 같은 ID·다른 본문은 `409`. crash 뒤 bounded retry에서도 메시지 중복은 0개
- 정상 한 턴은 receipt 1개와 `shared-main` 메시지 2개를 정확히 남긴다. credential 사용 시각과 기존 hash-only A2 관측 외에 note·note_chunks·auto_save_decisions·task·event·reminder는 불변
- 일정 생성 발화에서도 task·후보·확인 없는 write 0회
- credential별 동시 1개·분당 10회, conversation 3턴·5분 상한과 다른 credential의 탈취 session 거절
- 기존 텍스트 채팅과 PWA 반이중 5턴, C2 progress/TTS, H4 일정 카드가 회귀하지 않음

iPhone 현재 인수:

- 잠금 화면 표시 상태에서 단일 턴과 고정 3회 반복·로컬 종료가 PWA 실행과 잠금 해제 없이 동작했다
- 디스플레이 소등 상태에서는 최소 음성 단축어도 호출되지 않았고 서버 요청 0건이었다. 화면 소등 10회 성공 기준은 미달이 아니라 현재 선택한 iOS 음성 단축어 경로의 범위 밖으로 닫는다
- 같은 `requestId` 재시도, 3턴 5세트, 낭독 p50/p95와 추가 기기 credential 발급은 H6 확대를 중단했으므로 실기기 제품 인수에서 제외한다. 서버의 동시 중복·완료 재전송 멱등성 회귀 테스트는 유지한다
- iPad는 강의 노트 단계, 노트북은 V6 화면 봇 단계에서 기기별 음성 입구가 실제로 필요할 때 등록한다

가장 작은 롤백은 Pi의 `VOICE_SHORTCUT_ENABLED=false`로 exact route를 닫는 것이다. additive credential·receipt 행은 비활성 상태로 남겨 감사·재개에 사용하고, 기존 PWA 반이중·Web Push·전체 API token 경로는 계속 동작해야 한다.

## 9. 열린 결정

구현 전에 정한다.

1. **Realtime 코드 제거** — 운영 flag는 껐고 기록·롤백용 코드는 남겼다. 제거는 필요성이 생길 때만 별도 컨펌으로 한다
2. **H3 문턱** — 현재 작은 표본에서 정확 전사의 최저 logprob은 -0.024~-0.425, 오류 전사는 -0.652와 -1.356이지만 확정 문턱으로 쓰기엔 부족하다
3. **침묵·earcon** — 침묵 1200→1000ms와 생각 중 earcon을 각각 별도 실기기 변경으로 열지
4. **빈 전사 25%** — Realtime 시절 원인은 미규명이다. 클래식에서는 답변 생성 전 빈 전사를 알고 LISTENING으로 복귀하므로 답변까지 유실되지는 않는다
5. **H6 연결 UX** — iPhone 수동 설정으로 현재 사용 범위를 충족했고 디스플레이 소등 호출을 지원하지 못하므로 추가 UI를 만들지 않는다. iPad·노트북 등록은 각각 강의 노트와 V6에서 다시 판단한다
6. **H6 잠금 동작 — 종료.** 잠금 화면 표시 중에는 동작하고 디스플레이 소등 상태에서는 최소 음성 단축어부터 호출되지 않는다. 서버로 해결하지 않고 현재 제약으로 수용한다

## 10. 판단 기준

- 완전한 실시간 대화가 아니라 **말을 끝까지 듣고 정확히 이해한 뒤 답하는 것**이 목표다
- 지연 4초는 감수하되 **오답은 감수하지 않는다**
- 사용자에게 재발화를 요구하는 것은 답변 생성 **전에만** 허용한다. 답변 뒤의 정정 요구는 대화를 망친다
- 모델 판단에 맡기지 않고 코드로 집행할 수 있는 경계는 코드로 집행한다 (`spoken` 길이, 되묻기 상한, 폐기 규칙)
- 입·귀 transport가 PWA에서 iOS 단축어로 바뀌어도 회수·모델·저장이라는 뇌는 하나만 둔다
- 등록 상태는 인증 증명이 아니다. 활성 등록에 묶인 별도 scoped credential을 검증하고, 기기 라벨·요청 body를 신뢰하지 않는다
