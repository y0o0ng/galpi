# 포스트잇 손글씨 OCR 연구

강의 노트 포스트잇에서 `전송`한 손글씨를 시온(L3b)이 잘못 읽는 문제를 푼다. 2026-10-01 사용자 결정으로 클라우드 OCR·단축어·네이티브 앱 대신 **자체 OCR을 만든다**. 화면·저장 계약은 `Lecture-note-system_Design_v4.3.md` §6.6·§17.7이 정본이고, 이 문서는 OCR 연구의 목표·데이터·실측·단계만 다룬다.

## 1. 목표

- 완벽한 한글 손글씨 OCR이 아니라 **luna에 붙일 판독 힌트**다. 실측에서 Apple Vision 단독(CER 31.6%)을 힌트로 붙이자 luna가 34.5%에서 10.7%로 내려갔다(§3).
- **성공 판정:** 고정 시험지(1회차 140줄)에서 `자체 OCR + luna`가 `Vision + luna`(CER 10.7%)에 근접한다. 자체 OCR 단독 목표는 시험지 CER 30% 안팎이다.
- **멈춤 조건:** M2(바탕 학습)까지 해도 시험지 CER이 내려가지 않으면 멈추고 클라우드 OCR이나 네이티브 앱(iPad Vision)을 다시 검토한다.

## 2. 데이터

- **필체 등록**(schema v35 `lecture_handwriting_samples`). 획 벡터(칸 폭 = 1) + 정답 글이다.
- **1회차 140줄은 평가 전용이다.** 고정 문장(`?` 40·`ㄴ` 24·수식 30·헷갈리는 글자 20·메모 16·영문 10)이고 학습에 쓰지 않는다. 2회차부터는 틀에 낱말·기호를 끼운 새 문장이라 시험지와 겹치지 않는다 — 같은 문장으로 학습·평가하면 글씨 대신 문장을 외워 점수가 부푼다.
- 획 벡터라 굵기·기울기·크기·흔들림을 바꿔 한 줄을 여러 장으로 다시 그리는 증강이 공짜다. 1회차는 모두 한 줄이었고, 포스트잇의 여러 줄 덩어리는 획 높이로 줄을 나눈다.
- 측정 산출물(이미지·판독 결과)은 저장소 밖 스크래치에 두고 커밋하지 않는다. 표본은 Pi DB가 정본이다.

## 3. 실측 — 2026-10-01, 1회차 140줄

CER은 공백을 뺀 글자 편집 거리 / 정답 글자 수다. 한 줄 오류는 그 줄 길이에서 자른다(끝없이 반복 출력하는 모델 때문). 첫 글자 경로는 `?`·`ㄴ`·그 밖 세 갈래 일치 수다.

| 방식 | CER | 문장 일치 | 첫 글자 경로 |
|---|---|---|---|
| Apple Vision 단독(맥) | 31.6% | 13 | 89 |
| `gpt-6-luna` 단독(L3b 지금) | 34.5% | 21 | 135 |
| **Vision 판독 + luna** | **10.7%** | **72** | **139** |
| PaddleOCR-VL 0.9B(학습 없음, Colab T4 391초) | 72.1% | 9 | 111 |
| PaddleOCR-VL 1.5(학습 없음, 400초) | 78.0% | 6 | 102 |
| PaddleOCR `korean_PP-OCRv5_mobile_rec`(한 줄, 맥 CPU 23초) | 63.7% | 0 | 116 |
| EasyOCR 한국어(한 줄, 맥 CPU 12초) | 72.4% | 0 | 101 |

- 종류별로 Vision은 한글(`?` 질문 17%)에 강하고 수식(48%)·`ㄴ`에 약하며, luna는 수식(22%)·영문(3%)·첫 글자에 강하고 사용자 한글에 약하다. 합치면 둘 다 낫다(`?` 질문 4%, 수식 15%). 헷갈리는 글자 쌍은 어느 조합이든 40%대다 — `l`/`1`처럼 사람도 못 가르는 문항이 섞였다.
- 획을 굵게 다시 그리면 PaddleOCR 한 줄 인식기가 오히려 나빠졌다(77.9%).
- 버린 길: 사용자 손글씨 포스트잇 12장 첫 실측에서 sol급은 잘 읽었지만 비용·지연으로 사용자가 제외했다. iPad 손글씨 입력(Scribble)은 수식을 전혀 못 읽는다. 단축어로 기기 Vision을 부르는 길은 매번 앱이 넘어가 거슬린다(사용자 결정). 인텔 맥은 최신 PyTorch·Paddle을 못 깔아 VL 모델은 Colab에서 쟀다.

## 4. 단계

1. **M0 — 바탕 고르기.** 위 실측으로 닫았다. 학습 없이는 Vision에 못 미친다. 한 줄 인식기 둘(EasyOCR·PaddleOCR)이 가볍고 CPU에서 빠르다.
2. **M1 — 사용자 필체 파인튜닝.** EasyOCR 한국어 모델(PyTorch, 맥 CPU로 학습 가능)부터 2회차 이후 표본 + 획 증강으로 학습하고 1회차로 학습 곡선을 잰다. 느리거나 안 내려가면 PaddleOCR 한 줄 인식기를 Colab GPU에서 해본다. 처음 기준은 400~500줄이다.
3. **M2 — 부족할 때만 바탕 학습.** AI Hub 한글 손글씨 데이터로 한글을 먼저 가르치고 사용자 필체를 얹는다.
4. **M3 — 붙이기.** 인식기를 Pi나 전사 PC에서 돌려 L3b 판독 자리에 꽂는다. 서버가 모델 호출 전에 한 겹 정리한다(2026-10-01 사용자 제안·합의):
   - 첫 글자는 OCR 글이 아니라 **획 분류기**(첫 한두 획 → `?`·`ㄴ`·그 밖)로 판정한다. OCR은 첫 글자에 가장 약했다(Vision 89/140).
   - `?`면 새 chain(앞 대화 없음), `ㄴ`이면 그 포스트잇 chain에 이어 붙이고, 그 밖이면 메모로 두고 모델을 부르지 않는다. 확신이 낮으면 모델 호출 없이 경로 칩을 띄운다.
   - luna에는 접두어를 뺀 OCR 글 + 손글씨 이미지를 함께 보낸다 — OCR 글만 보내면 힌트 효과가 사라진다.
   - 그 뒤 실제 포스트잇으로 다시 잰다.
