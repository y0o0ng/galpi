# XION 픽셀 스킬 — 후속 구현 설계

현재 운영 계약의 정본이 아니다. 현재 규칙은 `reels/px/skills/`. 이 문서는 아직 구현되지 않은 것의 계획이다. 출처: 사용자 승인 초안(2026-10-14, 기준 `49facc0`).

## 1. Visual Review Preprocessor

> 전처리기는 B 스킬이 읽을 **증거 자료**를 만드는 결정론적 프로그램이다. 별도 LLM 에이전트가 아니다. 상세 추출 수량과 간격은 **토큰 비용 및 누락률을 측정하기 위한 초기 시험 설정**이며, 확정 최적값이 아니다.

### P-1. 위치와 목적

`build → Python 전처리 → visual → fix`

`lib/reels/production.js`가 `build` 완료 뒤, Sonnet `visual` 호출 전에 실행한다. 사람 피드백 이후의 `fix → visual` 경로에서도 현재 MP4로 재실행한다.

이 코드는 시각적 품질의 좋고 나쁨이나 MUST/NICE를 판정하지 않는다. MP4를 전체 스캔하여 시간별 요약과 중요한 변화 후보를 생성하고, Sonnet에 보내는 이미지 수를 제한한다.

### P-2. 입력과 출처

- 완성된 실제 MP4: **시각적 원본(source of truth)**
- `narration.ko.json`, `scenes.json`, `engine`/`templates`의 시간 계약: 장면·문장 경계
- 제작 보고서: 핵심 장면·변화의 예상 시간 **보조 힌트**
- 효과음 이벤트 기록: 역할·예정/실제 채택·누락·실제 시각

MP4의 SHA-256, 길이, 프레임레이트, 프레임 수를 기록한다. 보고서에 적힌 변화만 보고 영상에 변화가 있었다고 판단하지 않는다. 장면 시각은 기존 엔진의 계산과 일치해야 한다.

### P-3. 전체 스캔과 후보 탐지

실제 최종 MP4를 낮은 해상도로 디코딩해 출력 **24fps 전 프레임의 시간 흐름**을 차례로 분석한다. 프레임 차이의 크기, 변화율, 연속 정지 의심, 갑작스러운 변화, 반복 변화 패턴을 **후보**로만 기록한다.

추가적으로 장면 경계, 보고서가 지정한 핵심 과정, 복잡한 오브젝트의 변화, 카메라 이동, 효과음 사건 시각을 후보로 올린다.

**주의:** 픽셀 변화량은 의미 있는 움직임과 같지 않다. 카메라 이동이나 깜빡임도 높은 변화량을 낼 수 있고 느린 현상은 낮을 수 있다. 변화량 임계값으로 인간 품질 판단을 대체하지 않는다. 임계값·선정 점수는 시험으로 조정하되 새 튜닝 노브를 불필요하게 늘리지 않는다.

### P-4. 초기 시각 자료 예산 (시험용)

| 자료 | 초기값 | 용도 |
|---|---|---|
| **전체 요약** | 1초당 대표 프레임 **1장** | 모든 시간 구간·장면 커버리지 |
| **개요 시트** | **시트당 8프레임** | 시간순 이야기·무대·전환 파악 |
| **집중 구간** | 영상당 **최대 4구간**, 각 약 1초 | 인과관계·연속성·정지·카메라 등의 시간 흐름 |
| **일반 상세 샘플** | 해당 구간 **12fps** 연속 프레임 | 도트 애니메이션의 중간 상태 |
| **카메라 상세 샘플** | 필요하면 **24fps** 연속 프레임 | 카메라 버벅임·출력 프레임 |
| **고해상도 핵심 프레임** | 영상당 **최대 6장** | 정체성·비례·관절·구조·픽셀 클러스터 |

예를 들어 **80초 영상**은 전체 요약 프레임 약 80개 → 8칸 시트 약 10장, 집중 시트 최대 약 4장, 고해상도 핵심 프레임 최대 6장으로, **LLM이 처음 보는 이미지 약 20장**을 목표로 한다.

이것은 **독립 이미지 파일/시트 개수**의 근사치이지 이미지 토큰 20개, 비용 보장 또는 전 구간 12fps 판독을 의미하지 않는다. 일부 24fps 상세 구간은 더 많은 시트가 필요할 수 있으므로 실제 산출량과 토큰을 기록한다. 고해상도 원본이 필요한 미세 구조를 지나치게 축소한 시트에서 단정하지 않는다.

### P-5. 구간 선택 규칙

우선순위는 다음과 같다.

1. 확정 대본의 **핵심 인과관계**와 주요 상태 변화
2. 인체·동물·복잡한 기계의 비례·관절·연결부가 움직이는 구간
3. 1초 초과 완전 정지 의심 구간
4. 카메라 이동·확대·장면 연결
5. 중요한 사건과 효과음 동기화 시점
6. 기타 급격하거나 반복적인 변화 후보

중복 구간은 하나로 합친다. 특정 변화량이 큰 장면에만 집중하지 않고 다른 장면의 기본 대표 프레임을 남긴다. 상세 후보가 한도를 넘으면 제외된 후보의 시각과 이유를 `manifest.json`에 기록한다.

필수 자료와 선택 자료를 명확히 구분한다. 정밀 검토에서 누락된 구간은 Sonnet이 본 것처럼 보고하지 않는다.

### P-6. 출력 구조

기존 프레임 폴더 아래 별도 `review/`를 사용한다.

```text
reels/media/frames/epNN_px/
  review/
    manifest.json
    overview_001.png
    overview_002.png
    ...
    detail_001.png
    detail_002.png
    ...
    key_001.png
    key_002.png
    ...
```

`manifest.json`에는 다음을 기록한다.

- MP4 절대/상대 경로, SHA-256, 길이, fps, 총 프레임 수
- 장면·문장별 실제 시간 범위
- 각 시트의 파일명, 읽기 순서, 각 패널의 실제 영상 시각
- 상세 구간의 시작·종료·추출 fps·선정 이유
- 고해상도 프레임의 시각과 대상
- 자동 분석에서 발견한 후보와, 예산 때문에 제외한 후보
- 실제 선정 이미지의 개수와 생성 성공·완전성 상태
- 효과음 이벤트 메타데이터의 존재 여부와 검증 가능 범위

전처리 시트는 실제 MP4에서 나온 프레임만 사용하고, 생성 또는 축소 때문에 색·시간 의미가 달라졌다면 원본 검증 자료와 구분한다.

### P-7. 실패 처리 (fail-close)

다음 경우에는 Sonnet `visual` 호출 전에 **검토 준비 실패**로 멈춘다.

- MP4를 열 수 없거나 실제 영상 길이·FPS·프레임 수를 알 수 없음
- 엔진의 장면 시간 계약과 실제 영상 길이가 의미 있게 불일치
- 필수 요약 프레임이나 필수 파일 일부가 생성되지 않음
- manifest의 원본 SHA-256이 현재 MP4와 다름
- 이미지 파일이나 manifest가 손상돼 참조가 불가능함

후보가 상세 검토 한도를 초과한다는 사실 자체는 실패 조건이 아니다. 미선정 후보의 시각·이유를 기록한다. 선택적 음향 메타데이터가 없는 경우 해당 음향 검토는 **확인 불가**로 명시하며 검증 완료를 주장하지 않는다. 다만 확정된 별도의 필수 이벤트 계약이 충족되지 않은 경우에는 해당 상위 계약에 따라 실패 처리한다.

### P-8. 기존 파이프라인 통합

현재 `main`의 `lib/reels/production.js`에서 `visual` 단계는 Sonnet이고, `Read,Glob,Grep,Write` 위주로 권한이 한정돼 있다. MP4/FFmpeg 추출은 리뷰 에이전트에 맡기지 않고 **오케스트레이터의 결정론적 전처리**로 수행한다.

- `visual` 프롬프트의 기존 **`framesDir` PNG 전부 읽기** 명령을 폐기한다. 새 `manifest.json`에 지정된 시트와 핵심 프레임을 순서대로 읽도록 한다.
- 기존 제작 에이전트의 프레임 출력은 수정 단계 확인 및 호환성에 필요하면 유지할 수 있지만 리뷰에서 중복 입력하지 않는다.
- `CHECKS.visual`은 보고서 형식뿐 아니라 **전처리 결과의 존재·해시·필수 커버리지**를 확인한다.
- 기존 `build → visual → fix` 단계 이름, Sonnet 리뷰, MUST 기반 수정 계약은 유지한다.
- `reviseEpisode`의 `fix → visual` 앞에서도 현재 MP4를 대상으로 전처리를 실행한다. 해시가 바뀌면 기존 시트는 무효다.
- `SFX`의 역할·채택/누락 이벤트를 기록하려면 `templates.py`와 `audio.py`의 인터페이스 변경이 별도로 필요하다. 이전 편 기본 동작과 승인 사운드를 유지한다.

### P-9. 테스트 계약

- 전체 영상 구간이 시간순 요약에 빠짐없이 포함되는가?
- 정지 영상·느린 변화·빠른 사건을 과도하게 한 방식으로 취급하지 않는가?
- 장면·문장 경계와 실제 프레임 타임스탬프가 일치하는가?
- 같은 구간이 중복 선정되지 않는가?
- 상세·고해상도 자료 예산 상한 및 제외 후보 기록이 지켜지는가?
- 픽셀 구조 평가용 고해상도 프레임과 실제 시간의 대응이 맞는가?
- 불완전한 추출이 성공으로 처리되지 않는가?
- 재렌더 후 이전 MP4 해시의 검토 자료가 재사용되지 않는가?
- 전처리 실패 시 Sonnet이 호출되지 않는가?
- 수정 후 독립 검토에 새로운 자료가 전달되는가?
- 전처리 코드가 MUST/NICE 또는 미적 품질을 자동 판단하지 않는가?
- 시간 스트립만으로 확인할 수 없는 고속 움직임·청감은 확인 불가로 남는가?

### P-10. 운영 시험과 조정

첫 운영 시험에서 다음을 비교한다: 실제 이미지 입력 개수와 토큰·실행 시간, 발견한 주요 시각 결함, 상세 후보 누락, 사용자 검토에서 뒤늦게 발견한 문제.

**1초당 1개 개요 프레임, 상세 최대 4구간, 고해상도 최대 6장**은 고정된 과학적 최적값이 아니다. 시각 결함 누락이 확인되면 그 사례를 근거로 예산을 조정한다. 실측 없이는 토큰 절감률이나 검토 품질 개선을 단정하지 않는다.

5. 현재 효과음 이벤트가 `(시각, 종류)`만 저장되고 전역 2초 간격으로 필터링되므로, 역할별 효과음 실제 채택 이벤트에 대한 기계적 검증은 별도 연결 작업이 필요하다.
6. 별도 LLM 리뷰 단계, 기존 사람 승인 게이트 추가, Manim 트랙 변경, 승인된 과거 영상 재렌더는 이번 범위가 아니다.
