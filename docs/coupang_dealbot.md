# 딜 큐레이션 에이전트 설계문서

갈피 산하 자율 에이전트 — 쿠팡 파트너스 기반 니치 딜 큐레이션 봇

작성일: 2026-07-18 · 상태: Phase 0 착수 전

---

## 1. 개요

쿠팡 파트너스 어필리에이트 수익으로 갈피의 운영비를 자체 충당하는 자율 에이전트를 구축한다. 특정 니치의 딜을 공식 API로 수집하고, 자체 축적한 가격 히스토리로 "진짜 특가"만 판정해 스레드에 선별 게시한다.

이 프로젝트의 성격은 사업이 아니라 실험이다. 목표는 세 가지다: 자원 제약(예산 대사) 하에서 도는 자율 에이전트의 실전 검증, 갈피 V5(트레이딩 파이프라인)의 구조적 리허설, 그리고 부수적으로 발생하면 좋은 운영비 충당. 현금 기준 월 고정비가 1만 원 미만으로 예상되어 하방이 막혀 있고, 수익이 0이어도 에이전트 구축 경험과 가격 데이터셋이 산출물로 남는 구조다.

## 2. 배경 — 정책 검증 결과

쿠팡 파트너스 운영정책 원문(2026.6.8 적용판)을 직접 확보해 검증했다. 핵심 결론은 다음과 같다.

**플랫폼별 금지 조항은 없다.** 커뮤니티에 퍼진 "카카오톡 금지"는 정책 원문에 존재하지 않는 통념이다. 다만 무효클릭 유도 행위 목록에 "메일, 메신저, SMS 등을 이용하여 클릭을 요청하는 메시지를 발송하는 행위"가 포함되어 있어, 오픈채팅 기반 링크 배포는 이 조항으로 A급 제재(1회 위반 시 14일 수익 몰수, 2회 시 30일 몰수 및 계정 해지) 대상이 될 수 있다. 이것이 오픈채팅을 배제하고 스레드로 선회한 근거다.

**광고를 노출할 미디어는 등록·심사 대상이다.** 심사받는 것은 플랫폼이 아니라 등록한 계정이며, 기준은 미디어 운영기간과 공개 콘텐츠 수다. 따라서 계정을 미리 만들어 숙성시키는 순서가 필요하다. 일정 수익 발생 후 채널을 재검토하는 최종승인 절차도 별도로 존재한다.

**자동 포스팅 자체는 금지가 아니다.** 영구정지 사유로 명시된 것은 "자동화된 프로그램을 통해 인위적으로 클릭을 발생시키는 경우", 즉 자동 클릭이다. 다만 "스팸글, 홍보글 등의 도배성 내용"과 "미디어 고유의 콘텐츠보다 광고성 콘텐츠의 비중이 압도적으로 큰 경우"가 각각 부적합 콘텐츠·광고매체 기능 저하 조항에 있으므로, 링크만 기계적으로 올리는 운영은 매체와 무관하게 위반 소지가 있다. 게시 설계는 이 두 조항의 회피를 전제로 한다.

수수료는 별도 지정이 없으면 결제금액의 3%이며, 월 정산액 1만 원 이하는 익월 이월된다. 모든 게시물에는 공정위 규정에 따른 대가성 고지("파트너스 활동으로 수수료를 받을 수 있음")를 포함해야 한다.

## 3. 아키텍처

에이전트는 라즈베리파이의 cron으로 1시간 주기 실행되며, 갈피의 기존 인프라(Node.js, SQLite, Obsidian vault)를 공유한다. 실행 흐름은 다섯 단계다.

수집 단계에서는 쿠팡 파트너스 Open API(골드박스·카테고리 검색)로 대상 니치의 딜 목록을 받는다. 오픈채팅 크롤링은 채택하지 않는다 — 공식 API가 동일한 소스를 더 깨끗하게 제공하며, 기술적으로도 정책적으로도 우위다. 저장 단계에서는 상품ID별 가격을 SQLite에 시계열로 적재한다. 외부 가격비교 사이트에 의존하지 않고 자체 히스토리를 축적하며, 약 2주 후부터 "최근 N일 최저가" 판정이 자체 데이터로 가능해진다.

판정 단계는 LLM이 아닌 코드 로직이다(4장). 생성 단계에서는 판정을 통과한 딜에 한해 LLM이 한 줄 코멘트를 생성하며, vault에서 관련 지식 문서를 검색해 컨텍스트로 주입한다(5장). 게시 단계에서는 스레드 API로 게시한다.

핵심 설계 원칙은 **실행 주기와 게시 주기의 분리**다. 에이전트는 매시간 돌지만 게시는 판정 통과 시에만 발생한다. 게시 빈도가 자연스럽게 불규칙해져 도배 판정과 플랫폼 스팸 탐지를 동시에 회피한다. 여기에 하루 1회 링크 없는 통계 게시물(예: 당일 수집 딜 중 진짜 특가 비율)을 자동 생성해 광고 비중 조항에 대비하고 계정에 캐릭터를 부여한다.

게시 매체는 스레드가 1순위다. API가 무료여서 "비용이 토큰비뿐"이라는 손익 전제가 유지된다. X 확장은 스레드에서의 수익이 X API 비용을 상회하는 것이 확인된 이후에만 진행한다(X API의 무료 티어 한도와 유료 가격은 착수 전 확인 필요 — 9장).

## 4. 판정 로직

판정은 결정적 코드 로직으로 구현하며, LLM은 개입하지 않는다. 기본 판정은 해당 상품의 자체 가격 히스토리 대비 역대가(또는 최근 N일 최저가) 여부다. 니치별로 다음 파라미터가 추가된다: 보충제·향수처럼 용량이 있는 카테고리는 단위가격(g당·ml당) 기준을 병행하고, 향수는 정품 신뢰 문제에 대응해 판매자 필터(로켓배송·공식판매자만 통과)를 추가한다. 이 필터는 "쿠팡 향수 중 사도 되는 것만 걸러주는 계정"이라는 포지셔닝의 근거가 된다.

판정 통과선은 시스템 상수로 관리하며, 예산 로직이 이를 수정할 수 없다(6장).

## 5. 콘텐츠와 페르소나

계정의 캐릭터는 시스템 프롬프트에 명시적으로 정의하고 vault 문서로 버전 관리한다. 니치 전문성은 파인튜닝이 아니라 vault 기반 RAG로 구현한다 — 기기 비교 노트, 사용 소감, 카테고리 지식을 vault에 축적하고, 코멘트 생성 시 하이브리드 검색으로 관련 문서를 컨텍스트에 주입한다. 신제품 대응은 노트 추가만으로 완결되며 재학습이 불필요하다. 파인튜닝은 운영 데이터(좋은 코멘트 수백 건)가 쌓인 뒤 토큰비 절감 목적의 소형 모델 튜닝으로만 검토한다.

봇에게는 전용 컨텍스트 노트를 부여한다. 매 실행 시작 시 읽고 종료 시 갱신하는 자기 관리 작업 메모로, 섹션 스키마(최근 게시 요약 / 반응이 좋았던·나빴던 딜 유형 / 예산 상태 / 다음 실행 메모)를 고정하고 크기 상한 초과 시 스스로 압축하게 한다. 압축 로직은 갈피 의회 모드의 단계적 프롬프트 압축을 재활용한다.

세 가지 경계를 강제한다. 첫째, 지식 노트(사람 작성)는 봇에게 읽기 전용이다 — 봇의 환각이 ground truth를 오염시키는 경로를 차단한다. 둘째, 컨텍스트 노트는 참고 정보로만 취급하며 판정 기준과 페르소나 규칙은 시스템 프롬프트에서만 온다 — self-injection 방지이며, OpenLife에서 채택한 injection defense 구조를 적용한다. 셋째, 스펙·사실 주장은 DB 또는 vault 문서에 근거가 있는 것만 허용한다 — 니치 계정의 자산은 신뢰이며, 환각으로 인한 오정보 한 건이 계정 가치를 훼손한다.

## 6. 예산 대사

에이전트가 자기 손익을 인지하고 지출을 조절하는 구조로, OpenLife의 예산 대사 개념의 실전 적용이다.

SQLite에 장부 테이블을 두고 지출(실행별 토큰비 — API 응답 usage 기반 계산)과 수입(파트너스 실적)을 기록한다. 파트너스 Open API의 실적 리포트 엔드포인트 스펙은 확인 필요 사항이며, 미지원 시 월 정산 내역 수동 입력으로 시작해도 장부 구조는 동일하다.

성과 지표는 충당 성공/실패의 이분법이 아니라 **충당률(수익/지출 %)의 추세**다. 초기 수개월은 낮은 충당률이 정상이며, 추세가 판단 기준이다.

예산 로직이 조절할 수 있는 변수는 화이트리스트로 제한한다: 코멘트 생성 모델 등급과 실행 주기, 두 가지뿐이다. 판정 통과선·게시 품질 기준은 예산과 무관한 상수다. 자기 수익이 목표인 에이전트는 구조적으로 스팸 방향의 인센티브를 가지므로, 예산 압박이 게시 남발로 전이되는 경로를 설계 단계에서 차단한다.

## 7. 리스크

정책 해석 리스크: 선별 게시·비광고 콘텐츠 혼합 설계로 도배·광고 비중 조항과의 정면 충돌은 없으나, 해석 여지가 0은 아니다. 최악 시나리오는 계정 해지와 소액 몰수로, 하방이 제한적이다. 플랫폼 리스크: 스레드·X 모두 외부 링크 게시물의 도달을 억제하며 반복적 자동 링크 게시는 스팸 탐지 대상이다 — 실행/게시 주기 분리와 콘텐츠 혼합이 대응책이다. 비용 리스크: 손익 전제가 깨지는 유일한 항목은 X API이며, 확장 조건(3장)으로 통제한다. 신뢰 리스크: 환각에 의한 오정보는 근거 강제 원칙(5장)으로 대응한다. 수요 리스크: 니치의 딜 빈도가 낮아 수익이 목표선에 못 미칠 수 있다 — Phase 0 측정으로 추측이 아닌 데이터로 판단한다(8장).

경쟁 전략에 대한 전제: 범용 핫딜의 속도 게임은 1시간 주기 설계로는 참전 자체가 불가하며 참전하지 않는다. 니치 딜은 숙고 구매라 반감기가 길어 1시간 주기로 충분하며, 우위는 속도가 아니라 판정 정확도와 큐레이션 신뢰에서 확보한다. 확장이 필요해지면 속도 게임 진입이 아니라 니치 추가로 한다 — 아키텍처가 니치 비종속이므로 계정·페르소나·vault 폴더 교체로 두 번째 니치가 구동된다.

## 8. 실행 계획

**Phase 0 — 측정 (2주).** 파트너스 가입, API 키 수령, 골드박스·카테고리 검색 엔드포인트 응답 구조 확인. 니치 후보 3개(PC부품·게이밍 기어 / 음향기기 / 향수)를 병렬 수집하는 스크립트를 작성해 파이 cron에 등록한다. 게시는 하지 않는다. 병행 작업으로 스레드 계정을 미리 개설하고 수동 게시물을 쌓아 미디어 등록 심사에 대비한다(계정 숙성과 개발 기간을 겹치는 순서).

**Phase 1 — 니치 확정.** 2주 데이터에서 카테고리별 통과 딜 빈도와 평균 단가를 산출하고, 기존 경쟁 채널 수를 감안해 니치를 확정한다. 판단이 감이 아닌 산수가 되는 지점이다.

**Phase 2 — 게시 개시.** 미디어 등록 심사 통과 후 판정-생성-게시 파이프라인 가동. 페르소나 정의, vault 지식 문서 초기 구축, 컨텍스트 노트 스키마 적용.

**Phase 3 — 예산 대사 가동.** 장부 기록 개시, 충당률 추적, 예산 로직의 변수 조절 활성화.

**Phase 4 — 조건부 확장.** 스레드 수익이 X API 비용을 상회하면 X 추가. 니치 추가는 첫 니치의 충당률 추세 확인 후 검토.

**종료 조건.** 착수 시점에 명시한다(예: 게시 개시 후 3개월 시점의 팔로워·클릭 지표가 기준선 미달이면 종료). 수익도 경험도 아닌 관성 유지 상태를 방지하기 위한 장치다.

## 9. 미결정·확인 필요 사항

파트너스 Open API의 실적 리포트 엔드포인트 존재 여부와 스펙(가입 후 문서 확인). X API 무료 티어 게시 한도와 유료 티어 가격(공식 문서 확인 — 월 720회 게시가 무료 한도 내인지). 스레드 API의 게시 한도. 미디어 등록 심사에 필요한 계정 숙성 수준(운영기간·게시물 수의 실질 기준). Phase 1의 니치 확정 기준선(통과 딜 빈도 × 단가의 최소 요구치) 수치화.
