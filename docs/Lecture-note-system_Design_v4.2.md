## 2026-09-16 설계 중간 정리

사용자와의 설계 대화에서 확정한 UX를 기존 v4.2에 반영한다. 구현 일정·Phase 순서·API·DB 스키마는 이번에 확정하거나 변경하지 않는다. **설계가 모두 잡힌 뒤 로드맵·AGENTS.md·CLAUDE.md 등 관련 문서를 일괄 갱신한다. 지금은 이 설계서만 수정한다.** 아래 과거 버전 변경 요약은 이력이고, 충돌 시 이번 합의와 해당 본문이 우선한다.

- **합의:** 과거 화면 재현 대신 최종 필기의 재생 위치별 농도 표시 (§12.2). 지운 획은 되살리지 않으며 스트로크별 시각은 유지한다.
- **합의:** 질문 포스트잇과 기존 필기 선택 → `시온에게 묻기`를 함께 제공한다. `시온:` 답변과 `ㄴ` 후속 대화를 보존한다 (§6.6).
- **합의:** 일반 필기의 `?`·동그라미를 질문 호출로 해석하지 않는다. 강의 중 사용자가 명시적으로 요청하는 화면 Q&A는 허용하고 자동 질문·자동 답변은 만들지 않는다.
- **설계 방향:** AINOTE의 문맥 내 조작·통합 노트·작은 도구막대를 참고한다 (§6.7). 기기는 비용 때문에 구매하지 않고 보유 iPad를 기준으로 계속 설계한다.
- **추가 합의:** 일반 질문은 질문만, 선택 질문은 선택 영역과 해당 PDF 페이지, 후속 질문은 같은 포스트잇의 Q&A와 기존 첨부를 전달한다. 손글씨는 매번 인식 결과를 확인시키지 않고 원본을 유지하며 필요할 때만 정정한다 (§6.6).
- **추가 합의:** 포스트잇 접기·펼치기는 수동이다. 새 답변은 갈피 강조색 점, 실패는 별도 느낌표로 표시한다. 질문·초안을 보존하고, 재연결 때 기존 결과 확인은 자동·못 보낸 질문 재전송은 수동이다 (§6.6).
- **추가 합의:** 펜을 대고 유지 → 원형 메뉴 → 방향 이동 → 떼어서 선택. 중앙에서 떼거나 입력 중단 시 취소하며, 필기를 시작한 뒤의 멈춤은 메뉴 호출이 아니다 (§6.8).
- **추가 합의:** 원형 메뉴 항목은 펜·지우개·선택·질문 포스트잇 네 개다. 방향·임계값은 미정이다 (§6.8). 선택 질문은 선택 영역과 해당 PDF 페이지를 이미지로 전달하며 필수 OCR 파싱을 거치지 않는다. 전송 전 초안은 수정 가능하지만, 전송한 질문의 정정은 `ㄴ` 후속 대화로 남긴다 (§6.6).
- **조건부 방향:** 강의 중 갈피에 머무는 사용을 기준으로 웹앱 직접 녹음을 먼저 검증한다. 참고 검색 사이드바를 두되 범용 내장 브라우저는 만들지 않는다. 최대 3시간 필기·PDF·검색 병행, 앱 전환·잠금·복귀, 저장·시간 연결을 통과해야 녹음 방식을 채택한다 (§6.9·7·14).
- **합의:** 노트 열기와 녹음 시작은 분리한다. 일시정지·재개는 같은 강의에 연결하고 비녹음 구간의 필기는 보존하되 가짜 오디오 위치를 주지 않는다. 종료 후에도 필기·질문은 가능하며, 중단 후 복원해도 마이크는 사용자 확인 없이 재개하지 않는다 (§6.1·6.5·8.3).
- **합의 / 하드웨어 미구매:** 50~70만 원 PC에 갈피 서버·Whisper를 두고 향후 로컬 메모리 에이전트도 고려한다. 답변·요약 모델은 외부 API다. 보통 60~90분, 최대 3시간 강의를 학교 인터넷으로 전송하고 귀가 후 복습 시점에 결과가 준비되는 것이 목표다. 앞서 말한 종료 후 1시간은 엄격한 마감이 아니며 실시간 전사는 요구하지 않는다 (§11.2).
- **합의:** 녹음 복습은 온라인 우선이다. iPad → 집 PC 직접 전송이 기본이고 iCloud는 선택적 보관 수단이다. PC 정상 저장 확인 전 단말 사본을 삭제하지 않으며, 확인 후 정리 시점·장기 보존 기간은 미정이다 (§5).
- **합의:** 복습 독바는 스트로크 목록 대신 가사형 전사다. 현재 구간 강조·자동 따라가기·구간 탭 재생을 제공하고 수동 스크롤 중에는 따라가기를 멈춘다. 캔버스 농도 표시는 그대로이며 둘 다 오디오 재생 시각을 따른다 (§12.2).
- **합의:** 요약은 노트 선택 화면의 짧은 2~3문장 소개문이다. 자동 주제 목차·구간별 요약은 초기 범위에서 뺀다. 전사는 필요할 때만 구간별로 수정하고 표시·검색에 반영하며, 원본 전사·녹음·시간 연결은 유지한다 (§11.4·12.3·12.4).
- **미결정:** 녹음 시간 모델·저장/업로드 세부 구현·PC 사양/OS/STT 모델, 포스트잇 상세 배치, 20초 표시 구간, 계산 전용 경로, Q&A 저장·중복 방지, 교정 후 소개문 갱신 정책 (§20).
- **다음 논의:** `이 구간 설명해줘`의 입력 문맥. 현재 전사와 PDF·필기 중 어디까지 전달할지 정한다. 아직 채택된 계약이 아니다 (§20.1).

## v4.2 변경 요약

v4.1의 제품 방향은 유지하되, 구현 직전에 모호하면 데이터 손실이나 검색 누락으로 이어질 핵심 계약과 주변 전제를 확정한다.

- **§7 시간축 계약 보강.** `녹음 시작함`은 오디오 0초가 아니라 대략적 앵커다. 세션 시간과 오디오 로컬 시간의 변환식을 명시하고, 오디오 파트마다 독립 `session_offset_ms`와 보정 상태를 둔다.
- **§8 캔버스 충돌 처리 추가.** 이벤트 스트리밍은 되살리지 않되 `capture_device_id`, `base_revision`, `revision`을 이용한 낙관적 잠금과 `409 Conflict` 복구 경로를 둔다. 오래된 탭이 최신 필기를 덮어쓰지 못한다.
- **§10·§11 전사 정본 분리.** `raw_text`는 보존하고 `corrected_text`를 파생 교정본으로 둔다. 전역 문자열 치환 대신 세그먼트별 교정 결과와 출처·리비전을 기록한다.
- **§2.6·§11.5·§12.1 검색 결합 규칙 확정.** 요약 검색 실패를 판정한 뒤 전사로 넘어가는 조건부 폴백 대신, 두 인덱스를 항상 제한적으로 조회해 가중 결합한다.
- **§5.1 Split View 전제 완화.** 단축어가 원하는 창 배치를 자동 생성한다고 가정하지 않는다. 사용자가 미리 구성한 창 그룹을 재사용하고 실제 기기에서 복원성을 검증한다.
- **§11.1·§11.2 공급자 사실 정리.** 청크 분할은 특정 공급자의 단일 제한에 종속하지 않고 재시도 범위·다중 파트 병합·장애 격리를 위한 공통 규칙으로 둔다. OpenAI 폴백 후보는 최신 전사 모델로 갱신한다.
- **§15 표현 정정.** 네이티브는 Boox 경로를 닫는 것이 아니라 플랫폼별 캡처 클라이언트를 하나 더 유지하게 만든다.
- **§16.2 범위 확대.** 외부 전송 대상을 STT 오디오뿐 아니라 요약·교정 LLM에 전달되는 전사와 슬라이드 텍스트까지 포함하는 `외부 AI 처리`로 정의한다.

## v4.1 변경 요약

네이티브 캡처 앱의 트레이드오프를 §15에 실제 판단 자료로 기록한다. v4.0까지 §15는 "이런 일이 반복되면 검토한다"는 조건 목록이었고, 개발 환경이 가능한지조차 확인되지 않은 상태였다.

- **§15.1 신설 — 개발 환경 실현 가능성 확인.** 보유 맥에서 Xcode 26이 동작한다. 네이티브는 선택지에서 빠지지 않는다. 다만 만료되는 것은 맥이 아니라 아이패드라는 점을 기록한다.
- **§15.2/15.3 신설 — 네이티브가 사는 것과 파는 것.** 가장 큰 이득은 필기감이 아니라 단일 시계다.
- **§15.4 신설 — 결정 시점과 전환 비용.** Phase 0·1은 두 경로가 완전히 동일하므로 결정을 미루는 비용이 0이다.
- **§14 Phase 1.5에 선행 스파이크 추가.** 반나절로 웹/네이티브 판정을 끝낸다.
- **§8.2에 입력 구현 중립 원칙 명시.** 전환 시 버려지는 범위를 입력 경로로 한정한다.
- §20에 열린 결정 3건 추가.

## v4.0 변경 요약

v3.2는 캡처 데이터의 생존과 시간 정합에 설계 분량의 대부분을 썼고, 실제로 매 학기 매일 쓰게 될 복습·시험 준비 영역은 반 페이지였다. v4.0은 그 비중을 뒤집는다.

**하드웨어 사실 정정 (가장 큰 변경)**
당시에는 2020 인텔 맥북과 Pi 5만을 전제로 로컬 STT를 제외했다. **2026-09-16 재개정으로 이 결론은 대체됐다.** 당시 문서의 기기별 속도·한국어 품질 단정은 실제 강의 실측으로 검증된 결과가 아니며 현재 사양 선정 근거로 쓰지 않는다. 새 PC 구매 고려와 귀가 후 처리 목표를 반영한 현재 계약은 §11.2다.

이 결정이 파생시킨 삭제 항목이 크다. 야간 배치 큐, 맥북 오프로드 워커, 3단 전사 우선순위, Pi 처리 속도 리스크, 처리 상태 페이지가 모두 사라진다. 동시에 처리 지연이 시간 단위에서 분 단위로 바뀌면서 **강의 직후 교정**이라는 새 흐름이 열린다.

**삭제**
- 이벤트 단위 동기화 프로토콜(`seq`/`from_seq`/`accepted_through_seq`/멱등 재전송) → 주기적 전체 스냅샷 업로드
- 오디오 임펄스 탐지 기반 싱크, 발화 구호, end anchor → 녹음 시작 버튼 시각 + 복습 화면 1탭 보정
- 질문 마커 자동 Q&A 배치 파이프라인 → 북마크 + 온디맨드 생성
- provenance 6필드 → 3필드
- `capturing_offline` 서버 상태 축 → 클라이언트 UI 배지
- Shortcut C, 그리고 Shortcut A의 서버 호출
- 요약 스키마의 `claims` / `professor_emphasis` 추출
- 중간 캔버스 snapshot 전략

**추가**
- 강의 자료(PDF) 임포트와 슬라이드 배경 필기 — v3.2 최대 결함
- 필기 → 오디오 역방향 점프 (실사용에서 가장 잦은 방향)
- 과목 허브 / 시험 범위 통합 뷰
- 전사 교정 루프와 과목 용어 사전 축적
- 오디오 다중 파트
- 전사 세그먼트 병행 인덱싱
- 세션 스키마 일반화 (강의 / 회의)
- 처리 완료 알림

**순서 변경**
복습 화면을 캔버스보다 앞으로 옮긴다. 외부 API로 전사가 즉시 끝나므로, **캔버스 없이 오디오 + 전사 + 요약 + 검색만으로 이미 쓸 수 있는 제품이 된다.** 캔버스는 그 위의 증강이지 전제가 아니다.

## 0. Executive Summary

### 이름 규칙

시스템·서버·저장소·API·repo의 주체는 **갈피**이며 영문 표기는 **galpi**로 고정한다(도메인 `galpi.local`, 토큰 스코프, 코드 네임스페이스 포함). **시온(Xion)** 은 사용자를 상대하는 비서·에이전트의 대표 이름으로, 질문 답변, 요약 발화 주체, 알림 문구에만 쓴다. 시스템 컴포넌트 이름에는 쓰지 않는다.

### 무엇인가

강의 녹음, 펜 필기, 강의 자료, 전사, 노트 소개문, 검색, 복습을 하나의 세션으로 묶는 개인용 지식 시스템이다. 핵심 가치는 녹음도 AI 요약도 아니다.

> **시간을 축으로 음성·필기·슬라이드를 연결하고, 어느 쪽에서 시작하든 나머지로 즉시 이동하는 것.**

### 구성

- **녹음·필기:** 기존 갈피 웹앱의 Lecture Notes 탭에서 통합 캡처 우선 검증. 검증 전에는 채택 완료가 아니다.
- **세션 연결·업로드:** 녹음 종료 후 원본 저장 확인 → 학교 인터넷/핫스팟을 통해 집 PC에 직접 전송
- **질문·참고 검색:** 같은 화면의 포스트잇·참고 사이드바
- **전사:** 집 PC의 로컬 Whisper 우선 검토. 구현체·모델·사양은 실측 후 결정
- **답변·소개문 요약:** 외부 API. 녹음은 복습할 때 온라인 재생
- **인덱싱·저장:** 갈피 서버. 현재 운영 Pi에서 새 PC로의 이전은 별도 작업이며 승인되지 않았다.
- **영구 저장:** 볼트의 Markdown + sidecar

PC 구매·OS·배치 방식은 아직 미정이다. 향후 로컬 메모리 에이전트를 고려하되 모델·동시 부하가 정해지기 전에는 동시 실행 성능을 보장하지 않는다. iCloud는 필수 전송 경로가 아니다 (§5.3).

초기 버전은 iPadOS 네이티브 앱을 배포하지 않는다.

## 1. Product Goal

### 1.1 해결하려는 문제

- 교수의 정확한 설명을 다시 찾기 어렵다.
- 필기만 보면 당시 맥락이 복원되지 않는다.
- 녹음만 있으면 원하는 구간을 찾는 데 오래 걸린다.
- AI 요약은 근거 발화와 연결되지 않으면 신뢰하기 어렵다.
- 강의 자료가 별도 앱이나 제조사 클라우드에 갇히면 개인 지식 시스템과 연결되지 않는다.
- 시험 기간에 한 학기치를 다시 훑을 방법이 없다.

### 1.2 핵심 사용자 경험

이 시스템은 **두 방향**을 모두 지원해야 한다. v3.2는 한 방향만 설계했다.

**방향 A — 질문에서 근거로**

> "지난주 자료구조 시간에 교수님이 레드블랙 트리 삽입 예외를 뭐라고 설명했지?"

```text
삽입 직후 부모 노드가 빨간색인 경우, 삼촌 노드 색상에 따라
재색칠 또는 회전으로 분기한다고 설명했습니다.

[자료구조 · 3회차 · 슬라이드 14 · 12:40–14:50]
```

출처를 누르면 해당 시각 원음을 재생하고, 연결된 PDF 페이지·최종 필기·전사로 돌아간다. 요약은 노트 선택 화면의 소개문이고 복습 중 구간 요약은 제공하지 않는다. 필기는 과거 화면을 복원하지 않고 재생 위치에 따라 농도를 표시한다 (§12.2).

**방향 B — 필기에서 음성으로 (실사용 빈도가 더 높다)**

복습할 때 먼저 떠오르는 건 "12분 40초"가 아니라 노트의 한 줄이다. 노트를 보다가 이해가 안 되는 획을 탭하면 **그 획을 쓰던 순간의 음성이 재생된다.** 이 기능 하나가 웹 캔버스를 직접 만드는 이유를 정당화한다. 이것이 없다면 기성 필기 앱을 쓰는 편이 낫다.

두 방향에 더해 **강의 중 즉석 질문**을 지원한다. 예를 들어 동역학 강의를 듣다가 회전모먼트 공식이 기억나지 않으면 질문 포스트잇에 묻거나 이미 쓴 수식을 선택해 시온에게 묻는다. 이 대화는 교수의 발화와 구분해 강의 노트에 남긴다 (§6.6).

### 1.3 성공 조건

1. **캡처 신뢰성:** 보통 60~90분, 최대 3시간 강의에서 필기·녹음을 보존한다. 앱 전환·중단 후에는 저장된 구간과 누락/미확정 범위를 숨기지 않으며, 강제 종료 직전 미저장분까지 무손실이라고 약속하지 않는다.
2. **검색 회수성:** 기억하는 표현과 전사 표현이 달라도 관련 구간을 찾는다.
3. **근거 복원성:** 답변이 원음·필기·슬라이드로 연결된다.
4. **시험 기간 재사용성:** 학기 중반 이후에도 실제로 열어본다.

4번이 없으면 나머지 셋을 만족해도 사용은 중단된다.

## 2. Design Principles

### 2.1 캡처 단말은 교체 가능하다
아이패드, 향후 Boox, 별도 녹음기는 모두 교체 가능한 클라이언트다. 전사, 요약, 검색, 저장은 서버에 둔다.

### 2.2 로컬 우선, 서버는 나중에
필기와 녹음은 단말에 먼저 저장한다. 네트워크가 끊겨도 캡처를 계속하고 연결되면 전송을 재시도한다. **강의 중 오프라인 캡처와 복습용 오디오 다운로드는 별개이며 후자는 초기 범위 밖이다.** 전체 필기의 실시간 스트리밍은 목적이 아니다. 캡처 업로드의 자동 재시도와 못 보낸 Q&A의 수동 재전송은 구분한다 (§6.6). 업로드 주기만으로 전체 손실 상한을 보장하지 않는다 (§20.2).

### 2.3 안정성이 우아함을 이긴다
직접 만들지 않아도 되는 것은 만들지 않는다. 같은 앱의 녹음·필기로 조작을 줄이는 방향을 먼저 검증하되, 오래 켜두는 UX가 녹음 안정성 검증을 대신하지 않는다. 참고 검색은 기존 검색 경로를 활용하고 범용 브라우저·복습용 다운로드 관리·자동 주제 목차는 초기 범위에 넣지 않는다.

### 2.4 강의 중 상호작용 최소화
필기와 사용자가 원한 질문 외의 조작을 최소화한다. 질문 때문에 별도 채팅 화면으로 이동하거나 이미 쓴 내용을 다시 입력하게 하지 않는다. 캡처 화면은 소리를 내지 않고 실패는 눈에 보여야 한다.

### 2.5 사람이 읽는 노트, 기계가 읽는 sidecar
Markdown에는 사람이 읽는 정보와 작은 메타데이터만. 스트로크·타임라인·전사 세그먼트는 JSON/JSONL/SQLite로 분리한다.

### 2.6 요약과 전사를 함께 찾되 역할을 분리한다
**v3.2에서 변경.** 요약만 인덱싱하고 원본을 제외하면 요약이 놓친 내용은 영구히 검색 불가가 된다. 반대로 전사만 검색하면 중복·군더더기가 상위 결과를 잠식한다.

**소개문은 노트 단위, 전사는 시간 구간 단위다.** 짧은 소개문이 회수됐다고 그 노트의 어느 구간이 정답인지 확정할 수 없으며, 세부 근거는 전사에서 찾아야 한다. 소개문에 빠진 내용도 전사 검색으로 회수할 수 있어야 한다.

볼트 일반 검색에는 사람이 읽는 소개문을 노출하고 전사 인덱스는 Lecture 검색 경로에 둔다는 기존 경계를 유지한다. 다만 옛 `구간 요약 + 전사` 동급 후보 병합·요약 prior 수치는 소개문 계약에 그대로 적용하지 않는다. 구체 검색 결합은 §11.5·20에서 다시 설계한다.

### 2.7 네이티브 전환에는 증거가 필요하다
웹 통합 녹음·필기를 먼저 검증한다. 캡처 안정성·싱크·필기감이 기준을 통과하지 못하면 녹음/캡처 경로만 다른 방식으로 검토하고 갈피 전체를 네이티브로 재작성하지 않는다.

## 3. Confirmed Decisions

1. 초기 캡처 단말은 보유 중인 iPad와 Apple Pencil이다.
2. Lecture Notes는 별도 앱이 아니라 기존 갈피 웹앱의 독립 탭이다.
3. 녹음 시작은 명시적 조작이다. 웹 통합 녹음을 먼저 검증하며, 성공한 실제 녹음 상태와 시간 연결을 확인한 뒤 채택한다.
4. 세션 생성은 웹앱이 담당한다. 기본 전송은 집 PC로 직접 업로드이며 단축어 두 개를 필수로 두지 않는다.
5. **로컬 STT를 다시 열었다.** PC·모델은 미정이고 귀가 후 복습 시점의 준비가 목표다. 실시간 전사는 요구하지 않는다.
6. 원본은 보존한다. 녹음 종료 후 전송하고, 수신 이후 전사·소개문 생성·인덱싱을 진행한다. 재인코딩·청크 크기는 구현 전 검증 대상으로 남긴다.
7. 전사는 필요할 때 구간별로 수정한다. 원본 전사·오디오는 유지하고 수정문을 표시·검색에 반영한다. 자동 전공 지식 보완으로 실제 발화를 바꾸지 않는다.
8. 필기 데이터는 IndexedDB에 즉시 저장하고, `base_revision` 충돌 검사를 포함한 주기적 상태 업로드를 사용한다.
9. 오디오–필기 정합은 녹음 시각과 필기 시각의 연결로 관리한다. 일시정지·재개·중단·앱 재실행을 포함하는 시간 모델은 아직 미정이며 파일당 단일 오프셋만으로 해결됐다고 보지 않는다 (§7).
10. 강의 자료 PDF를 세션에 첨부하고 캔버스 배경으로 사용한다.
11. 중요·나중에 볼 북마크는 명시적 조작으로 남긴다. 일반 손글씨 도형·물음표를 명령으로 해석하지 않으며 시온 질문과 북마크를 구분한다 (§6.4·6.6).
12. 세션 스키마는 강의 전용이 아니라 컨테이너 기반으로 일반화한다.
13. Boox 또는 네이티브 캡처 앱은 실사용 데이터 확보 후 조건부 검토한다.
14. 재생 화면은 최종 필기의 농도 표시이며, 지우기·실행 취소 이력을 재생하는 과거 화면 복원이 아니다 (§12.2).
15. 질문 포스트잇과 기존 필기 선택 질문은 같은 대화 구조를 사용하고, 원본 필기를 지워도 질문·답변은 남는다 (§6.6).
16. 복습 독바는 가사형 전사다. 소개문은 노트 목록에 두고 초기 스트로크 목록·자동 주제 목차·구간별 요약은 제외한다 (§12).

## 4. System Architecture

아래는 합의한 제품 흐름이며 서버 이전·새 API·DB 스키마의 구현 승인이 아니다. 웹 직접 녹음과 로컬 전사는 각각 기기 검증·품질/속도 검증을 통과해야 한다.

```text
iPad · Galpi Web
  노트/PDF·필기·질문 포스트잇·참고 검색
  명시적 녹음 시작 → 일시정지/재개 → 종료
  필기/녹음 중간 로컬 저장 + 시간 연결
        │ 종료 후 원본 저장 확인 · HTTPS 직접 전송/재시도
        ▼
집 PC · 갈피 서버 (구매/이전 미실행)
  원본 보존 → 로컬 전사 → 외부 API 소개문 → 검색 인덱스
  Vault: 소개문 Markdown + 오디오/PDF/필기/전사/시간 연결
  Q&A 보존 (DB/sidecar 배치는 미정)
        │ 온라인 조회·오디오 재생
        ▼
Galpi Review
  노트 목록: 짧은 소개문
  PDF·필기: 재생 위치별 농도
  전사 독바: 현재 구간 강조·탭 재생·필요할 때 교정
```

### 4.1 컴포넌트 경계

**Capture Web Client** — 세션 생성·표시, PDF 배경, 필기 캔버스, 시각 태그, 녹음 조작, 중간 로컬 저장, 업로드·복구, 질문 포스트잇·이미지 선택 질문, 참고 검색, 캡처 중 자동 소리 재생 차단

**전송** — 웹 캡처에서 집 PC로 직접 전송. 외부 녹음·단축어는 웹 녹음 검증 실패 시 다시 검토할 대안이지 필수 컴포넌트가 아니다.

**Processing** — 오디오 검증·보존, 로컬 STT 우선 검토, 노트 소개문 생성, 인덱싱, 볼트 커밋. 자동 주제 목차·구간 요약 생성은 초기 범위 밖이다.

**Review Client** — 소개문이 있는 노트 선택 화면, 가사형 전사 독바, 타임코드 점프, PDF·최종 필기 농도 표시, 필기 → 음성 역점프, 보존된 Q&A, 필요할 때 전사 교정. 과목 허브·시험 범위 기능의 상세 범위는 미정이다.

강의 중 Q&A는 강의 후 Processing 완료를 기다리는 경로가 아니다. 입력 문맥과 사용자에게 보이는 동작은 §6.6을 따르고, 저장·API 연결의 구현 계약은 §20.1에서 별도로 확정한다.

### 4.2 공유 blob 경계

일반 첨부와 강의 오디오는 저장 기반만 공유한다 — 서버 생성 ID, SHA-256·MIME·크기 검증, temporary 저장, 인증된 읽기, 원자적 finalization, orphan 정리.

강의가 별도로 소유한다 — 세션, 대용량·재개 업로드, 오디오 파트 관리, 청크 전사, 학기별 보존 정책.

사람이 보는 강의 Markdown은 평면 Vault에, 바이너리와 기계 sidecar는 `_attachments/lectures/<session_id>/`에 둔다.

## 5. 전송·보관 — 합의

### 5.1 강의 종료 후 직접 전송

기본 흐름은 **갈피에서 녹음 종료 → 단말 원본 저장 확인 → 학교 인터넷/핫스팟으로 집 PC에 전송 → 정상 저장 확인 → 전사·소개문 처리**다. 집에 도착해야 업로드를 시작하는 흐름이 아니다. 기존 Shortcut A/B와 음성 메모 Split View는 필수 경로에서 제외한다.

전송 실패 시 단말 원본을 유지하고 연결이 돌아오면 재시도한다. 기존 해시 중복 방지·올바른 세션 연결·인증된 업로드/읽기 경계를 유지한다. 앱 종료·백그라운드 상태에서도 전송이 끝난다고 보장하지 않으며 재개 방식·완료 확인·저장 검증은 구현 전 과제다.

### 5.2 온라인 복습과 단말 사본

- 복습 녹음은 집 PC에서 온라인으로 불러온다. 별도의 복습용 다운로드·오프라인 듣기는 초기 범위에서 제외한다.
- 강의 중 네트워크가 없어도 필기·녹음을 보존해야 하는 요구는 그대로다.
- PC에 정상 저장됐는지 확인하기 전에는 아이패드 사본을 삭제하지 않는다. ACK의 실제 저장 보장과 확인 절차는 구현 전 확정한다.
- 정상 저장 확인 후 단말 사본을 언제 정리할지, 원본을 얼마나 오래 보관할지는 미정이다. 전사·소개문 완료가 오디오 삭제 조건은 아니다.
- 집 PC가 꺼지거나 연결되지 않으면 온라인 오디오 복습을 사용할 수 없다. 이 경우 원본이 삭제됐다고 표시하지 않는다.

### 5.3 iCloud는 선택적 보관 수단

사용자는 iCloud를 사용하지만 **iPad → 집 PC 직접 전송이 기본**이다. iCloud 연동은 필수 조건이 아니고 이를 위해 PC 운영체제를 결정하지 않는다. 향후 내보내기를 지원한다면 오디오뿐 아니라 PDF·필기·시간 연결·전사·Q&A도 함께 복원할 수 있어야 한다. 내보내기 형식·자동 연동 구현은 미승인이다.

기술 경계의 근거:
- [WebKit의 origin-private 저장소](https://webkit.org/blog/12257/the-file-system-access-api-with-origin-private-file-system/)는 웹앱 내부 저장소다. iCloud Drive에 자동으로 나타나는 파일과 같지 않다.
- [Apple iCloud Drive 설정](https://support.apple.com/en-us/118443)은 Mac·Windows 등의 동기화 경로를 안내한다. Linux 서버에 같은 공식 데스크톱 동기화 경로가 있다고 전제하지 않는다.
- [iPad 다운로드 유지](https://support.apple.com/en-om/guide/ipad/ipad8139864c/ipados)는 로컬 사본을 유지하는 기능이다. 클라우드에만 있는 파일의 오프라인 재생이나 갈피에서의 자동 접근을 보장하지 않는다.
- [iCloud Drive 동기화](https://support.apple.com/en-gb/guide/icloud/mm19ef899373/icloud)는 삭제도 반영한다. 독립 백업과 동일하게 취급하지 않는다.

참조는 2026-09-16 설계 검토 근거이며 실제 기기의 설정 확인이나 연동 인수를 뜻하지 않는다.

## 6. Capture UX

### 6.1 시작

1. 노트를 열어 과목·PDF·필기를 준비한다. 노트 열기만으로 마이크를 켜지 않는다.
2. 사용자가 명시적으로 `녹음 시작`을 누른다.
3. 권한·기기 동작을 거쳐 실제 녹음 시작이 확인된 뒤에만 `녹음 중`으로 표시한다. 버튼을 누른 시각이나 UI 타이머만을 실제 첫 샘플의 증거로 쓰지 않는다.
4. 녹음·로컬 저장·서버 연결 상태는 구분해 보여준다. 녹음 시작 실패가 필기·질문을 막지 않는다.

웹 직접 녹음은 §14의 실기기 검증을 통과해야 한다. 시작 확인 이벤트·실제 오디오 위치·필기 시각을 연결하는 구체 계약은 §7에서 열어둔다.

### 6.2 강의 중

- 기본 상태에서 Apple Pencil 입력만 필기로 처리한다. 손가락은 스크롤·확대·이동.
- 저장 완료된 필기는 화면을 벗어나도 복구할 수 있어야 한다. 앱 종료 직전의 미저장분까지 무손실이라고 단정하지 않는다.
- 서버가 끊기면 오프라인 배지를 띄우고 기록은 계속한다.
- 캡처 화면은 TTS, 효과음, 자동 재생을 하지 않는다.
- 질문 포스트잇과 선택 질문은 화면 안에서 다루고, 답변 도착이 필기나 페이지 위치를 강제로 바꾸지 않도록 설계한다 (§6.6).
- `일시정지` 중에도 필기는 가능하다. `재개`하면 같은 강의에 연결하고 쉬는 동안의 필기는 보존하되 녹음되지 않은 시간에 가짜 음성을 연결하지 않는다.
- 강의 중에는 보통 갈피를 계속 켜두는 사용을 기준으로 한다. 참고 검색은 §6.9에서 제공하되 앱 전환·잠금·마이크 중단이 없을 것이라고 가정하지 않는다.

### 6.3 강의 자료 (신규)

**v3.2의 가장 큰 결함은 빈 캔버스를 전제한 것이다.** 대학 강의는 교수 슬라이드 위에 필기하는 것이 기본이고, 자료 없이 백지에 쓰는 설계는 필기감이 아무리 좋아도 실사용에서 밀려난다.

- 세션 생성 시 또는 강의 중에 PDF를 첨부한다. 캔버스 페이지의 배경 레이어가 된다.
- 필기는 별도 레이어이며 PDF 원본을 변경하지 않는다.
- `page_change`는 사용자가 본 PDF 페이지와 시각의 연결이다. 교수가 그 페이지를 설명했다는 증거는 아니다. 자동 주제 경계·전사 교정의 확정 근거로 쓰지 않는다.
- 복습에서 당시 페이지로 돌아가는 연결과 명시적 선택 질문의 첨부에 활용한다. 답변에서 페이지를 근거로 제시하려면 실제 해당 자료를 확인해야 한다.
- 자료가 없는 강의는 빈 페이지로 폴백한다. PDF는 필수가 아니라 있으면 강해지는 신호다.

### 6.4 마커

북마크는 시온 질문과 별개다. 기존의 명시적 마커 조작을 기준으로 두되 최종 배치·명칭은 질문 UI와 함께 정한다. 손글씨 도형 인식은 쓰지 않는다.

- `★ 중요` — 사용자가 중요하다고 표시한 시각을 남긴다. 소개문에 모든 표시를 억지로 포함하지 않으며 별도 목록·정렬 방식은 미정이다.
- `? 나중에 볼 것` — 그 시각의 북마크를 남긴다. 시온에게 전송하는 질문이 아니다.

한 번 탭하면 현재 시각에 이벤트를 남기고, 길게 누르면 최근 마커를 취소한다.

**`?` 마커는 자동 답변을 생성하지 않는다.** 역할은 "여기 몰랐음, 나중에 볼 것"이라는 북마크다. 실제 질문은 §6.6의 명시적인 질문 흐름을 사용한다. 복습 화면의 `이 구간 설명해줘`도 온디맨드 진입점이며, 강의 후 전사 구간을 참조하는 이 입구의 세부 문맥은 별도로 정한다 (§20.1).

옛 `★`의 구간 요약 강제 포함 규칙은 소개문 계약과 충돌하므로 적용하지 않는다. 명시적 북마크의 보존과 요약 생성은 별개다.

### 6.5 종료

1. 사용자가 갈피에서 `녹음 종료`를 누른다.
2. 원본 저장 완료를 확인한 뒤 집 PC로 전송을 시작한다 (§5.1).
3. 노트는 그대로 열려 있다. 녹음 종료 후에도 필기·질문을 계속할 수 있다.
4. 전사·소개문은 귀가 후 복습할 때 준비되는 것을 목표로 처리한다 (§11.2).

**노트의 수명과 녹음의 수명은 별개다.** 녹음 종료가 노트 편집 금지나 강제 페이지 이탈을 뜻하지 않는다. 노트 닫기·같은 강의에 추가 녹음·처리 중 입력 변경의 구체 상태 전이는 §9·20에서 다시 확정한다.

### 6.6 질문 포스트잇 · 기존 필기 선택 질문 — 합의

**입구는 둘, 대화 구조는 하나다.** 질문의 문장 모양이나 물음표 유무가 아니라 사용자가 질문 흐름으로 들어와 전송한 행위가 시온을 향한 요청을 구분한다.

1. **새 질문:** 빈 질문 포스트잇 열기 → 손글씨로 질문 작성 → 명시적 전송.
2. **기존 내용 질문:** 선택 도구로 필기 범위를 둘러싸기 → 선택 영역 근처의 `시온에게 묻기` → 선택 내용이 붙은 질문 초안 → 필요한 질문을 덧붙여 전송.

선택한 수식만으로 계산·설명·검산 중 의도를 단정하지 않는다. 선택이나 포스트잇 열기 자체는 AI 호출이 아니고, 글쓰기를 잠시 멈췄다고 자동 전송하지 않는다. 일반 필기 모드의 원·별·물음표는 계속 필기다. 선택 모드가 켜진 동안의 둘러싸기만 선택으로 취급한다.

**대화 표시**

```text
[선택한 필기 사본 — 있는 경우]
질문: 여기서 부호가 왜 음수야?
시온: …
  ㄴ 반대 방향으로 돌면 어떻게 돼?
     시온: …
```

포스트잇 안에서 이어 쓰는 질문은 같은 대화의 후속 질문이고, 새 포스트잇은 새 질문이다. `ㄴ`은 후속 대화를 표시하는 UI이며 일반 필기의 해당 기호를 자동 인식하는 호출 명령이 아니다. 구체적인 후속 입력 영역과 전송 조작은 미결정이다.

**보존할 의미**

- 사용자가 전송한 질문의 손글씨·텍스트와 선택 원본의 사본, 시온의 답변, 후속 대화를 함께 보존한다. 원본 필기를 지우거나 수정해도 이미 남긴 Q&A를 함께 없애지 않는다.
- 원본 페이지·선택 위치와 강의 세션으로 돌아갈 연결을 둔다. 질문한 실제 시각과 질문이 가리키는 강의/오디오 위치는 구분한다. 복습 중 12분 지점을 물었다고 질문 생성 시각을 강의 12분으로 기록하지 않는다.
- 오디오 위치가 아직 보정되지 않았거나 대응되지 않으면 미확정으로 둔다. Q&A 보존을 강의 후 전사 완료에 종속시키지 않는다.
- 시온 답변은 교수 발화나 전사 정본이 아니다. 강의 근거와 사용자·시온 대화의 출처를 섞지 않는다.
- 이는 제품 보존 계약이다. 아래에서 초안·실패·재전송의 UX를 정하며, 구체 필드·DB/sidecar·요청 식별·사용자 삭제 정책은 아직 확정하지 않았다 (§20.1).

**질문 입력 문맥 — 합의**

| 진입 방식 | 기본 전달 내용 |
|---|---|
| 빈 포스트잇의 새 질문 | 질문만 |
| 기존 필기·원문 선택 질문 | 질문 + 선택 영역 + 그 영역이 속한 PDF 페이지. PDF 없는 백지 필기는 선택 영역만 첨부 |
| 같은 포스트잇의 후속 질문 | 그 포스트잇의 앞선 Q&A + 기존 첨부 자료 + 새 질문 |

원문 참조 여부를 모델이 추측해 주변 자료를 자동으로 붙이지 않는다. 진입 방식이 기본값을 정하고, 사용자는 `PDF 14쪽 첨부됨` 같은 표시를 보고 첨부를 빼거나 일반 질문에도 페이지를 추가할 수 있다. 현재 화면을 다른 페이지로 넘겨도 기존 질문의 첨부는 자동 교체되지 않는다. 페이지는 원문의 조건·그림·기호 정의를 보여주는 용도이며, 주변 손글씨 전체·다른 페이지·강의 전사는 기본으로 보내지 않는다. 문맥이 부족하면 필요한 자료를 묻는다. 강의 중 업로드·전사되지 않은 음성을 시온이 이미 들었다고 가정하지 않는다.

**이미지 입력 — 추가 합의**

- 선택 영역은 텍스트 파싱을 필수로 거치지 않고 이미지로 전달한다. 사진·도표·수식도 같은 경로를 사용한다.
- 선택 질문은 질문 + 선택 영역 이미지 + 해당 PDF 페이지 이미지를 기본으로 한다. 손글씨 질문도 이미지 원본으로 전달하고, 백지 필기는 PDF 페이지 없이 처리한다.
- 이미지는 현재 화면을 그대로 캡처하지 않고 원본 PDF·필기에서 만든다. 확대율에 따라 해상도가 떨어지거나 메뉴·선택 테두리·재생 농도 효과가 입력에 섞이지 않게 한다.
- 선택한 필기는 선택 이미지에 포함한다. 해당 PDF 페이지 이미지에 주변 손글씨 전체까지 자동으로 붙이지 않는다.
- 원본 PDF·필기 벡터·선택 위치와 실제 보낸 이미지 사본을 구분해 보존한다. PDF의 향후 텍스트 검색 가능성을 없애는 결정은 아니다. 해상도·용량 상한·모델은 구현 전 확정한다.

**손글씨 인식·정정 — 합의**

- 매번 인식된 텍스트를 검수·승인하게 하지 않는다. 손글씨 질문을 쓰고 명시적으로 전송하면 된다.
- 손글씨 원본을 질문 입력으로 유지한다. 인식 텍스트를 생성하더라도 원본을 버리거나 인식문만으로 대체하지 않는다.
- 전송 전 초안은 자유롭게 수정한다. 전송한 질문·이미지·기존 답변은 유지하고, 잘못 읽었을 때는 `ㄴ 저건 2가 아니라 z야`처럼 후속 질문으로 정정해 새 답변을 받는다. 질문만 바꿔 옛 답변이 수정된 질문에 대한 답처럼 보이게 하지 않는다.
- 부호·문자처럼 읽기에 따라 답이 달라지는 부분이 모호하면 그 부분만 되묻는다. 이전 오답은 자동 삭제하지 않으며 접어 읽는 상세 UI는 미정이다.
- 정정을 대화에서 참고하는 것과 사용자 필체로 모델 자체를 학습하는 것은 별개다. 개인화 학습은 이번 범위에 넣지 않으며 실제 오독 표본을 보고 별도로 판단한다. 모델·인식 파이프라인은 아직 확정하지 않았다.

**수동 접기·펼치기와 답변 표시 — 합의**

- 포스트잇은 필요할 때 펼쳐 보며, 접기와 펼치기는 모두 사용자 조작으로만 한다. 전송·답변 도착·페이지 이동 때문에 자동으로 접거나 펼치지 않는다.
- 접힌 포스트잇에 새 답변이 오면 갈피 강조색의 작은 점으로 표시한다. 빨간색을 새로 고정하거나 숫자·소리·깜빡임을 추가하지 않는다.
- 사용자가 펼쳐 새 답변을 확인하면 점을 없앤다. 답변 도착 전에 펼쳤다가 접은 행위는 새 답변 확인으로 치지 않는다. 펼친 상태에서도 아직 보지 못한 답변의 확인 판정은 구현 전에 정한다.
- 펼쳐진 상태에서 답변이 와도 포스트잇 크기·읽던 위치·필기 중인 페이지를 강제로 바꾸지 않는다.
- 입력 보존은 접힘 상태와 무관하다. 접힌 표시의 질문 번호·첫 줄, 원본 근처 배치·이동·긴 답변 내부 스크롤·확대 읽기는 제안 상태이며 세부 배치는 미확정이다. 페이지에 소속시키는 방향과 페이지 전환 중 열린 포스트잇을 표시하는 방법도 함께 확정한다.

**오프라인·실패·재전송 — 합의**

- 작성 중 초안은 기기에 저장한다. 포스트잇을 접거나 페이지를 넘겨도 사라지지 않는다.
- 오프라인에서 전송을 누르면 질문·선택 필기·첨부 페이지를 보존하고 `전송 안 됨`으로 표시한다. 연결이 돌아와도 못 보낸 질문을 자동 전송하지 않는다.
- 이미 보낸 뒤 연결이 끊기면 재연결 시 기존 요청의 결과부터 자동 확인한다. 답변을 못 받았다는 이유만으로 새 요청을 만들어 중복 전송하지 않는다.
- 실제 요청 실패가 확인되면 내용을 유지하고 `다시 보내기`를 제공한다. 결과가 아직 불명인 상태를 곧바로 실패로 단정하지 않는다. 요청 식별·상태 조회·재시도 멱등성은 구현 계약으로 남긴다.
- 접혔을 때 새 답변은 강조색 점, 실패·전송 안 됨은 별도 작은 느낌표로 구분한다. 펼치면 이유와 가능한 조치를 보여준다. 실패가 필기·녹음을 중단시키지 않는다.

새 포스트잇은 §6.8 원형 메뉴에서 호출한다. 길게 누르기만으로 곧바로 포스트잇을 열던 후보는 이 방식으로 대체한다. 기존 도구막대도 대체 조작으로 유지한다.

### 6.8 펜 길게 누르기 · 원형 메뉴 — 합의

**펜을 화면에 대고 잠시 유지 → 원형 메뉴 등장 → 방향 이동으로 항목 강조 → 펜을 떼면 선택**한다. `꾹`은 강한 압력이 아니라 접촉 시간이다. 메뉴에서 질문을 선택해도 포스트잇만 열며 질문을 전송하지 않는다.

- 처음 접촉한 자리에서 거의 움직이지 않은 경우만 메뉴 호출 후보로 본다. 이미 획을 그리기 시작했다면 도중에 멈춰도 메뉴를 열지 않는다.
- 메뉴가 열린 뒤 방향 이동 중에는 선택 미리보기만 한다. 중앙에서 떼거나 중앙으로 돌아와 떼면 취소한다. 입력이 중단되어도 취소하며 기본 항목을 임의 실행하지 않는다.
- 메뉴 호출에 사용한 점·이동 경로는 필기로 남기지 않는다. 메뉴가 열리기 전에 끝난 정상 필기·점은 잃지 않아야 한다.
- 항목은 **펜·지우개·선택·질문 포스트잇 네 개**로 합의했다. 4방향의 구체 배치는 아직 미정이며 사용 도중 항목 위치를 임의 재배치하지 않는 방향으로 설계한다.
- 누름 시간·이동 허용치·중앙 취소 영역·가장자리에서의 메뉴 배치는 실기기에서 정한다. 손가락의 스크롤·확대와 브라우저 기본 메뉴를 방해하지 않도록 캔버스에서 검증한다. 특정 펜의 압력·측면 버튼 기능을 필수로 삼지 않는다.
- 기존 도구막대를 보이는 대체 조작으로 남긴다. 제스처만 알아야 핵심 기능을 사용할 수 있게 만들지 않는다.

웹 구현 가능성의 근거는 접촉·이동·해제·취소와 입력 종류를 제공하는 [Pointer Events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events)다. Safari의 펜 입력 지원은 [WebKit 안내](https://webkit.org/blog/9674/new-webkit-features-in-safari-13/)에 있고, 방향 선택의 참고 패턴은 [Microsoft의 radial/marking menu 설명](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/mpc/using-context-menus)이다. 이는 API·패턴 존재의 근거이지 현재 아이패드의 오작동·지연 검증 완료를 뜻하지 않는다.

### 6.9 참고 검색 사이드바 — 합의

강의 중 필요한 참고 자료를 갈피 안에서 확인해 앱을 오가는 일을 줄인다. 필기 화면 옆에 사용자가 직접 열고 닫는 참고 사이드바를 두고, 검색 결과·짧은 설명·출처를 보여주며 필요하면 시온에게 설명을 요청한다. 단순 검색마다 AI 답변 완료를 기다리게 하지 않는다. 결과 도착이 필기 위치·작성 중 질문을 바꾸지 않게 한다.

기존 갈피 검색 경로를 재사용하는 방향이며 별도 검색 공급자나 범용 내장 브라우저를 추가하는 승인은 아니다. 모든 웹사이트를 사이드바 안에서 탐색하게 보장하지 않는다. 사이트가 [X-Frame-Options 등으로 삽입을 차단](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Frame-Options)할 수 있어 원문은 외부 브라우저로 열어야 할 수 있다. 웹 결과는 외부 자료이며 교수 발화·사용자 필기와 구분한다.

검색 사이드바와 복습 전사 독바의 공간 공유·전환·너비는 미정이다. 앱에 오래 머무는 UX는 녹음 신뢰성 보장이 아니며, 잠깐 벗어났을 때의 저장·중단·복귀를 별도로 검증한다.

## 7. Audio–Canvas Synchronization

### 7.1 시간축 계약

**같은 앱에서 녹음한다고 시계 문제가 자동 해결되는 것은 아니다.** 버튼 시각·이벤트 수신 시각·실제 오디오 첫 샘플은 구분한다. 녹음 시작·일시정지·재개·중단을 오디오 위치와 연결하고 필기 시각이 그 관계를 참조해야 한다. 구체 수집 방법과 저장 필드는 미확정이다.

복습에서는 **전사와 필기가 서로를 기준으로 삼지 않고 모두 오디오 재생 시각을 따른다.** 전사 구간 길이와 20초 후보 필기 표시 구간은 별개다. 전사 미완료·실패가 원음 재생과 필기 농도 표시를 막지 않는다.

아래는 기존 별도 녹음 경로의 시간 표현이다. 변수의 역할을 설명하기 위해 남기되 새 통합 녹음의 확정 스키마로 취급하지 않는다.

- `session_t_ms` — 갈피 캡처 세션 시작 이후의 단조 증가 시간
- `audio_local_ms` — 각 오디오 파일 내부의 재생 위치
- `session_offset_ms` — 해당 오디오 파트의 첫 프레임이 세션 시간축에서 시작하는 위치

아래 단일 오프셋 변환은 **누락·시간 압축·drift 문제가 없는 연속 구간에만** 쓸 수 있다. 일시정지·재개를 포함한 파일 전체의 변환식으로 고정하지 않는다.

```text
session_t_ms = audio_local_ms + audio_part.session_offset_ms
audio_local_ms = session_t_ms - audio_part.session_offset_ms
```

옛 음성 메모 경로의 `녹음 시작함` 버튼·단축어 완료 콜백은 실제 오디오 0초의 증거가 아니었다. 통합 경로도 UI 타이머나 녹음 데이터 조각 수만으로 시간을 확정하지 않는다. [MDN의 dataavailable 주의사항](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/dataavailable_event)은 조각 간격 지연·Safari 마이크 일시정지 가능성을 명시한다. 실제 시작·중단 감지와 최대 3시간 drift를 기기에서 검증한다.

v3.2의 임펄스 탐지(±30초 창에서 에너지 피크 검색)는 폐기한다. 강의실에는 기침, 의자, 문, 마이크 팝이 상시 존재해 오탐 가능성이 높고, 오탐이 나도 복습 시점까지 알기 어렵다.

### 7.2 복습 보정

통합 녹음에서도 보정이 필요할 수 있다. 아래는 기존 앵커 보정 후보이며 모든 강의에서 사용자에게 보정을 요구하기로 확정한 것이 아니다. 적용 가능한 연속 구간의 경계를 먼저 알아야 한다.

보정은 시스템이 대응 음성을 추측하는 버튼이 아니라, 사용자가 **같은 순간의 획과 음성을 지정하는 앵커 생성 흐름**이다.

```text
복습 화면에서 오디오를 해당 설명까지 탐색
→ 그때 작성한 획 선택
→ `이 소리가 이 획` 탭
→ session_offset_ms 계산·저장
```

계산식:

```text
audio_part.session_offset_ms
  = selected_stroke.t_ms - audio_player.currentTime_ms
```

보정은 해당 연속 구간에만 적용하며 누락 구간을 채우거나 여러 중단을 단일 오프셋으로 숨기지 않는다. 잘못 맞췄다면 다시 보정할 수 있어야 한다. drift까지 한 앵커로 해결됐다고 보지 않으며 구체 보정 단위는 실측 뒤 확정한다.

### 7.3 시계 모델

- `created_at` — 사람이 읽고 시스템 간 대조하는 벽시계
- `t_ms` — 세션 시작 이후 단조 증가 경과 시간
- `session_offset_ms` — 오디오 로컬 시간을 세션 시간으로 옮기는 파트별 값

기기 벽시계가 조정돼도 스트로크 순서와 재생 위치가 깨지지 않아야 한다. 단조 시계는 페이지 실행 수명과 오디오 시계가 같다고 전제하지 않는다. 브라우저 재실행 전후의 연결, 녹음 중단 경계, 매핑 확실성의 표현을 구현 전에 정한다.

### 7.4 오디오 다중 파트

같은 강의 안에서 일시정지·재개·중단 복구를 허용한다. 쉬는 동안의 필기는 남지만 녹음과 대응되지 않으며 중단 후에도 빈 구간을 유지한다. **재개마다 새 파일을 만드는지, 한 파일과 별도 시간 매핑을 쓰는지는 미정**이다. 아래 JSON은 기존 외부 파일 추가 경로의 예시이지 통합 녹음의 확정 계약이 아니다.

```json
"audio_parts": [
  {
    "part": 1,
    "file": "part1.m4a",
    "session_offset_ms": 0,
    "duration_ms": 2700000,
    "offset_source": "start_confirmation",
    "calibrated": false
  },
  {
    "part": 2,
    "file": "part2.m4a",
    "session_offset_ms": 3300000,
    "duration_ms": 2400000,
    "offset_source": "review_anchor",
    "calibrated": true
  }
]
```

파일 안에서 녹음이 멈춘 동안 시간이 압축될 수 있으므로 파일당 오프셋 하나·보정 한 번을 일반 보장으로 쓰지 않는다. 전사 시각은 오디오 내부 위치일 뿐 필기와의 시계 차이를 자동 복구하지 않는다. 미확정 매핑에는 정밀 점프를 보장하지 않고, 연결 가능한 구간만 사용한다.

## 8. Canvas Persistence

### 8.1 저장 모델

v3.2의 이벤트 단위 동기화 프로토콜(`seq`, `from_seq`, `accepted_through_seq`, `duplicate_event_ids`, 멱등 재전송, `sync_state`)을 폐기한다. **강의 중 모든 필기 이벤트를 서버로 스트리밍하지 않는다.** 명시적 선택 질문의 입력 전달은 별도이며, 이를 위해 전체 필기 스트리밍을 되살리지 않는다.

```text
Pointer event
→ stroke 생성 (t_ms 부착)
→ IndexedDB 즉시 append
→ 화면 렌더링
→ (2~5분마다 / 화면 이탈 시 / 세션 종료 시)
   revision 조건부 캔버스 상태 PUT
```

앞 세 단계는 서버 없이 동작한다. 주기 업로드는 서버 복제 지연을 줄이는 수단이며, 오프라인·강제 종료·단말 손실의 보장 범위는 별도로 검증해야 한다 (§20.2).

90분 필기 전체의 크기는 아직 가정하지 않는다. Tailscale 연결도 강의실에서는 인터넷 또는 핫스팟 업로드를 사용할 수 있다. Phase 1.5에서 **30분 원본 JSON·gzip 크기, 90분 예상 총전송량, 전체 PUT과 변경 페이지만 PUT할 때의 차이**를 실측한다. 전체 상태가 커지면 이벤트 스트리밍으로 돌아가지 않고 변경된 페이지 단위 dirty snapshot으로 축소한다.

### 8.2 캔버스 상태 형식

```json
{
  "session_id": "les_20260901_csds_0900_01",
  "capture_device_id": "ipad-main",
  "base_revision": 11,
  "revision": 12,
  "pages": [
    {"page_id": "p03", "slide_no": 14, "strokes": [
      {"stroke_id": "s1042", "t_ms": 420312, "tool": "pen", "width": 1.8, "points": []}
    ]}
  ],
  "markers": [
    {"t_ms": 427820, "type": "question"},
    {"t_ms": 511004, "type": "important"}
  ],
  "page_changes": [
    {"t_ms": 431200, "page_id": "p04", "slide_no": 15}
  ]
}
```

스트로크마다 `t_ms`를 유지하는 것이 §1.2 방향 B(필기 → 음성)의 전제다. 이 필드는 최적화 대상이 아니다.

위 JSON은 기존 캡처 스키마 초안이다. §12.2의 농도 표시는 현재 남아 있는 스트로크와 시각을 사용하고, 삭제된 획·지우개·실행 취소의 전체 이력은 복습을 위해 저장하지 않는다. Q&A는 이 캔버스 상태에 합쳐 지워지는 데이터가 아니며 §6.6의 보존 계약을 따른다. 복습 중 추가한 필기나 오디오와 대응되지 않는 필기에 가짜 녹음 시각을 부여하지 않는다. 해당 구분의 구체 스키마는 미결정이다.

**이 포맷은 입력 구현에 중립적으로 유지하는 것이 목표다.** 웹 캔버스와 향후 PencilKit 경로에서 서버·복습 렌더링을 재사용하기 위한 방향이며, 실제 전환 때 시간 모델·복구·포맷 변환까지 다시 검증한다 (§15.4).

### 8.3 복구

- 새로고침·브라우저 강제 종료 후 마지막으로 저장 완료된 로컬 상태 복구
- 업로드 실패 시 다음 주기에 자동 재시도
- PUT에는 `base_revision`을 보내고 서버 현재 revision과 다르면 `409 Conflict`를 반환
- 충돌 시 자동 덮어쓰지 않고 서버본·로컬본·기기 ID·수정 시각을 보여준 뒤 복구 선택
- 단일 기기 정상 경로에서는 ACK된 서버 revision을 다음 `base_revision`으로 저장
- 세션 종료 시 미업로드 또는 충돌 미해결 상태면 경고
- 캡처 중 원본을 유지하고 PC 정상 저장 확인 전 자동 정리 금지. 저장 확인 뒤 사본 정리 시점은 미정 (§5.2).

단말 로컬본은 캡처 중 가장 중요한 원본이지만, **오래된 탭이 항상 진실인 것은 아니다.** 이벤트 단위 동기화를 폐기한 결정과 revision 충돌 검사는 양립한다.

과거 화면 복원용 중간 snapshot 전략은 사용하지 않는다. §12.2는 현재 남아 있는 필기를 그리고 시각에 따라 농도만 조절한다. 저장·복구에 필요한 상태 snapshot과는 다른 문제다.

**녹음 중간 저장·복구 — 추가 합의**

- 녹음도 진행 중 나눠 저장한다. 강의 종료 때 한 번에 저장하는 구조로 두지 않는다. 저장 간격·파일 형식·복구 가능 범위는 실기기 검증 후 결정한다.
- 앱이 다시 열리면 진행하던 강의와 저장된 내용을 복원한다. 마이크는 자동으로 켜지 않는다.
- `녹음이 중단됐어 · 이어 녹음하기`를 제공하고 사용자가 누르면 같은 강의에 연결한다. 녹음되지 않은 시간은 빈 구간으로 유지하며 정확히 알 수 없는 경계는 미확정으로 남긴다.
- 강제 종료 직전의 미저장 필기·녹음까지 무손실 복구를 약속하지 않는다. 앱 오프라인 재실행과 저장소 삭제·용량 부족·단말 손실도 분리해 검증한다.

## 9. Session State

녹음 상태·노트 편집 가능 여부·전송·전사 처리 상태는 사용자에게 구분되어야 한다. 녹음 종료 뒤 필기·질문을 허용하고 전사 미완료여도 원음/필기로 복습할 수 있어야 한다. 아래는 **개정 전 상태 초안**이며 현재 합의의 확정 상태 기계가 아니다. 새 전이·필드는 구현 전에 정한다.

```text
capture_status     open → closed
audio_status       missing → stored → (failed)
processing_status  pending → ready → (failed)
```

오프라인 여부는 서버가 알 수 없고 알 필요도 없으므로 상태 축에서 뺀다. 클라이언트 배지로만 표시한다.

기존 `READY` 공식도 개정 전 초안이다. 노트 편집 종료를 전사 이용의 필수 조건으로 적용하지 않으며, 소개문 완료 여부로 원음 재생을 막지 않는다.

```text
READY = capture closed AND audio stored AND 캔버스 최종 업로드 완료
        AND transcript · summary · index 확정
```

실패는 단계와 재시도 가능 여부를 함께 기록한다. 원본이 보존돼 있으면 언제든 재처리할 수 있다.

## 11. Processing Pipeline

### 11.1 Ingest

1. MIME·길이 검사, 해시 계산, 중복 확인
2. **원본 보존**
3. 32kbps mono AAC를 기본 후보로 재인코딩하고 Phase 0에서 음질·용량을 실측
4. 20분 안팎 청크로 분할, 경계에 2~3초 겹침
5. 각 청크의 원본 파트·로컬 시작 시각·세션 시간축 오프셋 기록

위 코덱·비트레이트·20분 분할·겹침 수치는 기존 ingest 후보이며 로컬 전사 입력 조건과 실제 강의로 다시 검증한다. 처리 청크는 재시도 범위를 줄일 수 있지만 화면용 주제 목차나 20초 필기 표시 구간과 같은 개념이 아니다. 새 녹음 파일 형식·중단 경계·중복 텍스트 처리가 정해지기 전에는 고정 계약으로 삼지 않는다.

### 11.2 Transcription

**로컬 Whisper를 유력 후보로 다시 검토한다.** 외부 STT 고정과 로컬 STT 폐기 결론은 대체됐다. 다만 PC는 아직 구매하지 않았고 구현체·모델·양자화·동시 부하는 미정이다. 실패 시 외부 API로 자동 전환하는 계약도 아직 없다.

**사용 조건 — 합의**

- PC 구매 고려 예산은 50~70만 원이다. 갈피 서버와 Whisper를 로컬에서 돌리고 답변·소개문 요약은 외부 API를 사용한다.
- 향후 로컬 메모리 에이전트도 고려한다. 모델·작업 성격·실행 주기가 미정이므로 필요한 GPU·메모리나 동시 실행 성능을 확정하지 않는다. 시간에 민감하지 않은 작업이라면 전사와 순차 실행하는 안부터 검토한다.
- 보통 60~90분, 최대 3시간 녹음을 처리한다. 실시간 전사는 요구하지 않는다.
- 목표는 **강의가 끝난 뒤 학교에서 전송하고 귀가 후 복습할 때 전사·소개문이 준비되는 것**이다. 앞서 제시한 종료 후 1시간은 엄격한 SLA가 아니며, 1~2분/5분 완료라는 옛 기준도 폐기한다.
- 업로드 지연·PC 가용성·대기열·전사·소개문 생성을 합쳐 측정한다. 실제 복습까지의 시간 여유는 미측정이므로 특정 PC가 목표를 충족한다고 보장하지 않는다.
- 먼저 실제 한국어 전공 강의의 용어·수식·숫자·부호 보존과 전사 타임코드를 확인하고, 그 품질을 만족하는 모델로 처리 시간·메모리·장시간 부하를 측정한다.

[faster-whisper](https://github.com/SYSTRAN/faster-whisper#benchmark)와 [whisper.cpp](https://github.com/ggml-org/whisper.cpp)는 로컬 실행 검토의 1차 자료다. 공개 벤치마크의 모델·오디오·하드웨어는 사용자 강의/구매 후보와 다르므로 그 숫자를 그대로 적용하지 않는다.

출력에는 오디오 내부 시작·종료 시각과 전사가 필요하다. 전사 타임코드가 필기 시계와의 싱크를 자동 해결하지는 않는다 (§7). 기존 공급자 어댑터·폴백 구현은 현재 구현 승인이 아니며 구체 호출 경계는 모델 결정 후 정한다.

### 11.3 전사 구간과 처리 청크

복습 독바는 시각이 붙은 전사 구간을 사용한다. 단어별 가사 애니메이션 대신 구간 단위 강조를 제공한다. 읽기 좋은 문장/구간 표현과 타임코드 품질은 실측하며, 화면 줄바꿈을 새 시간 경계로 취급하지 않는다.

**자동 주제 목차·3~10분 구간별 요약은 초기 범위 밖이다.** 이를 위해 교수의 주제 전환을 별도로 판정하지 않는다. 내부 처리 청크·전사 구간·필기 농도 표시 구간은 다른 층위다. 사용자의 PDF 페이지 전환도 교수 설명의 주제 경계를 증명하지 않는다.

### 11.4 노트 소개문 요약 — 합의

노트를 선택하는 화면에서 제목 아래 보여주는 **짧은 2~3문장 소개문**을 만든다. 무엇을 배운 강의인지 떠올리고 노트를 고르는 용도다. 핵심 주제·다룬 내용을 적되 강의 전체의 모든 조건·예외를 압축하려 하지 않는다. 예시는 §10.3이다.

- 강의에서 확인되는 내용을 바탕으로 작성한다. 사용자 질문·시온 답변·웹 참고 설명을 교수 설명인 것처럼 섞지 않는다.
- 불명확한 수식·용어를 전공 지식으로 그럴듯하게 채우지 않는다. 소개문은 실제 발화의 대체 정본이 아니다.
- 자동 주제 목차·구간 요약·`claims`·`professor_emphasis` 생성은 초기 범위에 넣지 않는다.
- 외부 API로 생성하되 긴 전사 처리 방법·호출 횟수·입력 범위는 구현 전 확정한다. 3시간 전사를 무조건 한 호출로 처리한다고 가정하지 않는다.
- 옛 `구간 요약 + LLM 자동 용어 교정`을 한 호출로 강제하던 계약은 대체한다. 전사 교정은 §12.4의 필요 시 구간별 수정이 기준이며 자동 교정의 허용 범위는 별도 결정이다.

### 11.5 인덱싱

- **노트 소개문** — 노트 단위의 주제 파악과 선택을 돕는다. 어느 시간 구간의 근거인지 단정하지 않는다.
- **전사 구간** — 정확한 용어·예외·세부 발화를 찾고 실제 오디오로 돌아가는 근거다. 사용자 교정은 해당 검색 내용에 반영한다.
- 볼트 일반 검색과 Lecture 전사 검색의 경계는 유지한다 (§2.6). 소개문이 회수됐다는 이유만으로 세부 전사 확인을 생략하지 않는다.
- 옛 구간 요약 prior·동급 top-k 병합·수치는 적용을 보류한다. 노트 단위 후보와 전사 구간 후보의 결합, 평가셋·가중치·상한은 별도로 정한다. 이번 문서 편집에서 검색 알고리즘을 새로 확정하지 않는다.

### 11.6 Vault commit

아래는 기존 저장 초안이다. 사용자 수정·추가 녹음과 늦게 끝난 처리 결과 사이의 입력 revision/승격 계약은 아직 미정이며, 아래 메타데이터만으로 새 합의가 구현 가능하다고 판정하지 않는다 (§20.2).

Markdown, 오디오, 전사, 타임라인, 캔버스, 슬라이드, 인덱스 문서를 원자적으로 연결한다. 일부만 저장된 상태를 `READY`로 표시하지 않는다.

provenance는 세 개면 충분하다.

```text
stt_engine
summary_model
processed_at
```

v3.2의 `prompt_sha256`, `parser_version`, `output_schema_version`은 감사 대상 조직의 요구사항이다. 1인 시스템에서는 문제가 생기면 재처리하면 된다. 다만 `READY` 세션을 새 모델로 자동 재생성하지는 않는다. 재처리는 명시적 승인으로만 수행한다.

### 11.7 알림

처리가 끝나면 시온 명의로 알린다.

> 시온이 자료구조 3회차를 정리했어요. 확인할 구간 2개 (`?` 마커)

위 알림은 기존 후보 문구다. 완료 알림의 채널·표시·빈도는 아직 확정하지 않았으며 1~2분 처리나 강의 직후 검수를 전제로 하지 않는다. 귀가 후 복습 때 준비되는 것이 목표이고 매번 전사를 확인·교정하라고 요구하지 않는다. 처리 중이라도 원본 녹음·필기로 먼저 복습할 수 있어야 한다.

## 12. Review and Study UX

### 12.1 검색

소개문으로 강의를 알아보고, 세부 질문의 근거는 전사 구간에서 확인한다. 답변에는 실제 확인한 세션·오디오 시각과 필요한 경우 자료 페이지를 연결한다. 소개문을 발화 원문처럼 취급하지 않으며 원본 전사와 현재 교정문을 구분한다. 구체 회수·결합 알고리즘은 §11.5의 미결정 사항이다.

### 12.2 세션 복습 화면

- 오디오 플레이어 · 가사형 전사 독바. 구간별 요약 패널은 초기 범위에서 제외한다.
- 연결된 PDF 페이지와 최종 필기 (재생 위치별 농도 표시)
- **필기 → 음성 역점프** — 획을 탭하면 그 시각 재생
- 오디오를 맞는 설명까지 탐색한 뒤 획과 연결하는 `이 소리가 이 획` 보정 (§7.2)
- ★ · ? 마커 타임라인
- `이 구간 설명해줘` 온디맨드 버튼
- 전사 구간의 별도 `수정` 조작. 일반 탭은 해당 구간 재생으로 유지한다 (§12.4).

**과거 화면을 복원하지 않는다.** 현재 노트에 남은 최종 필기를 기준으로, 재생 위치에 따라 농도만 바꾼다. 지운 획은 재생 위치를 과거로 옮겨도 되살아나지 않는다. 획이 자라나는 애니메이션이나 모든 지우기·실행 취소 이력의 재생은 범위 밖이다.

**합의한 표시 의미**

- 재생 위치보다 뒤의 필기는 연하게, 현재 재생 구간과 이전 구간의 필기는 원래 색·농도로 표시한다.
- 중간부터 재생하면 이전 구간의 필기도 즉시 원래 색·농도로 표시한다. 끝까지 재생하면 녹음과 대응되는 필기는 모두 원래 색·농도가 된다.
- 뒤로 탐색하면 다시 미래가 된 필기는 연해진다. 이는 현재 재생 위치의 표시이지, 사용자가 한 번 들은 부분을 영구히 진하게 남기는 청취 이력이 아니다.
- 복습 중 추가한 필기·녹음과 대응되지 않는 필기는 별도로 구분하며 과거 녹음에 임의로 끼워 넣지 않는다. Q&A 표시 시점·접힘 상태는 아직 미결정이다.

**20초 구간은 후보이지 확정값이 아니다.** 채택한다면 현재 표시 구간 전체를 진하게 하므로 구간 안에서는 실제 재생 위치보다 조금 뒤에 쓴 획도 보인다. 이 표시 구간은 STT 공급자의 전사 세그먼트와 별개다. 길이·경계·농도 값은 실기기 확인 후 정한다.

**전사 독바 — 기존 스트로크 목록 후보를 대체하는 합의**

- 노래 가사처럼 현재 전사 구간을 강조하고 재생 위치를 따라 스크롤한다. 첫 버전은 단어별 애니메이션 없이 전사 구간 단위로 표시한다.
- 전사 구간을 누르면 그 구간 시작부터 재생한다. 같은 오디오 시각에 따라 필기 농도도 갱신한다.
- 사용자가 직접 스크롤하면 자동 따라가기를 잠시 멈춘다. `현재 재생 위치로`를 누르면 다시 따라간다. 읽던 곳을 자동으로 빼앗지 않는다.
- 독바는 사용자가 접고 펼친다. 접어도 녹음 재생과 캔버스 농도 표시는 계속된다.
- 전사와 필기는 모두 오디오 재생 시각을 참조한다. 전사 구간 길이가 필기 표시 구간 길이를 정하지 않는다.
- 전사 미완료·실패 상태에서도 원음 재생·필기 싱크는 사용 가능해야 한다. 독바에는 전사 상태를 보여주며 가짜 전사를 만들지 않는다.
- 개별 스트로크 목록은 초기 범위에서 뺀다. 캔버스의 필기 → 음성 역점프 자체는 유지한다.
- PDF 페이지를 전사 독바에 함께 표시할지, 재생/탐색에 따라 페이지를 자동 이동할지는 미정이다. 사용자의 페이지 열람 기록을 교수 발화의 페이지로 단정하지 않는다.

### 12.3 노트 선택 화면과 소개문 — 합의

제목 아래에 §11.4의 짧은 2~3문장 소개문을 보여준다. 사용자는 무엇을 배운 강의인지 알아보고 선택하며, 실제 복습은 PDF·필기와 전사 독바에서 한다. 소개문에 모든 내용·질문·중요 마커를 밀어 넣지 않는다.

과목별 정렬·미처리 상태 등 노트 목록의 상세 배치는 아직 미정이다. 기존 과목 허브·시험 범위 통합 뷰는 확장 후보로 남기되, 짧은 소개문을 묶는 것만으로 충분한 시험 요약이 된다고 가정하지 않는다. 자동 주제 목차·구간별 요약은 초기 범위에서 제외한다.

### 12.4 필요할 때만 전사 교정 — 합의

- 매 강의 전사 전체를 검수하라고 요구하지 않는다. 읽거나 들으며 발견한 틀린 구간만 수정한다.
- 전사 일반 탭은 구간 재생이다. 별도의 `수정` 동작으로 편집에 들어가며, 상세 입력 UI는 미정이다.
- 수정문은 표시·검색에 반영한다. 최초 전사와 원본 녹음은 보존하고 수정 이력을 구분한다.
- 글자를 고쳤다는 이유로 세그먼트 시작·종료 시각, 오디오 위치, 필기 싱크를 바꾸지 않는다. 타임코드 보정은 다른 작업이다.
- 전공 지식에 맞는 설명으로 고쳐 쓰는 것과 실제 발화를 정확히 옮기는 것을 구분한다. 불확실한 수식·용어는 임의로 완성하지 않고 원음을 확인할 수 있게 남긴다.
- 수정 후 소개문을 언제 다시 만들지, 이전 소개문/검색 결과의 오래됨을 어떻게 표시할지, 늦게 끝난 작업이 사용자 수정을 덮지 못하게 하는 구현은 미정이다. 재인덱싱만으로 소개문 문장이 갱신되지는 않는다.
- 옛 자동 용어 사전 축적·다음 강의 자동 반영은 이번 합의에 포함하지 않는다. 자동 교정 범위·사전·모델 학습은 실제 오류 표본을 보고 별도로 결정한다.

## 13. API Draft

**개정 전 API 초안이다.** 이번 합의로 녹음·노트·처리의 수명이 분리됐고 Q&A·이미지 입력·복구·검색 결합도 열려 있다. 아래 엔드포인트·필드를 구현 확정으로 읽지 않는다. 이 절의 API 재설계는 이번 문서 정리에 포함하지 않았다.

```text
POST /api/lecture/sessions
GET  /api/lecture/sessions/active
GET  /api/lecture/sessions/{id}
PUT  /api/lecture/sessions/{id}/canvas        # base_revision 조건부 상태
POST /api/lecture/sessions/{id}/audio         # 파트 추가
POST /api/lecture/sessions/{id}/slides
POST /api/lecture/sessions/{id}/offset
POST /api/lecture/sessions/{id}/finish
POST /api/lecture/sessions/{id}/reprocess
GET  /api/lecture/sessions/{id}/review
PATCH /api/lecture/segments/{id}              # 전사 교정
GET  /api/lecture/containers/{id}             # 과목 허브
GET  /api/lecture/containers/{id}/range       # 시험 범위 뷰
```

캔버스 PUT은 `capture_device_id`, `base_revision`, 새 `revision`을 받는다. 서버 현재 revision과 `base_revision`이 다르면 `409 Conflict`와 현재 메타데이터를 반환한다. 이벤트 배치·중복 처리 엔드포인트는 만들지 않는다. 오디오 업로드와 캔버스 상태 업로드 모두 네트워크 재시도를 허용하되, 캔버스는 충돌을 자동 덮어쓰지 않는다.

- **질문·도구:** 이미지 질문이 확대율·메뉴·재생 농도의 영향을 받지 않는지, 첨부 기본값/페이지 유지, 전송 질문 불변·후속 정정·Q&A 보존, 일반 물음표/원 미호출, 초안 생존·중복 요청 방지, 수동 접기/미확인 점, 원형 메뉴 네 도구·중앙 취소·정상 점/획 보존을 확인한다.
- **복습:** 중간 시작·뒤로 탐색의 농도, 삭제 획 미복원, 전사 강조·탭 재생·수동 스크롤 중 따라가기 중지·현재 위치 복귀, 독바 접기, 전사 미완료 시 원음/필기 사용, 온라인 오디오 실패 표시를 확인한다.

### Phase 0 — 전사·회수 검증 (개발 없이 오늘 가능)

### Phase 1 — Ingest와 복습 화면

**v3.2에서 순서 변경.** 캔버스보다 복습 화면을 먼저 만든다. 전사가 즉시 끝나므로 **캔버스 없이도 오디오 + 전사 + 요약 + 검색만으로 쓸 수 있는 제품이 완성된다.**

- 실제 녹음 5개 연속으로 올바른 세션에 연결
- 재시도에서 파일 손실 없음, 같은 파일 재공유 시 중복 없음

마지막 항목이 만족되지 않으면 캔버스를 만들어도 사용하지 않는다.

### Phase 1.5 — 캔버스 스파이크

**선행 스파이크 (반나절, Phase 0과 병행 가능)**

pdf.js로 슬라이드를 띄우고 Pointer Events로 펜 그리기만 붙여 30분 필기해 본다. 저장도 동기화도 붙이지 않는다. 목적은 하나뿐이다 — **웹 캔버스로 갈지 네이티브로 갈지를 반나절에 판정하는 것**(§15.4). 견딜 만하면 이 Phase를 그대로 진행하고, 아니면 Phase 1까지만 웹으로 마친 뒤 캡처를 처음부터 네이티브로 설계한다.

이 실험은 Swift 학습이나 개발자 계정 결제보다 먼저 한다. 결정에 필요한 정보만 가장 싸게 사는 순서다.

**작업** — Pointer Events, 펜/손가락 분리, PDF 배경 렌더링, IndexedDB 저장, 새로고침 복구, 지우개·실행 취소, 전체 상태 업로드 크기 실측

**통과 기준**
- 30분 연속 필기에서 스트로크 유실 없음
- 새로고침·브라우저 재실행 후 복구
- 네트워크 차단 중에도 정상 기록
- PDF 배경 위에서도 필기 지연이 거슬리지 않음
- 메모리 사용이 시간에 따라 비정상 증가하지 않음
- 30분 원본 JSON·gzip 크기와 90분 예상 총전송량이 측정됨
- 전체 PUT이 부담되면 페이지 단위 dirty snapshot으로 줄일 수 있음
- 두 탭 또는 stale revision 충돌에서 최신 필기가 자동으로 덮어써지지 않음
- 단축어 실행 뒤 사용자가 구성한 음성 메모·갈피 창 배치가 실사용 가능한 수준으로 복원됨

### Phase 2 — 전체 캡처 세션

**작업** — 90분 필기, 주기 업로드, 오프셋 확정, 다중 파트 오디오, 세션 종료

**통과 기준**
- 90분 세션 데이터 손실 0건
- 동기화 오차 목표 ±5초, 허용 상한 ±10초
- 오프라인 후 자동 복구
- 잘못된 세션에 오디오 연결 0건

### Phase 3 — 양방향 복습과 학습 도구

**작업** — 필기 → 음성 역점프, 슬라이드 인덱스, 마커 목록, 과목 허브, 시험 범위 뷰

**통과 기준**
- 노트에서 획을 탭해 해당 음성으로 이동하는 흐름이 실제로 쓰임
- 마커 오탐 0건
- 시험 범위 뷰가 시험 준비에 실제로 사용됨

### Phase 4 — 다주간 실사용 (2~4주)

**관찰 항목** — 녹음 시작 누락 빈도, 업로드 지연 빈도, 캔버스 사용 중 앱 전환 빈도, 복습 재사용률, 교정 지속 여부, 눈 피로·배터리, 아이패드에서 딴짓이 학습 흐름을 깨는 정도

이 데이터가 쌓인 뒤에만 e-ink나 네이티브를 검토한다.

## 15. Native / E-Ink Gates

검토하더라도 갈피 전체를 네이티브로 다시 만들지 않는다. 캡처(녹음·PencilKit·로컬 DB·업로드 큐)만 네이티브로 가고, 전사·요약·검색·Q&A·볼트·복습 화면은 웹에 남는다.

### 15.1 개발 환경 실현 가능성 (2026-08 확인)

아래는 기존 개발 환경 검토 기록이다. 새 PC·현재 iPad 모델/OS·서명/도구 지원은 이번에 실기기 확인하지 않았다. 네이티브 선택이나 구매 전에 공식 지원 조건을 다시 확인해야 하며 업데이트 제한을 지금 결정하지 않는다.

**가능하다.** 보유 맥은 2020년형 13인치 맥북 프로 4 Thunderbolt 포트 모델(10세대 쿼드 i5)이고 macOS Tahoe 26.3이 설치돼 있다. Xcode 26은 Intel과 Apple Silicon을 모두 지원하는 Universal 빌드를 별도로 배포하며 macOS Sequoia 15.6 이상을 요구한다(9to5Mac 2025-08, Xcode 26 RC 릴리스 노트). 조건을 충족한다.

**주의점**
- 설치 도구(`xcodes` 등)가 인텔맥에서 arm64 빌드를 받아 `Bad CPU type in executable`이 발생한 사례가 보고됐다(XcodesOrg 이슈 #456). 개발자 사이트에서 Universal `.xip`를 직접 받는다.
- Xcode 26.3 이상의 에이전트 기능이 인텔에서 동작하는지는 확인되지 않았다. 외부 코딩 도구를 쓰면 영향이 없다.
- 빌드 속도는 화면 두 개 규모의 캡처 앱에서 문제가 되지 않는다. 섀시 발열은 감수한다.

**시한 — 만료되는 것은 맥이 아니라 아이패드다.**

macOS Tahoe가 인텔 지원 마지막 릴리스이며 이후 3년간 보안 업데이트가 제공된다(WWDC25 Platforms State of the Union). Xcode 27이 인텔을 지원하지 않을 가능성이 높지만 확정된 정보가 아니다. App Store 배포가 목적이 아니므로 Xcode 26.x 고정 자체는 수년간 문제되지 않는다.

실제 제약은 아이패드가 다음 메이저 iPadOS로 올라갈 때 Xcode 26이 해당 버전의 디바이스 지원 파일을 갖지 못해 기기 설치·디버깅이 막히는 것이다. 우회 방법은 있으나 취약하다. **네이티브를 택하면 아이패드 OS 업데이트를 통제해야 하며, 이는 보안과 맞바꾸는 비용이다.**

### 15.2 네이티브가 사는 것

우선순위 순이다. 필기감이 1순위가 아니다.

1. **녹음과 필기의 제어 경계 통합.** 별도 음성 메모·수동 시작 확인·공유 전송 조작을 줄일 수 있다. 다만 이 이점은 웹 통합 녹음에서도 먼저 검증한다. 네이티브라고 §7 전체가 사라지는 것은 아니며 오디오/필기 시각 매핑·중단·재개·drift·복구 검증은 여전히 필요하다.
2. **PencilKit.** 저지연 필기, 팜 리젝션, 압력, 지우개·실행취소·도구 팔레트를 기본 제공한다. Safari의 Pointer Events는 Apple Pencil 저지연 경로를 사용하지 못한다. `PKStrokePoint`의 시간 오프셋을 쓰면 §1.2 방향 B를 점 단위 정밀도로 구현할 수 있다(API 형태 확인 필요).
3. **PDFKit + PencilKit 오버레이.** §6.3 슬라이드 배경 필기가 표준 패턴이 된다. 웹에서는 pdf.js 렌더링, 캔버스 합성, 줌·스크롤 좌표 동기화를 직접 구현해야 하며 이것이 웹 캔버스에서 가장 무거운 부분이다.
4. **저장 안정성.** Safari의 IndexedDB는 저장 압박이나 장기 미사용 시 삭제될 수 있다. 네이티브 파일시스템에는 해당 조건이 없다.
5. **백그라운드 업로드.** 백그라운드 URLSession으로 앱을 벗어나도 업로드가 이어진다.

### 15.3 네이티브가 파는 것

1. **서명 운영.** 무료 개발자 계정의 프로비저닝 프로파일은 7일이다. 학기 내내 매주 재설치해야 하고, 놓치면 강의 직전에 앱이 열리지 않는다. 실패가 최악의 타이밍에 발생하는 구조다. **유료 계정($99/년)은 네이티브의 선택 사항이 아니라 전제 조건으로 취급한다.**
2. **Swift 학습 비용.** 기존 배경은 C와 Node.js다. PencilKit·PDFKit·AVFoundation은 문서화가 충실하지만 시간이 든다. 다만 전자 노트 구상으로 이어지는 자산이기도 하다.
3. **코드베이스 분리와 렌더링 이중화.** 복습 화면은 네이티브로 가도 웹이다. 입력은 PencilKit, 표시는 웹 캔버스가 되며 `PKDrawing`은 자체 포맷이라 웹에서 직접 그릴 수 없다. 스트로크를 좌표·시각 배열로 추출하는 변환 계층이 필요하다.
4. **플랫폼별 클라이언트 유지비.** 서버·업로드 포맷이 중립이면 §2.1의 교체 가능성은 유지할 수 있다. 다만 iPad 네이티브와 Boox(Android)를 모두 지원하려면 캡처 클라이언트를 두 벌 개발·검증해야 한다. 회의 용도의 아이폰·맥 지원도 별도 입력 클라이언트 비용이 생긴다.
5. **검증 비용.** 최소 동작까지의 거리가 멀어 "해보고 아니면 만다"가 어렵다.

### 15.4 결정 시점과 전환 비용

**현재 방향은 웹 통합 녹음·필기 우선 검증이다.** 최대 3시간 사용·중단 복구·시간 연결을 통과해야 채택한다. 실패하면 녹음/캡처 경로만 다른 방식으로 검토한다. 녹음 주체 변경은 시간 모델·파일 수명·복구에 영향을 주므로 옛 "Phase 1까지 완전히 동일, 전환 비용 0" 단정은 적용하지 않는다. Phase 재배정은 아직 하지 않는다.

웹에서 네이티브로 전환하더라도 서버·복습 화면·필기 포맷을 최대한 유지하는 것이 목표다. 실제 교체 범위는 녹음 파일·시간 매핑·복구 계약까지 보고 판단하며, 입력 경로만 바꾸면 된다고 보장하지 않는다.

필기감뿐 아니라 녹음·검색 병행·저장·복구를 실측한다. 30분 필기나 반나절 시험만으로 최대 3시간 전체 계약이 검증됐다고 보지 않는다.

**검토 조건** — 웹 녹음이 중단을 숨기거나 복구 기준을 못 지킬 때, 웹 캔버스 지연·유실이 수업을 방해할 때, 동기화 오차가 허용 범위를 넘을 때, PDF·검색 병행 성능이 부족할 때.

### 15.5 e-ink

검토 조건 — 배터리 관리 번거로움, LCD 눈 피로, 아이패드의 다른 앱이 집중을 반복적으로 깨뜨림, 교재와 필기를 한 기기에서 장시간 사용해야 함.

기기 구매는 파이프라인 검증보다 앞서지 않는다. 네이티브 iPad 캡처를 택해도 공통 데이터 포맷과 API를 유지하면 Boox 경로는 기술적으로 남는다. 다만 웹 캡처 하나를 공유하는 대신 플랫폼별 캡처 클라이언트를 별도로 유지해야 하므로, e-ink 도입은 그 추가 비용까지 정당화할 실사용 근거가 생긴 뒤 판단한다.

## 16. Risks

### 16.1 녹음 정책
학교와 교수의 녹음 허용 범위를 확인한다. 기술로 해결할 수 없는 문제다.

### 16.2 외부 AI 처리 (중요)
외부로 나가는 데이터는 교수 음성만이 아니다.

- 로컬 STT: 새 PC에서 오디오 처리 우선 검토. 외부 STT를 비교/폴백으로 쓸 경우 오디오 외부 전송은 별도 결정
- 소개문 LLM: 전사와 필요한 강의 문맥. 구체 범위는 미정
- 질문/검색: 명시적으로 보낸 질문·선택 이미지·PDF 페이지 이미지, 검색어와 참고 결과. 일반 질문에 주변 강의 자료 전체를 자동 첨부하지 않음
- 결과물: 주변 학생 발화나 수업 중 민감한 내용이 포함될 수 있음

답변·소개문 모델을 외부 API로 사용하는 방향은 합의했다. 다만 학교/교수의 녹음·자료 처리 허용 범위와 공급자별 보존·학습·로그 정책을 확인하는 절차는 여전히 필요하다. 외부 AI를 쓸 수 없더라도 로컬 캡처·로컬 전사까지 기술적으로 불가능해지는 것은 아니며, 허용되지 않는 외부 단계만 구분한다.

**완화** — 필요한 데이터만 전송하고 실제 외부 전송 범위와 원본 보존 위치를 구분한다. 이미지 질문·외부 STT 후보·iCloud 내보내기를 같은 처리 경로로 묶어 자동 허용하지 않는다. 공급자별 정책과 삭제·재처리 절차는 구현 전에 확인한다.

### 16.3 API 의존
공급자 중단, 가격 변동, 지역 제한 가능성.
**완화** — 원본·로컬 캡처와 외부 답변/소개문 생성의 실패를 분리한다. 외부 STT 폴백은 아직 자동 실행으로 승인하지 않았다.

### 16.4 청크 경계 손실
20분 경계에서 단어가 잘릴 수 있다.
**완화** — 2~3초 겹침, 가능하면 침묵 구간에서 분할, 경계 부근 중복 텍스트 병합.

### 16.5 녹음 시작 누락
**완화** — 명시적 시작, 실제 녹음 확인 뒤 상태 표시, 시작 실패/중단 가시화. 같은 앱이나 계속 켜진 타이머를 실제 녹음의 증거로 쓰지 않는다.

### 16.6 잘못된 오디오 연결
**완화** — 캡처를 해당 강의에 연결한 상태로 직접 전송하고 세션 연결·길이·해시 중복 검증을 유지한다. 외부 파일 추가 경로의 상세 확인 UX는 별도다.

### 16.7 캔버스 손실·충돌
**완화** — 단말 중간 저장, 주기 업로드, `base_revision` 충돌 시 자동 덮어쓰기 차단, 복구 검증. 업로드 주기는 복제 지연을 줄일 뿐 전체 손실 상한을 고정하지 않는다. 녹음의 저장·복구 가능 범위도 별도로 확인한다.

### 16.8 요약 사각지대
**완화** — 소개문을 세부 근거의 대체물로 쓰지 않고 전사에서 회수할 수 있게 한다 (§2.6·11.5). 소개문에 빠진 내용·수식·정답 없는 질문을 평가에 포함한다.

### 16.9 동기화 오차
**완화** — 실제 녹음 위치와 필기 시각의 연결, 중단·재개·재실행 경계, drift 검증, 필요한 보정. 매핑이 미확정인 구간에 정밀 점프를 약속하지 않는다. 파일당 오프셋 하나는 일반 해법이 아니다 (§7).

### 16.10 저장 증가와 백업
32kbps mono 기준 90분 약 22MB는 압축 오디오만의 계산이며 원본·PDF·필기·Q&A 이미지·중간 저장·백업 크기는 포함하지 않는다. 실제 녹음 형식과 최대 3시간 데이터를 실측한다.
**완화** — PC 정상 저장 확인 전 단말 원본을 유지한다. 온라인 복습이 기본이며 단말 사본 정리·장기 보존·독립 백업은 별도 정책이다. iCloud는 선택적 동기화/보관 수단이지 독립 백업을 자동 대체하지 않는다 (§5).

### 16.11 슬라이드 자료
저작권이 있는 자료를 볼트에 보관한다. 개인 학습 범위를 벗어나 공유하지 않는다. PDF 용량도 저장 계산에 포함한다.

## 17. Implementation Order

**이 절과 §17.1은 개정 전 순서·로드맵 연결 기록이다.** 사용자 요청에 따라 이번에는 재편하지 않았다. 로컬 전사·웹 직접 녹음·소개문·전사 독바 계약으로 바뀌었으므로 아래 단축어/구간 요약/즉시 전사 전제를 그대로 실행하지 않는다. 전체 설계 후 관련 문서와 함께 갱신한다.

1. **Phase 0** — 실제 강의 오디오로 전사·회수 품질 측정, turbo/large-v3 결정
2. 세션·오디오 ingest API, 재인코딩·청크 분할
3. STT 어댑터, 요약 + 용어 교정, 인덱싱, 볼트 writer
4. 단축어 2개
5. **복습 화면 + 교정 루프 + 알림** ← 여기서 이미 쓸 수 있는 제품이 된다
6. 캔버스 스파이크 (PDF 배경 포함)
7. 로컬 저장과 주기 업로드
8. 90분 전체 캡처, 오프셋 확정, 다중 파트
9. 필기 ↔ 음성 양방향 연결, 마커
10. 과목 허브 / 시험 범위 뷰
11. 다주간 실사용 평가
12. 필요할 때만 네이티브 또는 e-ink

v3.2는 복습 화면이 9번이었다. 전사가 즉시 끝나는 지금 구조에서는 5번에서 이미 가치가 나오고, 캔버스는 그 위의 증강이 된다.

### 17.1 중앙 로드맵 위치

- Phase 0은 지금 진행할 수 있다.
- Phase 1은 단일 GPT·모델 라우팅과 일반 첨부 인증 업로드 패턴이 안정된 뒤, V5-B 이전에 진행한다.


## 20. Open Decisions

1. **외부 AI 처리의 구체 범위** — 답변·소개문 외부 API 방향은 합의했다. 학교/교수의 허용 범위, 실제 전달 자료, 공급자 보존 정책은 구현 전에 확인한다. 외부 STT 폴백·iCloud 전송은 각각 별도 선택이다.
2. **PC·로컬 STT** — 50~70만 원 구매 고려 예산 안에서 실제 강의 품질·최대 3시간 처리·타임코드·향후 메모리 에이전트 부하를 보고 사양/OS/구현체/모델을 정한다. 구매·서버 이전·자동 외부 폴백은 미승인이다.
3. **자동 전사 교정·용어 사전·STT prompt** — 필요 시 사용자 교정은 합의했다. 자동으로 실제 발화를 고쳐 쓰는 범위는 열지 않았고 표본·입력 한도를 확인한 뒤 별도 결정한다.
4. **오디오 보존** — PC 정상 저장 확인 전 단말 정리 금지와 온라인 복습은 합의했다. 확인 후 단말 사본 정리·장기 원본 보존·독립 백업 주기·iCloud 내보내기는 미정이다.
5. **슬라이드 PDF 텍스트 활용** — 선택 질문은 이미지 입력으로 합의했다. 향후 텍스트 검색·사전·소개문 문맥에 PDF를 쓰는 구체 범위는 별도 결정이며 사용자 페이지 전환을 교수 발화와 동일시하지 않는다.
6. **웹 통합 녹음 채택** — 우선 검증 방향은 합의했다. 최대 3시간 필기·PDF·검색 병행과 중단/복구/시간 연결을 실제 iPad에서 확인해야 한다. 기종·OS는 아직 답을 받지 못했다.
7. **유료 개발자 계정** — 네이티브가 확정된 뒤에 결제한다. 학교 차원의 개발자 프로그램 지원 여부는 확인되지 않았다.
8. **아이패드 OS 업데이트 정책** — 네이티브를 택할 경우에만 결정 사항이 된다(§15.1).
9. **녹음 시간·저장·전송 구현** — 첫 샘플 기준, 일시정지/재개 매핑, 브라우저 재실행 경계, 연속 구간/파일 관계, 중간 저장 주기·손실 범위, 백그라운드 전송·재개·ACK 의미를 정한다.
10. **캔버스 업로드 단위** — Phase 1.5의 JSON·gzip·총전송량 실측 뒤 전체 상태 또는 변경 페이지 PUT 중 결정한다.
11. **검색 결합** — 소개문은 노트 단위, 전사는 시간 구간 단위다. 옛 구간 요약 prior·top-k 결합을 그대로 쓰지 않고 세부 회수·평가·상한을 다시 정한다.

### 20.1 UX 설계의 다음 계약 — OPEN

1. **다음 논의: `이 구간 설명해줘`의 입력 문맥.** 가사형 전사 독바는 §12.2로 합의했다. 질문이 가리킬 구간·주변 전사·PDF/필기 첨부와 강의 밖 설명의 표시를 정한다. 아직 제안/미결정이며 일반 질문의 §6.6 기본값을 조용히 넓히지 않는다.
2. **포스트잇 상세 배치.** 수동 접기·펼치기와 알림 표시는 §6.6으로 합의했다. 접힌 표시의 내용·크기·이동·긴 답변 읽기, 페이지 전환 중 열린 포스트잇의 표시, `ㄴ` 후속 입력·전송, PDF 공간이 부족한 경우와 미확인 답변 판정의 세부 조건을 정한다.
3. **질문 입력·원형 메뉴 상세.** 선택 영역/해당 PDF 페이지 이미지와 전송 후 후속 정정은 §6.6, 펜·지우개·선택·질문 네 도구는 §6.8로 합의했다. 모델·이미지 해상도/용량·메뉴 방향·누름 시간·이동 허용치·가장자리 동작은 미정이다. 단순 계산 경로·사용자 필체 학습·임의 코드 실행은 승인하지 않았다.
4. **재생 표시 상세.** 20초 표시 구간·농도·여러 오디오 파트/빈 구간·복습 추가 필기/Q&A 표시, 전사 독바의 페이지 표시/이동, 검색 사이드바와 공간 공유를 정한다. 개별 스트로크 독바 목록은 초기 범위에서 제외했다.
5. **Q&A 저장 구현·삭제.** 초안 보존·재연결 시 기존 결과 자동 확인·못 보낸 질문 수동 재전송·전송 질문 불변/후속 정정은 §6.6으로 합의했다. DB/sidecar, 요청 식별·멱등성·상태 조회, 부분 답변 보존, 요청 취소, Q&A 자체 삭제는 미정이다.
6. **최소 구현 범위.** 필기·저장, 재생 농도, Q&A 보존을 우선하자는 제안은 있으나 기존 Phase를 대체하는 일정은 확정하지 않았다. 모든 설계가 잡힌 뒤 관련 문서를 함께 갱신한다.
7. **교정·소개문·진행 표시.** 전사는 별도 수정 동작으로 필요할 때만 고치고 표시/검색에 반영한다 (§12.4). 편집 UI·소개문 재생성·오래됨 표시·완료 알림·긴 질문 대화 입력 한도는 별도로 정한다.

### 20.2 앞선 v4.2 검토에서 남은 구현 전 과제 — OPEN / 해결 미승인

UX 단순화만으로 아래 문제가 해결된 것은 아니다. 기존 본문의 공식·예시·수치는 해당 전제가 성립할 때의 초안으로 읽는다.

- **시간축:** 시작·일시정지/재개·중단 후 수동 재개는 합의했다. 다만 §7의 단일 오프셋은 파일 내부의 시간 압축을 설명하지 못한다. 브라우저 재실행 후 시계 연결·첫 샘플 기준·누락 경계·drift 보정은 여전히 미정이다.
- **로컬 생존:** 오프라인 상태의 계속 필기와 앱의 오프라인 재실행은 다르다. 앱 파일의 오프라인 가용성·IndexedDB 복구·단말 손실을 구분해 검증해야 하며, 2~5분 업로드 주기는 전체 손실 상한이 아니다.
- **자료의 시간 의미:** `page_change`는 사용자가 본 PDF 페이지이지 교수가 설명 중인 슬라이드의 증거가 아니다. 강한 자동 매핑 설명은 §6.3·11.3에서 정정했지만 PDF 근거 연결·독바 페이지 이동의 구현은 미정이다.
- **파생본 갱신:** 전사 교정·오디오 추가·보정 변경 때 소개문과 인덱스의 재생성 범위, 처리 중 입력 변경과 늦게 끝난 작업의 결과 승격 조건이 미정이다. §9·10·11.6의 옛 상태/메타데이터 초안만으로 해결됐다고 보지 않는다. 재인덱싱만으로 오래된 소개문이 갱신되지는 않는다.
- **STT 폴백:** 텍스트를 반환하는 것과 세그먼트 타임코드를 제공하는 것은 다르다. 공급자·모델별 출력 형식과 타임코드 확보 경로를 검증해야 한다. [OpenAI 전사 API](https://developers.openai.com/api/reference/resources/audio/subresources/transcriptions/methods/create), [Groq STT](https://console.groq.com/docs/speech-to-text)를 근거로 구현 시점에 재확인한다.
- **평가:** 같은 질문 20개로 검색 가중치를 조정하고 최종 성능까지 판정하지 않는다. 미사용 평가 질문·정답 없는 질문·수식 보존 검증이 필요하다. 옛 1~2분/5분 처리 기준은 대체됐고 현재 귀가 후 복습 준비 목표도 실측 완료가 아니다.
