# 갈피 강의 노트 (Galpi Lecture Notes) — System Design

**Version:** 4.2
**Date:** 2026-08-05
**Status:** Phase 0 즉시 실행 가능 / 구현 미착수
**Primary device:** iPad + Apple Pencil
**Core strategy:** Apple 음성 메모 + 단축어 + 갈피 웹 캡처 + 외부 STT API

## v4.2 변경 요약

v4.1의 제품 방향은 유지하되, 구현 직전에 모호하면 데이터 손실이나 검색 누락으로 이어질 핵심 계약과 주변 전제를 확정한다.

- **§7 시간축 계약 보강.** `녹음 시작함`은 오디오 0초가 아니라 대략적 앵커다. 세션 시간과 오디오 로컬 시간의 변환식을 명시하고, 오디오 파트마다 독립 `session_offset_ms`와 보정 상태를 둔다.
- **§8 캔버스 충돌 처리 추가.** 이벤트 스트리밍은 되살리지 않되 `capture_device_id`, `base_revision`, `revision`을 이용한 낙관적 잠금과 `409 Conflict` 복구 경로를 둔다. 오래된 탭이 최신 필기를 덮어쓰지 못한다.
- **§10·§11 전사 정본 분리.** `raw_text`는 보존하고 `corrected_text`를 파생 교정본으로 둔다. 전역 문자열 치환 대신 세그먼트별 교정 결과와 출처·리비전을 기록한다.
- **§2.6·§11.5·§12.1 검색 결합 규칙 확정.** 요약 검색 실패를 판정한 뒤 전사로 넘어가는 조건부 폴백 대신, 두 인덱스를 항상 제한적으로 조회해 가중 결합한다.
- **§5.1 Split View 전제 완화.** 단축어가 원하는 창 배치를 자동 생성한다고 가정하지 않는다. 사용자가 미리 구성한 창 그룹을 재사용하고 실제 기기에서 복원성을 검증한다.
- **§11.1·§11.2 공급자 사실 정리.** 청크 분할은 특정 공급자의 단일 제한에 종속하지 않고 재시도 범위·다중 파트 병합·장애 격리를 위한 공통 규칙으로 둔다. OpenAI 폴백 후보는 최신 전사 모델로 갱신한다.
- **§15 표현 정정.** 네이티브는 Boox 경로를 닫는 것이 아니라 플랫폼별 캡처 클라이언트를 하나 더 유지하게 만든다.
- **§16.2 범위 확대.** 외부 전송 대상을 STT 오디오뿐 아니라 요약·교정 LLM에 전달되는 전사와 슬라이드 텍스트까지 포함하는 `외부 AI 처리`로 정의한다.

## v4.1 변경 요약

네이티브 캡처 앱의 트레이드오프를 §15에 실제 판단 자료로 기록한다. v4.0까지 §15는 "이런 일이 반복되면 검토한다"는 조건 목록이었고, 개발 환경이 가능한지조차 확인되지 않은 상태였다.

- **§15.1 신설 — 개발 환경 실현 가능성 확인.** 보유 맥에서 Xcode 26이 동작한다. 네이티브는 선택지에서 빠지지 않는다. 다만 만료되는 것은 맥이 아니라 아이패드라는 점을 기록한다.
- **§15.2/15.3 신설 — 네이티브가 사는 것과 파는 것.** 가장 큰 이득은 필기감이 아니라 단일 시계다.
- **§15.4 신설 — 결정 시점과 전환 비용.** Phase 0·1은 두 경로가 완전히 동일하므로 결정을 미루는 비용이 0이다.
- **§14 Phase 1.5에 선행 스파이크 추가.** 반나절로 웹/네이티브 판정을 끝낸다.
- **§8.2에 입력 구현 중립 원칙 명시.** 전환 시 버려지는 범위를 입력 경로로 한정한다.
- §20에 열린 결정 3건 추가.

## v4.0 변경 요약

v3.2는 캡처 데이터의 생존과 시간 정합에 설계 분량의 대부분을 썼고, 실제로 매 학기 매일 쓰게 될 복습·시험 준비 영역은 반 페이지였다. v4.0은 그 비중을 뒤집는다.

**하드웨어 사실 정정 (가장 큰 변경)**
보유 맥북은 2020년형 13인치 맥북 프로(4 Thunderbolt 포트, 10세대 쿼드 i5)이며 macOS Tahoe 26.3이 설치돼 있다. whisper.cpp의 Metal 백엔드와 Core ML 경로는 애플 실리콘 전용이며, 인텔맥은 CPU 전용 추론으로 떨어진다. Raspberry Pi 5는 whisper small이 실시간 대비 0.4~0.6배 수준이다. 즉 **한국어 강의 + 영어 전공용어를 감당할 large-v3급 모델을 로컬에서 돌릴 하드웨어가 없다.** 돌릴 수 있는 모델(small)은 쓸 이유가 없고, 쓸 만한 모델은 돌릴 수 없다. 로컬 STT를 폐기하고 외부 API로 확정한다.

이 결정이 파생시킨 삭제 항목이 크다. 야간 배치 큐, 맥북 오프로드 워커, 3단 전사 우선순위, Pi 처리 속도 리스크, 처리 상태 페이지가 모두 사라진다. 동시에 처리 지연이 시간 단위에서 분 단위로 바뀌면서 **강의 직후 교정**이라는 새 흐름이 열린다.

**삭제**
- 이벤트 단위 동기화 프로토콜(`seq`/`from_seq`/`accepted_through_seq`/멱등 재전송) → 주기적 전체 스냅샷 업로드
- 오디오 임펄스 탐지 기반 싱크, 발화 구호, end anchor → 녹음 시작 버튼 시각 + 복습 화면 1탭 보정
- 질문 마커 자동 Q&A 배치 파이프라인 → 북마크 + 온디맨드 생성
- provenance 6필드 → 3필드
- `capturing_offline` 서버 상태 축 → 클라이언트 UI 배지
- Shortcut C, 그리고 Shortcut A의 서버 호출
- 요약 스키마의 `claims` / `professor_emphasis` 추출
- 중간 캔버스 snapshot 전략

**추가**
- 강의 자료(PDF) 임포트와 슬라이드 배경 필기 — v3.2 최대 결함
- 필기 → 오디오 역방향 점프 (실사용에서 가장 잦은 방향)
- 과목 허브 / 시험 범위 통합 뷰
- 전사 교정 루프와 과목 용어 사전 축적
- 오디오 다중 파트
- 전사 세그먼트 병행 인덱싱
- 세션 스키마 일반화 (강의 / 회의)
- 처리 완료 알림

**순서 변경**
복습 화면을 캔버스보다 앞으로 옮긴다. 외부 API로 전사가 즉시 끝나므로, **캔버스 없이 오디오 + 전사 + 요약 + 검색만으로 이미 쓸 수 있는 제품이 된다.** 캔버스는 그 위의 증강이지 전제가 아니다.

## 0. Executive Summary

### 이름 규칙

시스템·서버·저장소·API·repo의 주체는 **갈피**이며 영문 표기는 **galpi**로 고정한다(도메인 `galpi.local`, 토큰 스코프, 코드 네임스페이스 포함). **시온(Xion)** 은 사용자를 상대하는 비서·에이전트의 대표 이름으로, 질문 답변, 요약 발화 주체, 알림 문구에만 쓴다. 시스템 컴포넌트 이름에는 쓰지 않는다.

### 무엇인가

강의 녹음, 펜 필기, 강의 자료, 전사, 구간 요약, 검색, 복습을 하나의 세션으로 묶는 개인용 지식 시스템이다. 핵심 가치는 녹음도 AI 요약도 아니다.

> **시간을 축으로 음성·필기·슬라이드를 연결하고, 어느 쪽에서 시작하든 나머지로 즉시 이동하는 것.**

### 구성

- **녹음:** Apple 음성 메모 (네이티브 안정성을 그대로 사용)
- **세션 연결·업로드:** Apple 단축어
- **필기·마커·복습:** 기존 갈피 웹앱의 Lecture Notes 탭
- **전사:** 외부 STT API
- **요약·교정·인덱싱·저장:** 갈피 서버(Pi)
- **영구 저장:** 볼트의 Markdown + sidecar

Pi는 전사를 하지 않는다. 오디오 수신, API 호출, 요약 생성, 인덱싱, 볼트 커밋만 담당한다. 전부 I/O 중심 작업이라 Pi에 적합하다.

초기 버전은 iPadOS 네이티브 앱을 배포하지 않는다.

## 1. Product Goal

### 1.1 해결하려는 문제

- 교수의 정확한 설명을 다시 찾기 어렵다.
- 필기만 보면 당시 맥락이 복원되지 않는다.
- 녹음만 있으면 원하는 구간을 찾는 데 오래 걸린다.
- AI 요약은 근거 발화와 연결되지 않으면 신뢰하기 어렵다.
- 강의 자료가 별도 앱이나 제조사 클라우드에 갇히면 개인 지식 시스템과 연결되지 않는다.
- 시험 기간에 한 학기치를 다시 훑을 방법이 없다.

### 1.2 핵심 사용자 경험

이 시스템은 **두 방향**을 모두 지원해야 한다. v3.2는 한 방향만 설계했다.

**방향 A — 질문에서 근거로**

> "지난주 자료구조 시간에 교수님이 레드블랙 트리 삽입 예외를 뭐라고 설명했지?"

```text
삽입 직후 부모 노드가 빨간색인 경우, 삼촌 노드 색상에 따라
재색칠 또는 회전으로 분기한다고 설명했습니다.

[자료구조 · 3회차 · 슬라이드 14 · 12:40–14:50]
```

출처를 누르면 해당 시각 원음 재생, 그때까지의 필기, 해당 슬라이드, 전사와 요약이 함께 복원된다.

**방향 B — 필기에서 음성으로 (실사용 빈도가 더 높다)**

복습할 때 먼저 떠오르는 건 "12분 40초"가 아니라 노트의 한 줄이다. 노트를 보다가 이해가 안 되는 획을 탭하면 **그 획을 쓰던 순간의 음성이 재생된다.** 이 기능 하나가 웹 캔버스를 직접 만드는 이유를 정당화한다. 이것이 없다면 기성 필기 앱을 쓰는 편이 낫다.

### 1.3 성공 조건

1. **캡처 신뢰성:** 90분 강의가 앱 전환이나 네트워크 문제로 사라지지 않는다.
2. **검색 회수성:** 기억하는 표현과 전사 표현이 달라도 관련 구간을 찾는다.
3. **근거 복원성:** 답변이 원음·필기·슬라이드로 연결된다.
4. **시험 기간 재사용성:** 학기 중반 이후에도 실제로 열어본다.

4번이 없으면 나머지 셋을 만족해도 사용은 중단된다.

## 2. Design Principles

### 2.1 캡처 단말은 교체 가능하다
아이패드, 향후 Boox, 별도 녹음기는 모두 교체 가능한 클라이언트다. 전사, 요약, 검색, 저장은 서버에 둔다.

### 2.2 로컬 우선, 서버는 나중에
필기는 단말에 먼저 저장한다. 네트워크가 끊겨도 계속 기록되고 재연결 시 올라간다. 다만 **실시간 스트리밍은 목적이 아니다.** 강의 중 서버는 필기 데이터로 아무 일도 하지 않으므로, 손실 상한을 몇 분으로 고정하는 주기적 업로드로 충분하다.

### 2.3 안정성이 우아함을 이긴다
직접 만들지 않아도 되는 것은 만들지 않는다. 녹음은 음성 메모, 전사는 외부 API. 갈피가 만들어야 하는 것은 그 사이를 잇는 시간축과 지식 구조다.

### 2.4 강의 중 상호작용 최소화
필기 외의 동작은 시작·종료 각 한 번씩. 실패는 즉시 눈에 보여야 한다.

### 2.5 사람이 읽는 노트, 기계가 읽는 sidecar
Markdown에는 사람이 읽는 정보와 작은 메타데이터만. 스트로크·타임라인·전사 세그먼트는 JSON/JSONL/SQLite로 분리한다.

### 2.6 요약과 전사를 함께 찾되 역할을 분리한다
**v3.2에서 변경.** 요약만 인덱싱하고 원본을 제외하면 요약이 놓친 내용은 영구히 검색 불가가 된다. 반대로 전사만 검색하면 중복·군더더기가 상위 결과를 잠식한다.

강의 전사는 볼트 전체에 비하면 작다. **요약과 전사 세그먼트를 별도 네임스페이스에 인덱싱하고, 질문마다 둘을 제한적으로 함께 조회한다.** 요약 결과에는 더 높은 prior를 주고 전사 결과는 정확한 용어·세부 발화를 보완한다. 두 후보군을 구간 단위로 합친 뒤 rerank하고, 최종 답변은 원본 전사 구간을 다시 읽어 생성한다.

```text
summary top-k + transcript top-k
→ 동일·인접 구간 병합
→ 가중 결합·rerank
→ 상위 근거만 모델에 전달
```

볼트 일반 검색에는 사람이 읽는 요약만 노출한다. 전사 인덱스는 Lecture 검색 경로 안에서만 사용해 일반 기억 검색을 오염시키지 않는다.

### 2.7 네이티브 전환에는 증거가 필요하다
웹과 단축어로 핵심 가치가 검증되기 전에는 네이티브 앱을 만들지 않는다. 기술적 욕망이 아니라 실사용 실패 데이터가 결정한다.

## 3. Confirmed Decisions

1. 초기 캡처 단말은 보유 중인 iPad와 Apple Pencil이다.
2. Lecture Notes는 별도 앱이 아니라 기존 갈피 웹앱의 독립 탭이다.
3. 녹음은 Apple 음성 메모를 사용하고, 녹음 시작 버튼은 사용자가 직접 누른다.
4. 단축어는 두 개뿐이며, 세션 생성은 웹앱이 담당한다.
5. **STT는 외부 API를 사용한다. 로컬 전사는 폐기한다.**
6. 오디오는 수신 즉시 저용량 재인코딩 후 청크 분할하여 전사한다.
7. 전사 오탈자 교정은 요약 단계의 LLM 호출에서 함께 처리하되 원본 전사를 덮어쓰지 않는다.
8. 필기 데이터는 IndexedDB에 즉시 저장하고, `base_revision` 충돌 검사를 포함한 주기적 상태 업로드를 사용한다.
9. 오디오–필기 정합은 세션 시간축과 파트별 오디오 로컬 시간의 변환으로 관리하고, 복습 화면에서 파트별로 보정한다.
10. 강의 자료 PDF를 세션에 첨부하고 캔버스 배경으로 사용한다.
11. 마커는 명시적 버튼 두 개뿐이며 손글씨 도형 인식은 쓰지 않는다.
12. 세션 스키마는 강의 전용이 아니라 컨테이너 기반으로 일반화한다.
13. Boox 또는 네이티브 캡처 앱은 실사용 데이터 확보 후 조건부 검토한다.

### 4.1 컴포넌트 경계

**Capture Web Client** — 세션 생성·표시, PDF 배경, 필기 캔버스, 시각 태그, 마커, 로컬 저장, 주기 업로드, 강의 중 오디오 재생 차단

**Processing** — 오디오 검증·재인코딩·분할, STT 호출, 구간 분할, 요약 및 용어 교정, 인덱싱, 볼트 커밋, 알림

### 4.2 공유 blob 경계

일반 첨부와 강의 오디오는 저장 기반만 공유한다 — 서버 생성 ID, SHA-256·MIME·크기 검증, temporary 저장, 인증된 읽기, 원자적 finalization, orphan 정리.

강의가 별도로 소유한다 — 세션, 대용량·재개 업로드, 오디오 파트 관리, 청크 전사, 학기별 보존 정책.

사람이 보는 강의 Markdown은 평면 Vault에, 바이너리와 기계 sidecar는 `_attachments/lectures/<session_id>/`에 둔다.

## 5. Shortcut UX

단축어는 두 개다. **A는 서버를 호출하지 않는다.**

### 5.1 Shortcut A — 강의 시작

```text
홈 화면 위젯 실행
→ 음성 메모 열기
→ 갈피 강의 노트 탭 열기
→ 사용자가 미리 구성한 음성 메모 + 갈피 창 그룹으로 전환
```

끝이다. 세션 생성, 과목 추론, 과목 선택은 전부 웹앱이 한다. 단축어 메뉴보다 웹 드롭다운이 고치기 쉽고, 시간표 데이터도 이미 서버에 있다. 이 결정으로 단축어 A의 토큰과 API 실패 경로가 통째로 사라진다.

**Split View는 권장 UX이지 단축어의 보장 기능이 아니다.** 단축어가 원하는 창 배치를 매번 자동 생성한다고 가정하지 않는다. 첫 설정 때 사용자가 두 앱을 나란히 배치해 창 그룹을 만들고, 단축어는 앱을 여는 보조 수단으로 사용한다. 실제 iPad에서 기존 배치가 안정적으로 복원되는지는 Phase 1에서 검증한다. 음성 메모의 녹음 파형이 화면에 계속 보이면 확인 체크박스보다 "녹음 시작 누락"을 강하게 막는다.

### 5.2 Shortcut B — 갈피로 보내기

```text
음성 메모에서 녹음 종료
→ 공유 → 갈피로 보내기
→ GET /sessions/active → 세션·과목·파일명·길이 표시
→ 사용자 확인
→ multipart 업로드
→ 서버 ACK 후 성공 표시
```

**안전장치**
- 활성 세션이 없으면 새로 만들거나 기존 세션을 고르게 한다.
- 같은 오디오 해시는 중복 업로드를 막는다.
- 길이가 비정상적으로 짧으면 경고한다.
- 실패해도 파일을 버리지 않고 재시도 경로를 남긴다.
- 같은 세션에 여러 파일을 이어 붙일 수 있다(§7.4).

잘못된 녹음을 강의에 연결하는 것이 한 번 더 확인하는 것보다 큰 실패다.

### 5.3 Credential

업로드 전용 토큰 하나면 된다.

```text
lecture:session:read-active
lecture:audio:upload
```

회전 가능해야 하며 서버 로그에 원문을 남기지 않는다.

## 6. Capture UX

### 6.1 시작

1. `강의 시작` 위젯 탭
2. 음성 메모 녹음 버튼 탭
3. 갈피 캡처 화면에서 과목 확인 후 **`녹음 시작함`** 탭 — 이 시각이 오디오 t≈0의 기준이 된다
4. 상단 상태 확인

```text
● 녹음: 사용자 확인함 (09:00:07)
● 세션: 활성
● 로컬 저장: 정상
● 서버: 연결됨 / 오프라인
```

웹앱은 음성 메모의 실제 녹음 상태를 읽지 못한다. `녹음` 표시는 사용자 확인 상태이며 기술적 감시가 아니다. Split View로 파형이 보이면 이 한계는 실질적으로 해소된다.

### 6.2 강의 중

- 기본 상태에서 Apple Pencil 입력만 필기로 처리한다. 손가락은 스크롤·확대·이동.
- 화면을 벗어나도 필기는 로컬에 남는다.
- 서버가 끊기면 오프라인 배지를 띄우고 기록은 계속한다.
- 캡처 화면은 TTS, 효과음, 자동 재생을 하지 않는다.

### 6.3 강의 자료 (신규)

**v3.2의 가장 큰 결함은 빈 캔버스를 전제한 것이다.** 대학 강의는 교수 슬라이드 위에 필기하는 것이 기본이고, 자료 없이 백지에 쓰는 설계는 필기감이 아무리 좋아도 실사용에서 밀려난다.

- 세션 생성 시 또는 강의 중에 PDF를 첨부한다. 캔버스 페이지의 배경 레이어가 된다.
- 필기는 별도 레이어이며 PDF 원본을 변경하지 않는다.
- 캔버스 페이지 번호 = 슬라이드 번호. `page_change` 이벤트로 **슬라이드 ↔ 시각 매핑**이 공짜로 생긴다.
- 이 매핑은 세 곳에서 쓰인다.
  1. 구간 분할의 가장 신뢰도 높은 신호 (§11.3)
  2. 복습·검색의 자연스러운 인덱스 — "14번 슬라이드 설명해줄 때"
  3. 답변 출처 표기
- 자료가 없는 강의는 빈 페이지로 폴백한다. PDF는 필수가 아니라 있으면 강해지는 신호다.

### 6.4 마커

캔버스 가장자리에 버튼 두 개. 손글씨 도형 인식은 쓰지 않는다.

- `★ 중요` — 요약에 반드시 포함하고 복습 목록 상단에 고정한다.
- `? 질문` — 그 시각의 북마크를 남긴다.

한 번 탭하면 현재 시각에 이벤트를 남기고, 길게 누르면 최근 마커를 취소한다.

**`?` 마커는 v1에서 자동 답변을 생성하지 않는다.** 마커의 실제 역할은 "여기 몰랐음, 나중에 볼 것"이라는 북마크다. AI가 내 질문을 추측해 미리 답을 만들어두는 기능은 한 번 신기하고 이후 열어보지 않는다. 복습 화면에서 **`이 구간 설명해줘` 버튼(온디맨드)** 으로 같은 결과를 필요할 때만 얻는다. 배치 비용도, 틀린 추측 재고도 생기지 않는다.

`★`는 요약 가중치라는 모호한 개념 대신 "해당 구간을 요약에서 생략하지 않는다"는 명시적 규칙으로 정의한다.

### 6.5 종료

1. 음성 메모 녹음 종료
2. 공유 → `갈피로 보내기`
3. 세션 확인 후 업로드
4. 캡처 화면에서 `세션 종료`
5. 1~2분 뒤 결과 확인 (§11.7)

`세션 종료`는 `capture_status`만 닫는다. 오디오는 종료 전후 언제든 붙일 수 있다.

## 7. Audio–Canvas Synchronization

### 7.1 시간축 계약

세션과 오디오는 서로 다른 시계를 사용한다.

- `session_t_ms` — 갈피 캡처 세션 시작 이후의 단조 증가 시간
- `audio_local_ms` — 각 오디오 파일 내부의 재생 위치
- `session_offset_ms` — 해당 오디오 파트의 첫 프레임이 세션 시간축에서 시작하는 위치

변환식은 하나로 고정한다.

```text
session_t_ms = audio_local_ms + audio_part.session_offset_ms
audio_local_ms = session_t_ms - audio_part.session_offset_ms
```

`녹음 시작함` 버튼은 오디오 0초를 뜻하지 않는다. 사용자가 음성 메모에서 이미 녹음을 시작한 뒤 갈피로 돌아와 누르므로, **버튼 시각은 초기 `session_offset_ms`를 추정하는 대략적 앵커**일 뿐이다. 복습 전에는 `calibrated: false`로 표시하고 정밀한 필기 → 음성 점프를 보장하지 않는다.

v3.2의 임펄스 탐지(±30초 창에서 에너지 피크 검색)는 폐기한다. 강의실에는 기침, 의자, 문, 마이크 팝이 상시 존재해 오탐 가능성이 높고, 오탐이 나도 복습 시점까지 알기 어렵다.

### 7.2 복습 보정

보정은 시스템이 대응 음성을 추측하는 버튼이 아니라, 사용자가 **같은 순간의 획과 음성을 지정하는 앵커 생성 흐름**이다.

```text
복습 화면에서 오디오를 해당 설명까지 탐색
→ 그때 작성한 획 선택
→ `이 소리가 이 획` 탭
→ session_offset_ms 계산·저장
```

계산식:

```text
audio_part.session_offset_ms
  = selected_stroke.t_ms - audio_player.currentTime_ms
```

보정 뒤 같은 파트의 모든 필기 ↔ 음성 이동에 같은 오프셋을 적용한다. 잘못 맞췄다면 다시 보정할 수 있고 이전 값은 감사용 이력으로만 남긴다. 자동 정렬은 이 흐름이 실제로 번거롭다고 확인된 뒤에 검토한다.

### 7.3 시계 모델

- `created_at` — 사람이 읽고 시스템 간 대조하는 벽시계
- `t_ms` — 세션 시작 이후 단조 증가 경과 시간
- `session_offset_ms` — 오디오 로컬 시간을 세션 시간으로 옮기는 파트별 값

기기 벽시계가 조정돼도 스트로크 순서와 재생 위치가 깨지지 않아야 한다. 벽시계는 초기 추정과 감사에만 쓰고, 확정된 재생 위치는 단조 시간과 오프셋으로 계산한다.

### 7.4 오디오 다중 파트

90분 강의에 쉬는 시간이 있으면 녹음을 끊는 것이 자연스럽고, 실수로 멈췄다 다시 켜는 일도 흔하다. **세션당 오디오 1개 전제는 실사용에서 곧바로 깨진다.** 각 파트는 독립 오프셋과 보정 상태를 가진다.

```json
"audio_parts": [
  {
    "part": 1,
    "file": "part1.m4a",
    "session_offset_ms": 0,
    "duration_ms": 2700000,
    "offset_source": "start_confirmation",
    "calibrated": false
  },
  {
    "part": 2,
    "file": "part2.m4a",
    "session_offset_ms": 3300000,
    "duration_ms": 2400000,
    "offset_source": "review_anchor",
    "calibrated": true
  }
]
```

2번째 이후 파트는 업로드 시 사용자가 대략적 시작 위치를 확인하고, 정확한 필기 ↔ 음성 이동이 필요하면 §7.2 방식으로 해당 파트를 보정한다. 재생·검색·전사는 `session_offset_ms`가 적용된 병합 시간축 위에서 동작한다. 따라서 보정 단위는 세션당 한 번이 아니라 **오디오 파트당 최대 한 번**이다.

## 8. Canvas Persistence

### 8.1 저장 모델

v3.2의 이벤트 단위 동기화 프로토콜(`seq`, `from_seq`, `accepted_through_seq`, `duplicate_event_ids`, 멱등 재전송, `sync_state`)을 폐기한다. **강의 중 서버는 필기 이벤트를 소비하지 않는다.** 오디오조차 강의가 끝난 뒤에 올라가는데 필기만 실시간 스트리밍 프로토콜을 가질 이유가 없다.

```text
Pointer event
→ stroke 생성 (t_ms 부착)
→ IndexedDB 즉시 append
→ 화면 렌더링
→ (2~5분마다 / 화면 이탈 시 / 세션 종료 시)
   revision 조건부 캔버스 상태 PUT
```

앞 세 단계는 서버 없이 동작한다. 손실 상한은 "최대 몇 분"으로 고정되고, 구현 부담은 한 자릿수 배로 줄어든다.

90분 필기 전체의 크기는 아직 가정하지 않는다. Tailscale 연결도 강의실에서는 인터넷 또는 핫스팟 업로드를 사용할 수 있다. Phase 1.5에서 **30분 원본 JSON·gzip 크기, 90분 예상 총전송량, 전체 PUT과 변경 페이지만 PUT할 때의 차이**를 실측한다. 전체 상태가 커지면 이벤트 스트리밍으로 돌아가지 않고 변경된 페이지 단위 dirty snapshot으로 축소한다.

### 8.2 캔버스 상태 형식

```json
{
  "session_id": "les_20260901_csds_0900_01",
  "capture_device_id": "ipad-main",
  "base_revision": 11,
  "revision": 12,
  "pages": [
    {"page_id": "p03", "slide_no": 14, "strokes": [
      {"stroke_id": "s1042", "t_ms": 420312, "tool": "pen", "width": 1.8, "points": []}
    ]}
  ],
  "markers": [
    {"t_ms": 427820, "type": "question"},
    {"t_ms": 511004, "type": "important"}
  ],
  "page_changes": [
    {"t_ms": 431200, "page_id": "p04", "slide_no": 15}
  ]
}
```

스트로크마다 `t_ms`를 유지하는 것이 §1.2 방향 B(필기 → 음성)의 전제다. 이 필드는 최적화 대상이 아니다.

**이 포맷은 입력 구현에 중립적으로 유지한다.** 웹 캔버스로 수집하든 PencilKit으로 수집하든 같은 구조로 저장되어야 한다. 그래야 네이티브로 전환할 때 교체 범위가 입력 경로 하나로 한정된다(§15.4).

### 8.3 복구

- 새로고침·브라우저 강제 종료 후 마지막 로컬 상태 복구
- 업로드 실패 시 다음 주기에 자동 재시도
- PUT에는 `base_revision`을 보내고 서버 현재 revision과 다르면 `409 Conflict`를 반환
- 충돌 시 자동 덮어쓰지 않고 서버본·로컬본·기기 ID·수정 시각을 보여준 뒤 복구 선택
- 단일 기기 정상 경로에서는 ACK된 서버 revision을 다음 `base_revision`으로 저장
- 세션 종료 시 미업로드 또는 충돌 미해결 상태면 경고
- 사용자가 명시적으로 지우기 전까지 로컬 원본 유지

단말 로컬본은 캡처 중 가장 중요한 원본이지만, **오래된 탭이 항상 진실인 것은 아니다.** 이벤트 단위 동기화를 폐기한 결정과 revision 충돌 검사는 양립한다.

중간 snapshot 전략은 삭제한다. §12.2의 정적 복원은 일회 replay로 충분하며, 실측에서 느릴 때만 캐시로 다시 도입한다.

## 9. Session State

세 축은 독립이다. 다만 v3.2보다 전이를 줄인다.

```text
capture_status     open → closed
audio_status       missing → stored → (failed)
processing_status  pending → ready → (failed)
```

오프라인 여부는 서버가 알 수 없고 알 필요도 없으므로 상태 축에서 뺀다. 클라이언트 배지로만 표시한다.

사용자에게 보이는 `READY`는 파생 상태다.

```text
READY = capture closed AND audio stored AND 캔버스 최종 업로드 완료
        AND transcript · summary · index 확정
```

실패는 단계와 재시도 가능 여부를 함께 기록한다. 원본이 보존돼 있으면 언제든 재처리할 수 있다.

## 11. Processing Pipeline

### 11.1 Ingest

1. MIME·길이 검사, 해시 계산, 중복 확인
2. **원본 보존**
3. 32kbps mono AAC를 기본 후보로 재인코딩하고 Phase 0에서 음질·용량을 실측
4. 20분 안팎 청크로 분할, 경계에 2~3초 겹침
5. 각 청크의 원본 파트·로컬 시작 시각·세션 시간축 오프셋 기록

공급자와 요금제마다 직접 업로드 제한이 다르므로 특정 숫자를 파이프라인 계약으로 박지 않는다. 청크 분할은 **파일 제한 대응뿐 아니라 실패 재시도 범위 축소, 다중 파트 병합, 경계 장애 격리**를 위한 공통 규칙이다. 구현 시 선택한 공급자의 현재 제한보다 충분히 작은 청크를 사용한다.

### 11.2 Transcription

**외부 API로 확정한다.** 로컬 경로는 하드웨어가 지지하지 않는다.

| 후보 | 공개 가격 기준 | 공개 속도 기준 | 역할 |
|---|---:|---:|---|
| Groq `whisper-large-v3-turbo` | $0.04 / audio hour | 216× | 기본 후보 |
| Groq `whisper-large-v3` | $0.111 / audio hour | 189× | 정확도 비교 대상 |
| OpenAI `gpt-4o-transcribe` | 토큰 기반 | 공급자 기준 | 정확도 폴백 후보 |
| OpenAI `gpt-4o-mini-transcribe` | 토큰 기반 | 공급자 기준 | 비용·속도 폴백 후보 |

*Groq 가격·속도와 무료 플랜 한도는 2026-08 공식 문서 기준이며 구현 직전 다시 확인한다. OpenAI 최신 전사 모델은 기존 Whisper 계열보다 언어 인식·정확도 개선을 표방하지만, 한국어 전공 강의 품질은 Phase 0에서 직접 측정한다.*

Groq 기준 비용 차이는 작으므로 기본 선택은 한국어 전공용어 정확도로 결정한다. 무료 플랜은 현재 두 Whisper 모델에 모델별 일 2,000요청과 오디오 시간 한도를 제공하지만, 무료 정책은 운영 보장이 아니므로 Phase 0 검증에만 의존한다.

공식 확인 링크:
- https://console.groq.com/docs/speech-to-text
- https://developers.openai.com/api/docs/models/gpt-4o-transcribe
- https://developers.openai.com/api/docs/models/gpt-4o-mini-transcribe

**공급자 추상화** — STT 호출은 어댑터 한 겹 뒤에 둔다. 입력은 오디오 청크와 언어, 출력은 `{start_ms, end_ms, raw_text}` 배열로 정규화한다. 공급자 변경, 가격 변동, 서비스 중단이 파이프라인 나머지에 파급되지 않아야 한다. 한국어 특화 상용 STT(클로바, 리턴제로 계열 등)는 아직 가격·품질을 확인하지 않았으며, 어댑터가 있으면 나중에 비교만 하면 된다.

### 11.3 구간 분할

고정 길이로 자르지 않는다. 다음 신호를 함께 쓴다.

1. **슬라이드 전환** — 가장 신뢰도 높은 신호
2. 긴 침묵
3. 주제 전환 표현
4. 중요·질문 마커
5. 최대 길이 상한

권장 구간 길이 3~10분.

### 11.4 요약 + 용어 교정 (통합)

한 번의 LLM 호출에서 요약과 전사 교정을 함께 수행한다.

**입력:** 구간 전사 + 과목 용어 사전 + 해당 구간의 슬라이드 텍스트(있으면)
**출력:**

```yaml
summary: 레드블랙 트리 삽입 후 균형 복원 과정
keywords: [레드블랙 트리, recoloring, rotation]
segment_corrections:
  - segment_id: seg_0042
    corrected_text: "부모 노드와 삼촌 노드가 모두 빨간색이면 재색칠한다."
    reason: "과목 용어 사전과 슬라이드 14 문맥"
source_range_ms: [760000, 1092000]
slide_no: 14
```

v3.2의 `claims`와 `professor_emphasis`는 삭제한다. 억양은 텍스트에 남지 않으므로 "교수 강조" 판정은 사실상 모델의 추측이고, `claims`는 환각 위험이 가장 높은 필드다. 이 필드들이 존재했던 이유는 원본 전사를 인덱싱하지 않겠다는 옛 원칙 때문이었고, §2.6 변경으로 근거가 사라졌다.

**용어 교정을 STT의 `prompt` 파라미터가 아니라 이 단계에 두는 이유:** STT prompt는 공급자별 길이·동작 차이가 있어 과목 사전 전체를 안정적으로 전달하는 계약으로 삼기 어렵다. 반면 요약 단계는 구간 문맥·과목 용어·슬라이드를 함께 보고 세그먼트별 교정안을 만들 수 있으며 추가 호출도 없다.

교정은 `{from, to}`를 전사 전체에 치환하지 않는다. 같은 음절이 다른 문맥에서는 맞을 수 있으므로 **`segment_id`별 완성 교정문**을 반환하고, 서버가 해당 세그먼트의 `corrected_text`만 갱신한다. `raw_text`는 절대 수정하지 않는다.

### 11.5 인덱싱

- **요약 인덱스** — 의미 압축과 주제 회수에 높은 prior
- **전사 세그먼트 인덱스** — 정확한 용어·예외·짧은 발화 보완
- 질문마다 양쪽에서 제한된 top-k를 조회하고 동일·인접 시간 구간을 병합
- 병합 후보를 가중 결합·rerank한 뒤 상위 근거만 답변 모델에 전달
- 볼트 일반 검색에는 요약 인덱스만 노출하고 전사 인덱스는 Lecture 전용 검색 경로에 격리

초기 기준값은 평가 가능한 설정으로 둔다.

```text
summary_top_k = 5
transcript_top_k = 5
summary_prior > transcript_prior
final_evidence_segments <= 4
```

정확한 가중치와 컷은 Phase 0의 20문항 평가로 결정한다. "요약 결과가 하나라도 있으면 전사 검색을 생략"하는 규칙은 두지 않는다.

### 11.6 Vault commit

Markdown, 오디오, 전사, 타임라인, 캔버스, 슬라이드, 인덱스 문서를 원자적으로 연결한다. 일부만 저장된 상태를 `READY`로 표시하지 않는다.

provenance는 세 개면 충분하다.

```text
stt_engine
summary_model
processed_at
```

v3.2의 `prompt_sha256`, `parser_version`, `output_schema_version`은 감사 대상 조직의 요구사항이다. 1인 시스템에서는 문제가 생기면 재처리하면 된다. 다만 `READY` 세션을 새 모델로 자동 재생성하지는 않는다. 재처리는 명시적 승인으로만 수행한다.

### 11.7 알림

처리가 끝나면 시온 명의로 알린다.

> 시온이 자료구조 3회차를 정리했어요. 확인할 구간 2개 (`?` 마커)

강의 종료 후 1~2분이면 결과가 나오므로 **강의실을 나오면서 요약을 확인하고 교정할 수 있다.** 알림이 없으면 이 흐름 전체가 성립하지 않는다. v3.2에는 알림 문구 예시만 있고 경로 설계가 없었다.

## 12. Review and Study UX

### 12.1 검색

```text
질문
→ 요약 인덱스 top-k + 전사 인덱스 top-k 병렬 조회
→ 동일·인접 시간 구간 병합
→ 가중 결합·구간 rerank
→ 원본 `raw_text`와 현재 `corrected_text` 대조
→ 근거 기반 답변 + 세션·슬라이드·타임코드 출처
```

요약을 근거 원문처럼 취급하지 않는다. 최종 답변은 가능하면 원본 전사 구간을 다시 읽고 생성한다.

### 12.2 세션 복습 화면

- 오디오 플레이어 · 현재 구간 전사 · 구간 요약
- 해당 시각의 슬라이드와 필기 (정적 복원)
- **필기 → 음성 역점프** — 획을 탭하면 그 시각 재생
- 오디오를 맞는 설명까지 탐색한 뒤 획과 연결하는 `이 소리가 이 획` 보정 (§7.2)
- ★ · ? 마커 타임라인
- `이 구간 설명해줘` 온디맨드 버튼
- 전사 인라인 교정

**정적 복원만 구현한다.** 특정 시각으로 이동하면 그때까지의 스트로크를 한 번에 그린다. 재생에 따라 획이 자라나는 애니메이션은 v1 범위 밖이다.

### 12.3 과목 허브 / 시험 범위 뷰 (신규)

**v3.2는 세션 단위 화면밖에 없었다.** 그러나 사용 빈도가 가장 높은 순간은 시험 2주 전이고, 그때 필요한 것은 한 강의가 아니라 범위 전체다.

**과목 허브** — 회차 목록, 주제 색인, 미처리 세션 표시, 슬라이드 전체 목록

**시험 범위 뷰** — 3~7주차처럼 범위를 지정하면
- 회차별 요약을 묶은 통합 요약
- 여러 회차에 반복 등장한 주제
- `★` 전체 목록 (교수가 강조했다고 내가 표시한 것)
- `?` 전체 목록 (내가 모른다고 표시한 것) ← 시험 대비 우선순위

이미 저장된 요약을 재조회·재정렬하는 것이므로 구현 비용이 낮다. 반면 체감 가치는 이 문서에서 가장 크다.

### 12.4 교정 루프 (신규)

v3.2의 Phase 0 통과 기준에는 "강의당 수동 교정 5분"이 있었지만 **교정하는 화면이 설계에 없었다.**

한국어 STT의 전공용어 오인식은 반드시 발생한다. 교정한 결과가 인덱스에 반영되지 않으면 검색 품질이 낮은 채로 굳는다.

```text
구간의 `corrected_text` 인라인 수정
→ `correction_source: user`, revision 증가
→ 해당 세그먼트·연결 요약 재인덱싱
→ 검증된 용어쌍만 과목 용어 사전에 축적
→ 다음 강의의 §11.4 프롬프트에 자동 반영
```

사용자 수정은 원본 `raw_text`를 지우지 않는다. 용어 사전에는 모든 문장 교정을 그대로 넣지 않고, 사용자가 확정한 반복 가능한 용어쌍만 추출한다.

교정할수록 다음 강의의 오류가 줄어드는 선순환이 이 시스템의 장기 품질을 결정한다. 초기 용어 사전은 볼트의 과목 노트, 강의계획서, 교재 목차, 슬라이드 PDF 텍스트에서 추출한다.

## 14. Validation Plan

### Phase 0 — 전사·회수 검증 (개발 없이 오늘 가능)

Groq 무료 티어로 비용 없이 실행한다.

**작업**
- 강의 녹음 1~2개를 32kbps mono로 변환하고 원본과 청취 품질 비교
- Groq turbo와 large-v3를 기본 비교하고 필요하면 OpenAI 최신 전사 모델을 폴백 표본으로 추가
- 3~10분 구간 요약 + 용어 교정 프롬프트 시험
- 사전 작성 질문 20개로 회수 테스트

**통과 기준**

| 항목 | 목표 |
|---|---:|
| 전공 용어 식별 | 90% 이상 |
| 질문 20개 중 관련 구간 회수 | 16개 이상 |
| 타임코드 정확도 | 정답 발화 ±30초 |
| 강의당 수동 교정 시간 | 5분 이하 |
| 처리 완료 | 강의 종료 후 5분 이내 |

**동시에 결정할 것:** 기본 STT와 폴백 STT. 우선 Groq turbo와 large-v3를 한국어 전공용어 정확도로 비교하고, 둘 다 기준 미달일 때만 OpenAI 최신 전사 모델 또는 한국어 특화 공급자를 추가 비교한다.

여기서 전사 품질이나 회수율이 낮으면 이후 단계를 시작하지 않는다.

### Phase 1 — Ingest와 복습 화면

**v3.2에서 순서 변경.** 캔버스보다 복습 화면을 먼저 만든다. 전사가 즉시 끝나므로 **캔버스 없이도 오디오 + 전사 + 요약 + 검색만으로 쓸 수 있는 제품이 완성된다.**

**작업** — 세션·오디오 API, 단축어 2개, 청크 전사, 요약·교정, 볼트 writer, 인덱싱, 복습 화면, 교정 루프, 알림

**통과 기준**
- 실제 녹음 5개 연속으로 올바른 세션에 연결
- 재시도에서 파일 손실 없음, 같은 파일 재공유 시 중복 없음
- 검색 결과에서 2회 이하 동작으로 근거 원음 재생
- 교정한 내용이 재검색에 반영됨
- **이 단계만으로 기존 음성 메모 검색보다 실제로 빠르다고 판단됨**

마지막 항목이 만족되지 않으면 캔버스를 만들어도 사용하지 않는다.

### Phase 1.5 — 캔버스 스파이크

**선행 스파이크 (반나절, Phase 0과 병행 가능)**

pdf.js로 슬라이드를 띄우고 Pointer Events로 펜 그리기만 붙여 30분 필기해 본다. 저장도 동기화도 붙이지 않는다. 목적은 하나뿐이다 — **웹 캔버스로 갈지 네이티브로 갈지를 반나절에 판정하는 것**(§15.4). 견딜 만하면 이 Phase를 그대로 진행하고, 아니면 Phase 1까지만 웹으로 마친 뒤 캡처를 처음부터 네이티브로 설계한다.

이 실험은 Swift 학습이나 개발자 계정 결제보다 먼저 한다. 결정에 필요한 정보만 가장 싸게 사는 순서다.

**작업** — Pointer Events, 펜/손가락 분리, PDF 배경 렌더링, IndexedDB 저장, 새로고침 복구, 지우개·실행 취소, 전체 상태 업로드 크기 실측

**통과 기준**
- 30분 연속 필기에서 스트로크 유실 없음
- 새로고침·브라우저 재실행 후 복구
- 네트워크 차단 중에도 정상 기록
- PDF 배경 위에서도 필기 지연이 거슬리지 않음
- 메모리 사용이 시간에 따라 비정상 증가하지 않음
- 30분 원본 JSON·gzip 크기와 90분 예상 총전송량이 측정됨
- 전체 PUT이 부담되면 페이지 단위 dirty snapshot으로 줄일 수 있음
- 두 탭 또는 stale revision 충돌에서 최신 필기가 자동으로 덮어써지지 않음
- 단축어 실행 뒤 사용자가 구성한 음성 메모·갈피 창 배치가 실사용 가능한 수준으로 복원됨

### Phase 2 — 전체 캡처 세션

**작업** — 90분 필기, 주기 업로드, 오프셋 확정, 다중 파트 오디오, 세션 종료

## 15. Native / E-Ink Gates

검토하더라도 갈피 전체를 네이티브로 다시 만들지 않는다. 캡처(녹음·PencilKit·로컬 DB·업로드 큐)만 네이티브로 가고, 전사·요약·검색·Q&A·볼트·복습 화면은 웹에 남는다.

### 15.1 개발 환경 실현 가능성 (2026-08 확인)

**가능하다.** 보유 맥은 2020년형 13인치 맥북 프로 4 Thunderbolt 포트 모델(10세대 쿼드 i5)이고 macOS Tahoe 26.3이 설치돼 있다. Xcode 26은 Intel과 Apple Silicon을 모두 지원하는 Universal 빌드를 별도로 배포하며 macOS Sequoia 15.6 이상을 요구한다(9to5Mac 2025-08, Xcode 26 RC 릴리스 노트). 조건을 충족한다.

**주의점**
- 설치 도구(`xcodes` 등)가 인텔맥에서 arm64 빌드를 받아 `Bad CPU type in executable`이 발생한 사례가 보고됐다(XcodesOrg 이슈 #456). 개발자 사이트에서 Universal `.xip`를 직접 받는다.
- Xcode 26.3 이상의 에이전트 기능이 인텔에서 동작하는지는 확인되지 않았다. 외부 코딩 도구를 쓰면 영향이 없다.
- 빌드 속도는 화면 두 개 규모의 캡처 앱에서 문제가 되지 않는다. 섀시 발열은 감수한다.

**시한 — 만료되는 것은 맥이 아니라 아이패드다.**

macOS Tahoe가 인텔 지원 마지막 릴리스이며 이후 3년간 보안 업데이트가 제공된다(WWDC25 Platforms State of the Union). Xcode 27이 인텔을 지원하지 않을 가능성이 높지만 확정된 정보가 아니다. App Store 배포가 목적이 아니므로 Xcode 26.x 고정 자체는 수년간 문제되지 않는다.

실제 제약은 아이패드가 다음 메이저 iPadOS로 올라갈 때 Xcode 26이 해당 버전의 디바이스 지원 파일을 갖지 못해 기기 설치·디버깅이 막히는 것이다. 우회 방법은 있으나 취약하다. **네이티브를 택하면 아이패드 OS 업데이트를 통제해야 하며, 이는 보안과 맞바꾸는 비용이다.**

### 15.2 네이티브가 사는 것

우선순위 순이다. 필기감이 1순위가 아니다.

1. **단일 시계 — 가장 큰 이득.** 앱이 직접 녹음하면 §7 전체가 사라진다. 오프셋 계산, 복습 화면 보정, 다중 파트 오디오, `녹음 시작함` 버튼, 단축어 두 개, 공유 시트 업로드, 리스크 16.5·16.6·16.9가 함께 사라진다. 시작 흐름이 버튼 하나가 된다. 매 강의 반복되는 마찰이므로 누적 이득이 가장 크다.
2. **PencilKit.** 저지연 필기, 팜 리젝션, 압력, 지우개·실행취소·도구 팔레트를 기본 제공한다. Safari의 Pointer Events는 Apple Pencil 저지연 경로를 사용하지 못한다. `PKStrokePoint`의 시간 오프셋을 쓰면 §1.2 방향 B를 점 단위 정밀도로 구현할 수 있다(API 형태 확인 필요).
3. **PDFKit + PencilKit 오버레이.** §6.3 슬라이드 배경 필기가 표준 패턴이 된다. 웹에서는 pdf.js 렌더링, 캔버스 합성, 줌·스크롤 좌표 동기화를 직접 구현해야 하며 이것이 웹 캔버스에서 가장 무거운 부분이다.
4. **저장 안정성.** Safari의 IndexedDB는 저장 압박이나 장기 미사용 시 삭제될 수 있다. 네이티브 파일시스템에는 해당 조건이 없다.
5. **백그라운드 업로드.** 백그라운드 URLSession으로 앱을 벗어나도 업로드가 이어진다.

### 15.3 네이티브가 파는 것

1. **서명 운영.** 무료 개발자 계정의 프로비저닝 프로파일은 7일이다. 학기 내내 매주 재설치해야 하고, 놓치면 강의 직전에 앱이 열리지 않는다. 실패가 최악의 타이밍에 발생하는 구조다. **유료 계정($99/년)은 네이티브의 선택 사항이 아니라 전제 조건으로 취급한다.**
2. **Swift 학습 비용.** 기존 배경은 C와 Node.js다. PencilKit·PDFKit·AVFoundation은 문서화가 충실하지만 시간이 든다. 다만 전자 노트 구상으로 이어지는 자산이기도 하다.
3. **코드베이스 분리와 렌더링 이중화.** 복습 화면은 네이티브로 가도 웹이다. 입력은 PencilKit, 표시는 웹 캔버스가 되며 `PKDrawing`은 자체 포맷이라 웹에서 직접 그릴 수 없다. 스트로크를 좌표·시각 배열로 추출하는 변환 계층이 필요하다.
4. **플랫폼별 클라이언트 유지비.** 서버·업로드 포맷이 중립이면 §2.1의 교체 가능성은 유지할 수 있다. 다만 iPad 네이티브와 Boox(Android)를 모두 지원하려면 캡처 클라이언트를 두 벌 개발·검증해야 한다. 회의 용도의 아이폰·맥 지원도 별도 입력 클라이언트 비용이 생긴다.
5. **검증 비용.** 최소 동작까지의 거리가 멀어 "해보고 아니면 만다"가 어렵다.

### 15.4 결정 시점과 전환 비용

**Phase 0과 Phase 1은 네이티브든 웹이든 완전히 동일하다.** 네이티브 결정이 영향을 주는 범위는 Phase 1.5 이후뿐이므로 **결정을 미루는 비용은 0이다.** 순서를 뒤집어 Swift 학습과 서명 설정에 먼저 몇 주를 쓰면, 전사 품질 미달로 프로젝트가 중단될 경우 그 시간이 통째로 사라진다.

웹으로 시작했다가 네이티브로 전환할 때 **버려지는 것은 입력 경로뿐이다.** 데이터 모델(§8.2), 업로드 API, 복습 화면의 스트로크 렌더링, 오프셋 처리는 모두 유지된다. 이를 보장하기 위해 스트로크 포맷을 입력 구현에 중립적으로 유지한다.

**사전 추정(검증 전):** 웹 캔버스가 Phase 1.5 통과 기준("필기 지연이 거슬리지 않음")을 넘길 확률은 높지 않다고 본다. 90분 연속 필기에서 지연 차이는 누적된다. 다만 이는 추측이며 §14의 선행 스파이크로 반나절에 확인 가능하다. 추측으로 결정하지 않는다.

**기존 검토 조건(유지)** — 웹 캔버스 지연·유실이 수업을 방해할 때, 음성 메모와 웹앱을 따로 시작하는 실수가 반복될 때, 동기화 오차가 자주 허용 범위를 넘을 때, PDF 배경 렌더링 성능이 웹에서 부족할 때.

### 15.5 e-ink

검토 조건 — 배터리 관리 번거로움, LCD 눈 피로, 아이패드의 다른 앱이 집중을 반복적으로 깨뜨림, 교재와 필기를 한 기기에서 장시간 사용해야 함.

기기 구매는 파이프라인 검증보다 앞서지 않는다. 네이티브 iPad 캡처를 택해도 공통 데이터 포맷과 API를 유지하면 Boox 경로는 기술적으로 남는다. 다만 웹 캡처 하나를 공유하는 대신 플랫폼별 캡처 클라이언트를 별도로 유지해야 하므로, e-ink 도입은 그 추가 비용까지 정당화할 실사용 근거가 생긴 뒤 판단한다.

## 16. Risks

### 16.1 녹음 정책
학교와 교수의 녹음 허용 범위를 확인한다. 기술로 해결할 수 없는 문제다.

### 16.2 외부 AI 처리 (중요)
외부로 나가는 데이터는 교수 음성만이 아니다.

- STT 공급자: 재인코딩된 오디오와 선택적 용어 prompt
- 요약·교정 LLM: 전사 구간, 과목 용어 사전, 필요한 경우 슬라이드 추출 텍스트
- 결과물: 주변 학생 발화나 수업 중 민감한 내용이 포함될 수 있음

로컬 전사가 선택지에서 빠졌으므로 **외부 AI 처리를 허용하지 않으면 자동 전사·요약 파이프라인을 사용하지 않는다.** 기술 결정이 아니라 사용자 판단이며 §20에서 명시적으로 결정한다.

**완화** — STT와 요약 모델 각각의 보존·학습·로그 정책 확인, 필요한 데이터만 전송, 원본 오디오는 갈피에만 보관, STT에는 재인코딩본만 전송, 슬라이드 원문 전체 대신 해당 구간 텍스트만 전달, 공급자별 삭제·재처리 절차 기록.

### 16.3 API 의존
공급자 중단, 가격 변동, 지역 제한 가능성.
**완화** — §11.2 어댑터 한 겹, 폴백 공급자 1개 사전 확인.

### 16.4 청크 경계 손실
20분 경계에서 단어가 잘릴 수 있다.
**완화** — 2~3초 겹침, 가능하면 침묵 구간에서 분할, 경계 부근 중복 텍스트 병합.

### 16.5 녹음 시작 누락
**완화** — Split View 상시 노출, 시작 화면 확인 표시, 종료 시 오디오 미연결 경고, 홈 화면 위젯 고정.

### 16.6 잘못된 오디오 연결
**완화** — 공유 시트 입력 기본, 업로드 전 파일명·길이·세션 표시, 해시 중복 차단.

### 16.7 캔버스 손실·충돌
**완화** — IndexedDB 즉시 저장, 주기 업로드로 손실 상한 고정, `base_revision` 충돌 시 409로 자동 덮어쓰기 차단, 복구 테스트를 기능보다 먼저 구현.

### 16.8 요약 사각지대
**완화** — §2.6의 요약·전사 병렬 후보 조회로 구조적으로 완화한다. Phase 0에서 요약은 놓쳤지만 전사가 회수한 사례와 그 반대 사례를 따로 기록한다.

### 16.9 동기화 오차
**완화** — 세션 시간 ↔ 오디오 로컬 시간의 명시적 변환식, 파트별 `session_offset_ms`, 복습 앵커 보정, 세션 내부 단조 증가 시간. `calibrated: false` 파트는 정밀 점프를 보장하지 않는다고 UI에 표시한다.

### 16.10 저장 증가와 백업
90분 32kbps mono가 강의당 약 22MB, 주 5강 × 15주면 대략 1.6GB다. SD카드는 수명이 짧고 백업 없는 단일 장애점이다.
**완화** — 텍스트 자산은 기존 볼트 백업 경로에 포함, 오디오는 외장 SSD 또는 맥북으로 주기 오프로드. 학기 종료 시 오디오 보존 정책을 정한다. 원본 무압축본을 얼마나 오래 둘지도 함께 결정한다.

### 16.11 슬라이드 자료
저작권이 있는 자료를 볼트에 보관한다. 개인 학습 범위를 벗어나 공유하지 않는다. PDF 용량도 저장 계산에 포함한다.

## 17. Implementation Order

1. **Phase 0** — 실제 강의 오디오로 전사·회수 품질 측정, turbo/large-v3 결정
2. 세션·오디오 ingest API, 재인코딩·청크 분할
3. STT 어댑터, 요약 + 용어 교정, 인덱싱, 볼트 writer
4. 단축어 2개
5. **복습 화면 + 교정 루프 + 알림** ← 여기서 이미 쓸 수 있는 제품이 된다
6. 캔버스 스파이크 (PDF 배경 포함)
7. 로컬 저장과 주기 업로드
8. 90분 전체 캡처, 오프셋 확정, 다중 파트
9. 필기 ↔ 음성 양방향 연결, 마커
10. 과목 허브 / 시험 범위 뷰
11. 다주간 실사용 평가
12. 필요할 때만 네이티브 또는 e-ink

v3.2는 복습 화면이 9번이었다. 전사가 즉시 끝나는 지금 구조에서는 5번에서 이미 가치가 나오고, 캔버스는 그 위의 증강이 된다.

### 17.1 중앙 로드맵 위치

- Phase 0은 지금 진행할 수 있다.
- Phase 1은 단일 GPT·모델 라우팅과 일반 첨부 인증 업로드 패턴이 안정된 뒤, V5-B 이전에 진행한다.
- Phase 1.5~4는 V5-B 시작 전에 마치거나 `PAPER_AUTONOMOUS` 관찰 기간과 병행한다.
- 강의와 거래 시스템은 DB, worker queue, scheduler budget, API cost ledger를 공유하지 않는다. Pi CPU·저장량 상한만 전역 정책에서 함께 조정한다. **STT·요약 API 비용은 갈피 전역 cost ledger에 포함한다.**

```text
V4.5-M 단일 GPT
→ Attachment U0/U1
→ Lecture Phase 0/1  (여기서 실사용 시작)
→ Lecture canvas
→ V5-B 시작 또는 PAPER 관찰과 Lecture field test 병행
```

## 18. Non-Goals

- App Store / TestFlight 배포, 무료 계정 IPA 재서명 운영
- 화자 분리
- 실시간 전사, 강의 중 실시간 AI 답변
- 완전한 손글씨 OCR, 도형 자동 인식
- 협업 필기
- 제조사 수준의 범용 노트 앱 기능
- 로컬 STT

초기 목표는 범용 필기 앱이 아니라 **시간이 연결된 신뢰성 높은 개인 강의 캡처·복습 시스템**이다.

## 20. Open Decisions

1. **외부 AI 처리 허용 여부** — STT 오디오와 요약·교정용 전사·슬라이드 텍스트의 외부 전송 범위를 사용자 결정으로 확정한다. 이것이 "아니오"면 자동 처리 경로는 보류된다.
2. **기본·폴백 STT 공급자** — Phase 0에서 Groq turbo/large-v3를 먼저 비교하고, 기준 미달일 때 OpenAI 최신 전사 모델 또는 한국어 특화 공급자를 추가한다.
3. **STT prompt 사용 범위** — 공급자별 제한을 구현 전 확인하되 §11.4의 세그먼트 교정 설계는 이 값에 의존하지 않는다.
4. **오디오 원본 보존 기간** — 재인코딩본만 남길지, 원본을 학기말까지 둘지.
5. **슬라이드 PDF 텍스트 추출** — 용어 사전 자동 구축에 쓸지, 수동 관리할지.
6. **캡처 구현 방식 (웹 / 네이티브)** — §14 선행 스파이크 결과로 판정한다. 개발 환경 가능 여부는 §15.1에서 확인 완료.
7. **유료 개발자 계정** — 네이티브가 확정된 뒤에 결제한다. 학교 차원의 개발자 프로그램 지원 여부는 확인되지 않았다.
8. **아이패드 OS 업데이트 정책** — 네이티브를 택할 경우에만 결정 사항이 된다(§15.1).
9. **Split View 복원성** — Shortcut A 실행 뒤 사용자가 만든 창 그룹이 실제 기기에서 안정적으로 복원되는지 Phase 1/1.5에서 확인한다.
10. **캔버스 업로드 단위** — Phase 1.5의 JSON·gzip·총전송량 실측 뒤 전체 상태 또는 변경 페이지 PUT 중 결정한다.
11. **검색 결합 가중치** — Phase 0 평가셋으로 요약 prior, 전사 prior, top-k, 인접 구간 병합 범위를 결정한다.

## 21. Final Product Definition

```text
[홈 화면 위젯]
      ↓
[음성 메모] + [갈피 캔버스 · 슬라이드 배경]   (사용자가 구성한 Split View)
      ↓
[공유 → 갈피로 보내기]
      ↓
[재인코딩 → 청크 → STT API → 요약·교정 → 인덱스 → 볼트]   (1~2분)
      ↓
[알림 → 강의 직후 교정]
      ↓
[시온 Q&A ↔ 타임코드 ↔ 음성 · 필기 · 슬라이드]
      ↓
[시험 범위 뷰]
```

최종 판단 기준은 기능 개수가 아니다.

> 기억이 흐릿한 강의 내용을 검색했을 때 몇 초 안에 정확한 설명과 당시 필기로 돌아갈 수 있는가.
> 그리고 시험 2주 전에 이 시스템을 실제로 여는가.

두 질문에 안정적으로 "그렇다"고 답할 수 있을 때 핵심 가치가 검증된 것이다.
